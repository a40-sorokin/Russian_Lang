## 2. Назначение сервиса

RL — сервис для изучения орфографии и пунктуации русского языка, в том числе подготовки к ЕГЭ.
Первая очередь включает:
- выполнение диктантов с пропусками букв и знаков препинания;
- отчёт о выполнении;
- дерево правил и персональный прогресс;
- предпочтения пользователя по правилам;
- тренировку трудных написаний слов по колодам;
- историю выполнений;
- секретные ссылки на пройденный диктант (dictation_done) и прогресс дерева;
- административное управление пользователями и учебным контентом;
- административную статистику использования сервиса (UC-32);
- удаление учётной записи с сохранением обезличенного `user_profile` (административное UC-36, самостоятельное UC-37), а также восстановление/смену пароля и привязку способов входа (UC-38–40).

#### Сохранение результатов

- Посетитель: выполняет доступный диктант и видит отчёт; результат не сохраняется и не участвует в прогрессе. Отчёт формируется в памяти запроса и недоступен после обновления страницы. Действуют ограничения: не более N диктантов в календарные сутки (N = 4, настройка) и неблокирующая рекомендация выдерживать M часов между повторами одной версии (M = 2, настройка).
- Студент: результат диктанта сохраняется в dictation_done; ответы по подстановкам правил — в placeholder_done; ответы по словарным подстановкам — в word_done. Самостоятельная тренировка слов также создаёт word_done, но с dictation_done_id = NULL. Действует ограничение: неблокирующая рекомендация выдерживать M часов между повторами одной версии (M = 2, настройка).
- Администратор: управляет контентом и пользователями; предпросмотр/тестирование контента не должно создавать учебную историю реального студента. Администратор с ролью student в обычных учебных сценариях рассматривается как студент.

## 3. Акторы


#### Посетитель (visitor)

Неаутентифицированный пользователь; не имеет роли в БД. Может просматривать доступные материалы, выполнять активный диктант (с ограничениями) и открывать действующие секретные ссылки только на чтение. Не имеет личной истории и не сохраняет результаты.

#### Студент (student)

Аутентифицированный незаблокированный пользователь с ролью student. Может выполнять диктанты и тренировки слов, видеть отчёты, историю и прогресс, менять предпочтения правил, управлять собственными приватными колодами и секретными ссылками.

#### Администратор (admin)

Пользователь с ролью admin. Управляет пользователями, ролями, правилами, диктантами и версиями, словами, подстановками, публичными колодами, пересчётом прогресса и аудитом, а также может безвозвратно удалять пользователей (UC-36). Может также иметь роль student; в учебных сценариях действует как студент.

#### Планировщик (system scheduler)

Системный процесс ежедневного пересчёта прогресса. Не является ролью пользователя.
При регистрации роль student назначается автоматически в одной транзакции с созданием user_profile. visitor — не роль в БД.

## 5. Пользовательские сценарии


### UC-01. Просмотреть главную и доступные материалы

- Пользователь открывает главную страницу.
- Система показывает описание сервиса и доступные разделы.
- Показывает только публичные (`is_public=true`), активные, не удалённые диктанты с действующей версией и другие публичные материалы.
- Пользователь выбирает диктант или раздел правил.
Архивные и soft-deleted правила не включаются в обычное учебное дерево. Неактивные и чужие приватные диктанты студентам не показываются; собственные приватные доступны автору, администратору доступны все для управления.

### UC-02. Зарегистрироваться

Доступны регистрация по email/password и через настроенные OAuth-провайдеры Better Auth. Новая email-регистрация допускается при `service_setting.email_registration_enabled=true` (по умолчанию true), отключение не блокирует вход, смену и восстановление пароля уже существующих пользователей.

**Email/password:** пользователь вводит email, nickname и пароль 8–128 символов. Для 8–11 символов система показывает предупреждение о повышенном риске и требует отдельный флажок, по умолчанию выключенный. Без подтверждения сервер отклоняет операцию. Подтверждение нигде не хранится, в том числе в аудите. Better Auth хранит только штатный `scrypt`-хеш. Email обязательно подтверждается одноразовой ссылкой; до подтверждения `user_profile` и роль student не создаются, доступа к защищённым функциям нет. Если письмо не доставлено, регистрация не завершается; специальное восстановление отправки в первой очереди не реализуется.

**OAuth:** вход через VK ID, Яндекс ID; Sber ID только после подтверждения работоспособности отдельной интеграции. Используются проверенный issuer, стабильный provider account ID и подтверждённый email. Если email отсутствует/не подтверждён, регистрация остаётся незавершённой до собственной верификации email. Нельзя автоматически связывать идентичности по одному совпадению email.

**OAuth-onboarding (обязательный маршрут для новых пользователей):**
1. До перехода к OAuth-провайдеру на странице RL пользователь явно отмечает `approval_personal_data`; `approval_marketing_mail` и `approval_3th_part` по умолчанию выключены. Сервер связывает снимок выбранных согласий с одноразовым OAuth `state` и проверяет его после callback. Обычная кнопка «Войти» не должна незаметно создавать профиль без такого шага; для новой identity направлять пользователя в регистрацию.
2. После успешного callback, до активации RL, показывается экран «Завершение регистрации»: обязательный nickname, проверка уникальности и формата, отображение подтверждённых согласий. Если провайдер не передал **достоверно подтверждённый** email, пользователь вводит email и подтверждает его одноразовой ссылкой RL. Email, просто возвращённый провайдером, не считается подтверждённым.
3. Пока nickname, согласия и email не подтверждены, профиль не активен, роль student/admin не назначена и защищённые операции недоступны. Запрещено создавать второй активный профиль при повторном callback или обновлении страницы.
4. Незавершённая OAuth-identity хранится в ограниченном состоянии Better Auth/серверной БД и восстанавливается при повторном входе тем же провайдером; подтверждение email завершается только по действующей одноразовой ссылке. Если адаптер Better Auth не поддерживает callback без email, агент обязан провести интеграционный спайк и описать безопасный промежуточный механизм до реализации, а не придумывать фиктивный email или считать непроверенный адрес подтверждённым.
5. `admin_email` применяется только после полного завершения onboarding и подтверждения email; присвоение founder в транзакции должно быть идемпотентным и защищённым от гонки.

**Создание профиля:** в одной транзакции RL создаются активный `user_profile` и роль `student`; при первичном совпадении подтверждённого email с `admin_email` присваивается роль admin и неизменяемый `is_founder_admin=true` (не более одного профиля с true). Изменение admin_email не действует ретроактивно. При отдельной транзакционной границе Better Auth запускать компенсацию/блокировать незавершённую identity — атомарность всей интеграции без доказательства адаптера не заявляется. В `user_profile` записываются три согласия: `approval_personal_data`, `approval_marketing_mail`, `approval_3th_part` (все boolean NOT NULL DEFAULT false). Первое требуется для регистрации и отмечается пользователем явно; два других добровольны и по умолчанию выключены. Сервер проверяет обязательное согласие при регистрации, а не через глобальный CHECK на строке профиля.

**Проверки:** уникальность действующего email и nickname, формат nickname, назначение ролей, идемпотентная регистрация, запрет на восстановление обезличенного профиля. При повторной регистрации тем же email после полного удаления создаётся новый `user_profile.id`.

### UC-03. Войти / выйти

Better Auth проверяет email/password или OAuth, выдаёт сессию. На сервере каждый защищённый запрос проверяет действующий `user_profile` (`is_anonymized=false`, `is_locked=false`), роли и отсутствие незавершённой `user_deletion_jobs`. При успешном создании новой сессии обновляется `last_signin_at` и создаётся append-only `user_signin_log` — источник статистики UC-32. Существующий email/password вход работает и при `email_registration_enabled=false`.

Связывание OAuth/credential-методов не выполняется автоматически при совпадении email; используется только UC-40. При попытке входа через другой неприкреплённый способ выдаётся безопасное сообщение, не раскрывающее чужие данные. Выход завершает текущую сессию Better Auth.

### UC-04. Выполнить диктант без регистрации

Предусловия: dictation_record.is_public = true, dictation_record.is_active = true, запись не удалена, существует активная версия.
- Посетитель выбирает диктант.
- Сервер проверяет **мягкий** дневной лимит N (по умолчанию 4; настройка) в рамках подписанной серверной сессии посетителя. Границы календарных суток (с 00:00 включительно до следующего 00:00 исключительно) определяются в настроенной временной зоне сервиса (`Europe/Moscow` по умолчанию). При исчерпании лимита в этой сессии дальнейшее прохождение ограничивается и предлагается регистрация; очистка cookie может обойти лимит — осознанное ограничение первой очереди.
- Сервер сначала определяет активную версию по `valid_from` / `valid_to` и времени PostgreSQL, затем проверяет **рекомендуемый интервал** для неё: если посетитель уже выполнял её менее M часов назад (по умолчанию 2; настройка), показывает предупреждение, **не запрещая продолжить**: «Для лучшей усвояемости рекомендуется повторить диктант не раньше чем через M часов».
- Парсер разбирает dictation_version.text на текстовые сегменты и подстановки.
- UI показывает текст и варианты ответов.
- Посетитель отвечает и отправляет работу.
- Сервер проверяет ответы и формирует отчёт.
- После показа отчёта (кроме случая, когда это был последний разрешённый диктант в сутки) показывается предложение зарегистрироваться для отслеживания прогресса и создания секретных ссылок.
- Если это был последний разрешённый диктант в сутки, показывается предложение зарегистрироваться для безлимитного выполнения диктантов.
Результат не создаёт dictation_done, placeholder_done, word_done или rule_progress. Альтернативы в UI перемешиваются. _ (пробел) и # (пустой ответ) визуально различаются. Опция + включает проверку регистра; без неё сравнение регистронезависимое. Отчёт формируется в памяти запроса и не сохраняется; после обновления страницы результат недоступен.
Техническая рекомендация: счётчики дневного лимита и времени последнего выполнения версии для посетителя хранить в сессии (cookie) или ином механизме, согласованном с архитектурой; сброс дневного счётчика — в 00:00 по настроенной временной зоне сервиса (`Europe/Moscow` по умолчанию).

### UC-05. Выполнить диктант с сохранением результата

Предусловия: пользователь аутентифицирован, не заблокирован, имеет роль student; диктант активен и не удалён, а также публичен или принадлежит текущему пользователю.
- Студент выбирает диктант.
- Система загружает активную версию. Для **неё** проверяет M часов с предыдущего выполнения: при нарушении показывает предупреждение, но **не блокирует** прохождение.
- Система использует загруженную активную версию и показывает её текст.
- Студент заполняет подстановки и отправляет работу.
- Сервер повторно валидирует payload и проверяет ответы.
- В одной транзакции создаются:
- dictation_done с user_id, dictation_version_id, score_ok, score_fail;
- placeholder_done для подстановок с id правила;
- word_done для подстановок wp, с dictation_done_id;
- обновление user_profile.last_learn_at.
- Запускается пересчёт прогресса этого пользователя.
- Система показывает отчёт.

**Критические правила:**

- прохождение ссылается на фактически показанную версию, а не на версию, ставшую активной позже;
- повторное прохождение создаёт новые записи;
- dictation_done, placeholder_done, word_done append-only;
- score_ok / score_fail учитывают все подстановки, в том числе без id;
- placeholder_done включает только подстановки правил;
- word_done.created_at для ответов внутри диктанта равен dictation_done.created_at;
- ошибка сохранения любого элемента результата должна откатывать транзакцию целиком;
- заблокированный пользователь не может отправить результат.

**Защита от двойной отправки (P0):** при начале каждого авторизованного прохождения клиент генерирует UUID `submission_request_id` и повторно использует его при сетевом retry/двойном нажатии. Сервер атомарно проверяет `UNIQUE(user_id, submission_request_id)` и SHA-256 канонически сериализованных ответов (`submission_payload_hash`). Повтор того же UUID с тем же payload возвращает сохранённый результат без новых `dictation_done`, `placeholder_done`, `word_done` и пересчёта прогресса; другой payload при том же UUID — HTTP 409. Для нового сознательного прохождения генерируется новый UUID. UI отключает повторную отправку до ответа, но это не заменяет серверную идемпотентность. Для анонимного прохождения без записи результата в БД достаточно клиентской защиты от повторного клика.

### UC-10. Просмотреть личный прогресс

- Студент открывает прогресс.
- Система загружает активное дерево и rule_progress.
- Отсутствие строки rule_progress означает **собственный** статус Grey только для `use_in_placeholder = true`; для false собственный статус не применяется. Итоговый статус родителя вычисляется при чтении по детям и может отличаться от Grey.
- Загружается предпочтение из user_rule_preference; отсутствие строки означает InUse.
- Родительские статусы показываются по алгоритму агрегации модели: при `rule.use_in_placeholder = false` статус зависит исключительно от активных дочерних правил (Red при любом Red; Green при всех Green; Grey при всех Grey либо отсутствии активных детей; иначе Yellow). Собственный прогресс для таких правил не хранится.
Прогресс учитывает попытки за последние четыре месяца из placeholder_done и word_done. Для word_done в прогресс правил входят только записи, связанные с word_placeholder.rule_id IS NOT NULL AND is_exception = false.
current_score = (placeholder_ok + word_ok) - (placeholder_bad + word_bad) - 2.
«−2» — коэффициент надёжности: правильных ответов должно быть как минимум на 2 больше, чем ошибок (согласно модели).
Пороговые значения берутся из rule.score_good_default и rule.score_excellent_default только для правил с `use_in_placeholder = true`. Архивные правила не пересчитываются и исключаются из агрегации родителей. Агрегация выполняется снизу вверх по точным правилам модели; нельзя заменять её упрощённым поиском «худшего статуса».

Пример различия при одном активном дочернем правиле со статусом Green и отсутствии собственных выполнений у родителя:

| `rule.use_in_placeholder` родителя | Собственный статус | Итоговый статус |
|---|---|---|
| `true` | Grey | Yellow |
| `false` | Не применяется | Green |

Для `false` без активных детей итоговый статус Grey.

### UC-15. Выполнить тренировку слов — нормативный алгоритм тренировочной сессии (v8.2)

**Цель:** тренировка одной доступной колоды заканчивается автоматически, когда пользователь хотя бы один раз правильно ответил на **каждое** слово колоды в рамках текущей тренировки. Это условие имеет приоритет над квотами показа 2:3:1. Повторный запуск той же колоды создаёт новую тренировку, все состояния и отметки правильного ответа сбрасываются. Исторические `word_done` не сбрасываются.

**Снимок состава:** при старте сервер фиксирует идентификаторы слов колоды и соответствующие активные `word_placeholder` (включая необходимую версию задания). В снимок включаются только слова, у которых есть хотя бы одна активная (не soft-deleted) `word_placeholder`; слова без активных подстановок пропускаются — тренировать их нечем, это допустимое состояние, а не ошибка (администраторский интерфейс выделяет такие слова и фильтрует по ним, см. UC-28). Изменения колоды администратором/владельцем не меняют уже начатую тренировку. Колода без слов, а также колода, в которой после исключения слов без активных подстановок не осталось тренируемых слов, не запускается; показывается сообщение об отсутствии слов.

**Несколько подстановок одного слова (обязательная часть UC-15):** снимок для каждого `word.id` содержит **все** активные `word_placeholder`, отсортированные по `word_placeholder.id` ASC, со стабильными данными задания. За один показ слова сервер предъявляет ровно **одну** такую подстановку. Для каждого слова в `deck_training_session.state_json` хранится `next_placeholder_index` (0-based, начальное значение 0). При выдаче текущей карточки выбранные `word_id` и `word_placeholder_id` фиксируются в `state_json`; повторный запрос текущей карточки не выбирает новую подстановку. Только после **принятого нового ответа**, атомарно с записью `word_done`, индекс увеличивается по модулю числа подстановок данного слова. Идемпотентный retry с тем же `answer_request_id` индекс не увеличивает. Правильный ответ **на любую предъявленную подстановку** делает `ever_correct=true` именно для слова. Тренировка завершается, как раньше, после хотя бы одного правильного ответа на каждое слово; все подстановки каждого слова показывать необязательно. Ограничение UX: некоторые подстановки слова пользователь может не увидеть за одну тренировку; это принято для первой очереди. **Вся описанная логика входит в объём реализации UC-15 (P1); нельзя вынести выбор подстановок или обновление `ever_correct` в отдельную необязательную очередь.**

**Два независимых признака для каждого слова:** `last_answer_state` ∈ `NEW`, `ERROR`, `CORRECT` (`NEW` до первого ответа; далее определяется **последним** ответом) и `ever_correct` (boolean, первоначально false, становится true после **любого** правильного ответа в этой тренировке и более не сбрасывается). Таким образом, повторная ошибка может вернуть `last_answer_state=ERROR`, но не отменяет уже достигнутого `ever_correct=true`. Условие завершения: `ever_correct=true` у всех слов снимка.

**Квоты выбора:** последовательные неперекрывающиеся блоки из максимум шести показов имеют целевые квоты `NEW=2`, `ERROR=3`, `CORRECT=1`. Квоты применяются к состоянию **перед** показом, а не после ответа. Перед каждым показом выбирается категория с наибольшим остатком квоты; при равенстве порядок `ERROR → NEW → CORRECT`. Если категория пуста, выбирается следующая непустая категория с незаполненной квотой в том же порядке; если таких нет — первая непустая в резервном порядке `ERROR → NEW → CORRECT`. Фактическое соотношение может отличаться от 2:3:1 при нехватке категорий или досрочном завершении блока; это допустимо.

**Выбор внутри категории:** слово с наименьшим номером своего последнего показа в этой тренировке (никогда не показанное — раньше всех); затем `deck_word.sort_order` по возрастанию, NULL после чисел; затем `word.id` по возрастанию. Нельзя повторять то же слово два раза подряд, если в доступных категориях есть иное слово; при отсутствии альтернативы повтор допустим. Для соблюдения запрета немедленного повтора сначала исключить последнее показанное слово из кандидатов, если остались другие, затем применить квоты и сортировку. После каждого ответа записать `word_done` (`dictation_done_id=NULL`), обновить `last_answer_state`, при правильном ответе установить `ever_correct=true`, затем проверить завершение, и только если не завершено — выбрать следующее слово. После фиксации каждого ответа запускается пересчёт прогресса этого пользователя (гранулярность «после каждого ответа» — решение от 10.11.2026); сбой пересчёта не откатывает сохранённый ответ, страховка — ежесуточный пересчёт. Пользователь немедленно видит результат каждого ответа (верно/неверно) — обратная связь входит в сценарий тренировки, а не в историю (история слов исключена из первой очереди, см. раздел 8).

**Сессия:** сервер хранит `training_id` (случайный UUID), `user_profile.id`, `deck.id`, неизменяемый снимок слов/подстановок, состояния, `ever_correct`, номер показа, квоты текущего блока, последнее показанное слово, статус `active|completed|abandoned`, время создания/последней активности. Клиенту передаётся только идентификатор сессии и текущая карточка; все переходы выполняет сервер. Для первой очереди хранить состояние в PostgreSQL в отдельной служебной таблице `deck_training_session` с JSONB-снимком и состояниями, TTL 24 часа с последней активности. Изменение/завершение сессии и запись ответа выполняются атомарно в транзакции с блокировкой строки сессии; повторная отправка одного ответа с тем же `answer_request_id` идемпотентна (не создаёт вторую `word_done`). Одновременно разрешена только одна активная тренировка конкретной колоды у пользователя; повторный запуск завершает прежнюю как `abandoned` и создаёт новую. Истёкшая сессия переводится в `abandoned`; возобновление не предусмотрено.

**Завершение:** после последнего необходимого правильного ответа сервер устанавливает `completed`, больше не выдаёт карточки и показывает «Колода пройдена» с двумя действиями: «Выбрать другую колоду» (список доступных колод) и «Перейти к диктантам» (каталог диктантов). Завершение до шестого показа в блоке допустимо. Повторное прохождение той же колоды разрешено из каталога и начинает новую сессию. Если пользователь покинул тренировку до завершения, это `abandoned`, а не `completed`.

**Критерии приёмки:** (1) начальные состояния NEW/false; (2) после каждого ответа обновляются оба признака; (3) правильный ответ, затем ошибка дают ERROR/true; (4) 2:3:1 соблюдается при доступности категорий и отсутствии ограничений; (5) при нехватке категорий нет зависаний; (6) финальный правильный ответ немедленно завершает тренировку; (7) повторный запуск сбрасывает состояния; (8) каждый ответ даёт одну `word_done`, дубликат запроса не дублирует запись; (9) конкурентные запросы сериализованы; (10) после завершения предлагаются колоды и диктанты; (11) слова без активных подстановок исключаются из снимка, колода только из таких слов не запускается; (12) каждый ответ тренировки запускает пересчёт прогресса пользователя; (13) для слова с несколькими подстановками показывается одна на карточку и идёт циклический выбор; (14) повтор текущей карточки и идемпотентный retry не сдвигают индекс; (15) первый правильный ответ на любую подстановку закрывает слово.

### UC-17. Создать секретную ссылку

Поддерживаемые ресурсы (согласно модели v8.2):
- dictation — ссылка на конкретное прохождение dictation_done (семантика resource_id уточнена: для resource_type = 'dictation' хранится id записи dictation_done, а не dictation_record);
- rule_progress_tree — правило и прогресс его активного поддерева.
Студент выбирает ресурс и срок действия. Система генерирует `raw_token` из 32 криптостойких случайных байтов, кодирует его base64url без padding (43 символа), вычисляет `token_hash = SHA-256(raw_token)` и сохраняет только `token_hash` (UNIQUE NOT NULL). Соль не нужна для токена с 256 битами случайной энтропии. URL `/share/<token>` выдаётся только при создании. Ссылка имеет `scope = 'all'`, `is_active = true`, `user_id` владельца. Для `dictation` предупреждение: «Получатель ссылки увидит ваши ответы, включая ошибки, и общий счёт за конкретное прохождение диктанта».
Безопасность: токен не содержит последовательный ID, не хранится в логах, аналитике, кэше; по хэшу выполняется индексированный поиск; доступ только на чтение, проверяются владелец, ресурс, срок и отзыв. В URL и в БД не используется отдельная соль.

### UC-18. Открыть ресурс по секретной ссылке

- Пользователь открывает URL.
- Система извлекает токен из URL, вычисляет его хэш и находит ссылку по token_hash.
- Проверяет is_active, expires_at, deleted_at и доступность ресурса.
- Показывает ресурс только на чтение.
- Для rule_progress_tree показывает указанное правило и активное поддерево с прогрессом владельца.
- Для dictation (фактически — dictation_done) показывает исторический отчёт о конкретном прохождении: заголовок диктанта, номер версии, общие счётчики, сохранённые детали (ответы по правилам и словам).
При отзыве, истечении срока, soft delete или недоступности ресурса показывать: «доступ к информации ограничен».
Посетитель не может выполнять действия от имени владельца. Ссылка ведёт на конкретное прохождение; не путать с dictation_record.

### UC-19. Отозвать секретную ссылку

Студент открывает список собственных ссылок и отзывает выбранную. Система устанавливает is_active = false, обновляет audit-поля. Отозванная ссылка больше не предоставляет доступ. Список показывает ресурс, срок действия и статус.


## 6. Административные сценарии и управление учётной записью


### UC-20. Найти и просмотреть пользователей

Администратор видит список `user_profile`: nickname, email, `last_signin_at`, `last_learn_at`, `is_locked`, роли и **статус профиля «действующий / обезличенный»** (по `is_anonymized`). Поддержать поиск (включая email), фильтры по роли/блокировке/активности, сортировку и пагинацию. У обезличенных профилей персональные поля NULL; их не заменять ранее известными значениями из истории. Отдельного статуса «soft-deleted, но ещё действующий» для профиля нет; `deleted_at` обозначает завершение фазы 1, статус очистки Better Auth показывается отдельно по `user_deletion_jobs` при наличии прав.
Профиль пользователя показывает роли, даты активности, блокировку и причину, историю диктантов и тренировок, прогресс, колоды и ссылки в объёме, нужном для администрирования. Не показывать секреты аутентификации.

### UC-21. Заблокировать / разблокировать пользователя

Блокировка: администратор указывает причину; система проверяет `is_founder_admin=false` и атомарно устанавливает `user_profile.is_locked=true`, `locked_at`, `locked_by`, `lock_reason`, `restored_at=NULL` с записью аудита. **Нормативный источник состояния блокировки — RL `user_profile.is_locked`, не дублирующий Better Auth `banUser`.** Все защищённые endpoint и вход проверяют этот флаг. После коммита сервер **обязательно отзывает все действующие Better Auth-сессии** пользователя через подтверждённый серверный механизм (`revokeUserSessions` или эквивалент установленного адаптера); при временной ошибке повторяет действие через фоновую задачу и восстановительный опрос заблокированных профилей с активными сессиями (техническая схема — в `RL_Стек_v9.8.md`). Пока отзыв не подтверждён, блокировка не маркируется как полностью технически завершённая, но доступ уже закрыт серверной проверкой `is_locked`. Запрещено считать отзыв «необязательным, если поддерживается».
Разблокировка: устанавливает is_locked = false, заполняет restored_at, добавляет запись в admin_audit_log с action_type = 'unlock_user'.
Блокировка не удаляет историю и прогресс. Проверять is_locked на каждой защищённой серверной операции.
 
**Исключение founder:** профиль с `is_founder_admin=true` запрещено блокировать (`is_locked=true`) любым администратором, API и штатным worker. Запрет проверяется сервером и PostgreSQL-триггером; операция отклоняется без частичного изменения. Разблокировка уже ошибочно заблокированного founder допускается только в контролируемой восстановительной процедуре, с аудитом. Блокировка других пользователей действует по общему сценарию.

### UC-22. Управлять ролями

Администратор назначает/снимает роли через role_user_profile. Дубли запрещены. Действующий профиль обязан иметь хотя бы одну роль; снятие последней роли отклоняется транзакционно. Обезличенный профиль имеет ноль ролей. student назначается при регистрации, visitor не хранится в БД, role.code неизменяем. Предотвращать снятие роли admin с последнего администратора. Изменения журналировать. Роль admin может быть назначена автоматически только **первому** founder при первоначальном `admin_email`-бутстрапе (UC-02); последующие совпадения не выдают admin; ручные назначения и снятия выполняются здесь.
Администратор с ролью student в учебных сценариях (UC-04–UC-16) рассматривается как студент; его прохождения создают историю и участвуют в пересчёте прогресса. Предпросмотр (UC-26) — отдельный режим без сохранения истории. Снятие роли student не удаляет исторические записи.

### UC-23. Управлять деревом правил

Администратор может создавать/редактировать правила, менять пороги, перемещать узлы, менять sort_order, управлять use_in_placeholder, is_norule, is_exception, is_archived, просматривать использования и прогресс.

**Ограничения:**

- корень all_rules нельзя редактировать/удалять;
- нельзя создать второй корень или цикл; сервер проверяет отсутствие цикла при каждом создании/перемещении под транзакционной блокировкой корневой строки `all_rules`; прямого триггера БД против циклов в P0 нет, UC-34 диагностирует повреждения и запросы защищены от бесконечной рекурсии;
- is_norule = true не может иметь детей; флаги `is_norule` и `use_in_placeholder` независимы: для словарного правила значение false возможно, но не обязательно;
- `use_in_placeholder = false` запрещает ссылки `id:<rule.id>` в новых и редактируемых версиях диктантов; при переключении true → false проверяются активные и запланированные к публикации версии с такими ссылками, а также версии с историческими `dictation_done`; переключение отклоняется даже для активной версии без попыток;
- для `use_in_placeholder = false` собственный `rule_progress` отсутствует, итоговый статус вычисляется только по активным детям, а при отсутствии детей равен Grey;
- архивные правила не показываются в обычном дереве, не пересчитываются и не участвуют в агрегации;
- при deleted_at обязательно is_archived = true;
- физическое удаление ограничено FK и не является обычным действием;
- архивация родительского правила не архивирует дочерние автоматически.
Каждое изменение записывать в admin_audit_log.

### UC-24. Управлять записями диктантов

Студент создаёт и редактирует **только собственные приватные** записи диктантов. Администратор может управлять любыми записями: создавать, редактировать title, subject, is_active, sort_order, просматривать версии и число прохождений, выполнять soft delete. `dictation_record.is_public` имеет значение `false` при создании и на уровне БД; перевод в `true` и обратное изменение публичности разрешены **только администратору**. Проверка авторства и полномочий обязательна на сервере для каждого чтения и изменения, включая прямые URL. dictation_record содержит заголовок; текст хранится в dictation_version.text.
При создании записи одновременно создаётся первая версия (version_number = 1, valid_from = now(), valid_to = NULL). UC-25 применяется для публикации последующих версий (version_number > 1).

### UC-25. Создать и опубликовать версию диктанта

- Владелец приватного диктанта или администратор вводит текст и valid_from (по умолчанию now() Postgres). Публиковать диктант для общего доступа может только администратор; публикация очередной версии внутри приватного диктанта не меняет его видимость.
- Сервер валидирует текст и подстановки.
- В транзакции блокирует открытую версию FOR UPDATE.
- Закрывает предыдущую версию на момент публикации.
- Создаёт новую версию с version_number = prev.version_number + 1, valid_to = NULL.
- Пересобирает dictation_version_rule и dictation_version_word_placeholder.
Для первой версии используется UC-24.

**Инварианты:**

- интервал полуоткрытый [valid_from, valid_to);
- активность определяется серверным временем Postgres;
- valid_from не в прошлом и строго позже предыдущего;
- интервалы не пересекаются и не имеют разрывов;
- одна открытая версия на диктант;
- версию с прохождениями редактировать нельзя;
- архивную версию редактировать нельзя;
- конкурентная публикация защищена транзакционной блокировкой и ограничениями БД.
Механизм отложенной публикации без cron: активная версия определяется запросом с условием valid_from <= now() < valid_to (или valid_to IS NULL) на серверном времени Postgres.

### UC-26. Проверить и предварительно просмотреть диктант

Парсер должен выдавать детальные ошибки с индексом/номером подстановки и причиной. До публикации проверить (согласно модели v8.2):
- текст не пуст, размер нормализованного текста не более 30 720 байт (30 КиБ UTF-8; CRLF/CR→LF, Unicode NFC);
- не более 100 подстановок;
- не более 5 альтернатив в подстановке;
- длина альтернативы не более 5 символов;
- допустимые символы соответствуют грамматике модели;
- правильный ответ — первая альтернатива;
- указанные rule.id и wp.id существуют;
- пары (id правила, key) и (wp, key) уникальны в версии;
- key по умолчанию равен 1;
- символы `[`, `]`, `{`, `}` вне подстановок запрещены; `/` вне подстановки запрещён: сервер и редактор удаляют его до валидации, сообщая пользователю количество удалённых символов; внутри подстановки `/` остаётся разделителем альтернатив;
- пробелы внутри [] незначащие;
- + включает case-sensitive проверку.
При ошибке публикация не выполняется, предыдущая версия не изменяется. Предпросмотр/тестовый запуск не создаёт историю реального пользователя. Администратор с ролью student в обычном прохождении создаёт историю как студент.

### UC-27. Управлять словами и подстановками слов

Администратор создаёт и редактирует word и word_placeholder, связывает подстановку с правилом, задаёт исключение, просматривает использование и выполняет soft delete.

**Правила:**

- word.data хранится в нижнем регистре;
- уникальна пара (data, spart);
- rule_id IS NULL — словарное слово без правила;
- при rule_id IS NOT NULL пороги наследуются от rule, собственные пороги должны быть NULL;
- привязка `word_placeholder.rule_id` при создании или редактировании разрешена только к правилу с `use_in_placeholder = true`; иначе сервер возвращает ошибку валидации;
- is_exception = true допустимо только при rule_id IS NOT NULL;
- исключения не входят в прогресс указанного правила;
- soft-deleted подстановки не используются в новых диктантах/колодах;
- слово/подстановку с историческими выполнениями физически не удалять.

**Просмотр использования (источник определён 10.11.2026):**

- использование подстановки word_placeholder — производная таблица `dictation_version_word_placeholder` (версии со ссылками `wp:<id>`, с состоянием версии: активная / запланированная / архивная); заполняется и пересобирается вместе с `dictation_version_rule`;
- использование слова — состав колод (`deck_word`) и список его подстановок;
- справочно — количество выполнений подстановки из `word_done` (история попыток, не использование в контенте);
- для правил используется `dictation_version_rule` (без изменений).

### UC-28. Управлять публичными колодами

Администратор создаёт и редактирует публичные колоды, состав deck_word, порядок слов, is_active и soft delete. Только admin может установить is_public = true. Дубли слов внутри колоды запрещены. При просмотре состава колоды слова без активных (не soft-deleted) word_placeholder визуально выделяются; доступна фильтрация состава по признаку «есть/нет активных подстановок». Такие слова — допустимое состояние (например, словарная заготовка), но они не тренируются (см. UC-15) и не попадают в диктанты.

### UC-29. Пересчитать прогресс одного пользователя

Администратор выбирает пользователя по ID или email, подтверждает операцию. Система запускает rule_score_calculation, показывает время, число обработанных правил и ошибки. История попыток не меняется; user_rule_preference не меняется. Действие журналируется как recalc_progress.

### UC-30. Пересчитать прогресс всех незаблокированных пользователей

Администратор подтверждает массовый пересчёт. Система запускает фоновую задачу, обрабатывает пользователей пакетами и показывает статус/ошибки. Область — все незаблокированные пользователи. Сбой на одном пользователе не должен без необходимости останавливать всю задачу. Операция идемпотентна и журналируется.

### UC-31. Просмотреть журнал административных действий

Показывать admin_audit_log: дату, администратора, action_type, пользователя/правило/прочие ключи, значения и комментарий. Поддержать фильтры по периоду, администратору, действию и объекту. Журнал append-only: не редактировать и не удалять записи. Не записывать в него пароли и секретные токены.
Обезличивание пользователя в UC-36/37 не удаляет `user_profile`, поэтому FK `admin_audit_log.admin_id/user_id` продолжают ссылаться на обезличенную запись; ON DELETE SET NULL не срабатывает. Это не является редактированием журнала со стороны приложения — это следствие FK-ограничения, документированное в разделе 7. В интерфейсе такие записи отображаются с пометкой «пользователь удалён»; для `delete_user` персональные идентификаторы в `value_1..3` запрещены; `value_1` содержит только случайный `operation_id`, как описано в UC-36.

### UC-32. Просмотреть статистику использования сервиса

Специфицировано 10.11.2026 (v8.2). Системные ошибки вынесены из UC-32: администратор просматривает их в GlitchTip (self-hosted, стек); отдельный экран ошибок в RL — вне первой очереди (см. раздел 8).

Администратор открывает раздел «Статистика» панели администрирования. Раздел состоит из страниц (или вкладок) по показателям; к каждому показателю применяются общий фильтр периода и фильтры аудитории.

**Показатели:**

1. **Регистрации новых пользователей** — количество созданных `user_profile` за период (по `user_profile.created_at`).
2. **Авторизации зарегистрированных пользователей** — количество входов за период (по `user_signin_log`). Авторизация — успешный вход с созданием новой сессии Better Auth; продление действующей сессии не считается. Журнал заполняется при каждом входе (UC-03).
3. **Выполненные диктанты** — количество прохождений (`dictation_done`) за период, в том числе: количество **повторных прохождений** (прохождение считается повторным, если у того же пользователя есть более раннее `dictation_done` по той же версии); суммарные и средние `score_ok` / `score_fail` (верные ответы и ошибки).
4. **Выполненные слова** — количество `word_done` за период, с разбивкой по источнику: в рамках диктанта (`dictation_done_id` IS NOT NULL) / самостоятельная тренировка (`dictation_done_id` IS NULL).
5. **Созданные колоды** — количество `deck`, созданных за период (по `deck.created_at`; считаются все колоды, включая публичные админские).
6. **Слова, добавленные в колоды** — количество `deck_word`, созданных за период (по `deck_word.created_at`).

**Период:** день, неделя, 10 дней, месяц или произвольный интервал «от–до». Границы календарных дней и недель — во временной зоне сервиса (Europe/Moscow по умолчанию); «10 дней» — скользящие 10 суток, включая текущую; время событий — timestamptz (UTC). Пустые периоды отображаются нулями, а не ошибкой.

**Аудитория (применяется к показателям 2–6):**

- все пользователи;
- когорта — пользователи, зарегистрированные за заданный период (по `user_profile.created_at`; период когорты задаётся отдельно и не обязан совпадать с периодом показателей);
- роль — все / имеющие роль student (включая администраторов с ролью student) / имеющие роль student и не имеющие роли admin (по `role_user_profile`).

Для показателя 1 (регистрации) фильтры аудитории не применяются: показатель сам определяется периодом.

**Правила подсчёта.** Считаются все события за период, включая события пользователей, позднее заблокированных; при UC-36/37 персональные события исключаются из подсчёта после физической очистки, а исторические регистрации сохраняются; события создания колод и добавления слов считаются по факту события (`created_at`) независимо от последующего soft delete; при безвозвратном удалении (UC-36) события пользователя удаляются и перестают учитываться. Показатели агрегированные, без персональных данных; детализация по конкретному пользователю — через UC-20. Отображение — таблицы со значениями за период и разбивкой по дням внутри периода; визуализация графиками — на усмотрение реализации (Recharts, стек).

**Критерии приёмки:**

- все шесть показателей доступны за каждый вид периода, включая произвольный интервал;
- фильтры аудитории (когорта регистрации, роль, «студент без роли admin») применяются к показателям 2–6 и не применяются к показателю 1; период когорты задаётся независимо от периода показателей;
- повторные прохождения определяются корректно: второе и последующие прохождения той же версии тем же пользователем;
- суммы и средние score_ok / score_fail соответствуют данным dictation_done за период;
- word_done корректно разбивается по источнику (диктант / самостоятельная тренировка);
- границы дней и недель — по временной зоне сервиса;
- статистика агрегированная, не содержит персональных данных и не дублирует UC-20;
- события заблокированных пользователей учитываются, пока не удалены по UC-36/37; при обезличивании персональные события удаляются, исторические регистрации остаются по `user_profile.created_at`;
- пустой период отображается нулями, а не ошибкой.

**Не смешивать с UC-34:** диагностика контента описана отдельно.


**Показатель «Регистрации»:** число профилей с `user_profile.created_at` в выбранном периоде, включая позднее обезличенные tombstone-профили. Дата `created_at` при UC-36/37 сохраняется, поэтому историческое число регистраций не уменьшается. Это не означает сохранения личных событий: входы, прохождения и другие события удаляются согласно политике удаления. При фильтрах по текущей роли или статусу обезличенный профиль может не попадать в сегмент, поэтому интерфейс должен пояснять, что общий показатель — исторический, а сегментированный — по сохранившимся атрибутам.

### UC-33. Плановый пересчёт прогресса

Ежедневно планировщик запускает rule_score_calculation для всех активных (необезличенных и незаблокированных) пользователей. Время попыток — последние четыре месяца. Для cron calculated_by = NULL. Архивные правила пропускаются, предпочтения не меняются. Задача должна быть идемпотентной и сохранять сведения об ошибках.

### UC-34. Диагностика контента

Проверка дерева включает поиск циклов с отслеживанием уже посещённых `rule.id`; при обнаружении цикла показывается нарушение целостности без зависания. Это диагностика повреждений, не замена обязательной серверной проверки при UC-23.

Администратор запускает проверки:
- корректность единственного корня и дерева, отсутствие циклов;
- отсутствие детей у is_norule;
- валидность подстановок активных версий;
- соответствие dictation_version_rule и dictation_version_word_placeholder фактическому тексту;
- существование связанных правил и word_placeholder;
- слова без активных подстановок;
- неиспользуемые подстановки и правила;
- пустые колоды;
- просроченные/отозванные секретные ссылки;
- аномалии прогресса.
Диагностика не исправляет данные автоматически без отдельного подтверждения.

### UC-35. Редактировать собственный профиль

- Студент открывает форму редактирования профиля.
- Может изменить nickname.
- Сбор трёх согласий при регистрации обязателен; отдельный кабинет управления маркетинговыми подписками и юридическим документооборотом не входит в первую очередь.
- Email не редактируется вручную — синхронизируется из Better Auth.
- Сервер проверяет формат nickname и уникальность без учёта регистра.
- Изменения сохраняются; при конфликте уникальности возвращается понятная ошибка.

### UC-36. Административное удаление учётной записи

Администратор не вправе удалять самого себя этим сценарием; собственное удаление — UC-37. **Первый администратор не может быть удалён никем и никаким штатным способом**, включая UC-36, UC-37, API и фоновые задачи. Его роль admin нельзя снять. Администратор выбирает другого пользователя, подтверждает необратимость и решает серверную задачу сложения двух двузначных чисел (не более 3 попыток с серверным лимитом). Используется общая двухфазная процедура UC-37 с целью, выбранной администратором, без требования повторного входа удаляемого пользователя. Внешние FK общего контента не блокируют обезличивание. Журнал аудита содержит только случайный `operation_id`, без email/nickname целевого лица.

### UC-37. Самостоятельное удаление учётной записи

**Предусловия:** активный профиль и сессия Better Auth; `is_founder_admin=false`. Перед удалением обязательна **повторная аутентификация**: для email/password — проверка текущего пароля; для OAuth — новый провайдерский вход с подтверждением того же issuer/provider account ID и свежести. Если провайдер не позволяет проверить свежесть, такой путь удаления запрещён до появления согласованной альтернативы. Существующая cookie-сессия сама по себе недостаточна. Пользователь явно подтверждает необратимость и информируется об удаляемой учебной истории и сохранении публичного контента.

**Фаза 1, единая транзакция RL:** сервер проверяет полномочия, неизменяемый `is_founder_admin`, свежую повторную идентификацию, отсутствие активной задачи и защищает операцию блокировкой по `auth_user_id`/профилю. Создаётся `user_deletion_jobs` с `operation_id`, `auth_user_id`, `pending`. Удаляются `word_done`, `placeholder_done`, `dictation_done`, `rule_progress`, `user_rule_preference`, `user_signin_log`, `deck_training_session`, секретные ссылки, собственные приватные колоды и диктанты с версиями и зависимостями, роли и иные личные зависимые записи в порядке реальных FK; чужие прохождения удаляемых приватных диктантов удаляются, и прогресс затронутых пользователей пересчитывается; чужие самостоятельные `word_done` по удаляемым приватным колодам сохраняются. Публичные диктанты, колоды, правила, словарь и ссылки автора/редактора на профиль сохраняются. `user_profile.id` остаётся; персональные поля, `auth_user_id`, nickname, email, даты активности/блокировок очищаются, `is_anonymized=true`, `anonymized_at` и `deleted_at` заполняются. Аудит append-only записывает факт и случайный operation_id без PII. Ошибка откатывает фазу 1.

**Фаза 2, после коммита:** серверная задача `pg-boss` идемпотентно удаляет Better Auth user и относящиеся `account`, `session`, credential, verification; отсутствие записи считается успехом. При сбое повторение 1, 5, 30 минут, затем ежечасно; после 10-й неудачной попытки (включая первую) — `failed_manual_review`, `next_attempt_at=NULL`; ручное возобновление с новым циклом `attempts=0` и аудитом. Tombstone блокирует вход и воссоздание старого профиля даже при сбое удаления identity. Только после успешной второй фазы UI показывает полный успех; до этого — «данные RL удалены, ожидается очистка учётной записи».

**После удаления:** прежний email можно использовать для новой регистрации; создаются новые Better Auth user и `user_profile.id`, старые роли/прогресс/приватные объекты не восстанавливаются. Публичный контент без специального переназначения остаётся доступен администраторам на обычных правах. Риск наличия PII в названиях и текстах материалов осознанно принят, автоматического анализа нет; процедура реагирования на обращения о PII сохраняется. Запрет самоудаления первого администратора несмотря на риск по 152-ФЗ принят как бизнес-решение и должен пройти юридическую оценку до запуска.

**Тесты:** rollback, гонки регистрации и удаления, повторная задача и 404, изоляция сторонних ответов, сохранение публичных FK, удаление приватных материалов и истории, блокировка pending/failed, повторный вход, отказ первому администратору, ошибки OAuth с другой identity, отсутствие PII в логах и аудите.

### UC-38. Восстановить забытый пароль

Для credential account независимо от `email_registration_enabled`: форма принимает email; ответ не раскрывает существование аккаунта. Better Auth создаёт одноразовый ограниченный по времени токен и отправляет ссылку через почтовый сервис, размещённый согласно требованиям хранения данных в РФ. Новый пароль 8–128 символов, для 8–11 — явное непредустановленное подтверждение риска без хранения; все старые сессии отзываются. Недействительный/использованный токен отклоняется. Восстановление не создаёт новый профиль.

### UC-39. Сменить пароль

Действующий credential-пользователь указывает текущий и новый пароль 8–128 символов. Для 8–11 символов требует подтверждения риска. Проверка текущего пароля серверная, сохраняется только scrypt-хеш, другие сессии отзываются. При отсутствии credential account пользователь должен сначала добавить способ email/password по UC-40.

### UC-40. Управлять привязкой способов входа

Аутентифицированный действующий пользователь привязывает VK ID/Яндекс ID или email/password после доказательства владения текущим и новым способом входа. Совпадение email недостаточно. Запрещено привязать чужой внешний account или отвязать последний доступный способ авторизации. При привязке сохраняется прежний `user_profile.id`.

## 7. Сквозные правила


#### Блокировка

is_locked = true запрещает вход и защищённые действия. При блокировке заполнить locked_at, locked_by, lock_reason; при разблокировке is_locked = false, заполнить restored_at. Блокировка не удаляет историю.

#### Исторические данные

`user_profile` не удаляется физически в UC-36/37: профиль необратимо обезличивается, личная история (включая append-only записи) удаляется как документированное исключение; Better Auth identity удаляется отдельно. Публичные версии диктантов сохраняются, приватные материалы удаляемого пользователя удаляются.
admin_audit_log: append-only; при обезличивании профиль остаётся и его FK в журнале не обнуляются. Новая запись об удалении содержит только случайный operation_id в value_1, остальные поля идентификации цели пусты, nickname/email/raw auth_user_id не сохраняются.

#### Прогресс и предпочтения

rule_progress — вычисляемое состояние обучения. user_rule_preference — пользовательское намерение. Смена InUse / Ok / Pause не меняет прогресс. Отсутствие записи предпочтения означает InUse.

#### Архивные правила

Архивное правило не отображается в обычном учебном дереве, не пересчитывается и не входит в агрегацию родителей. Исторические попытки сохраняются. После снятия архивации правило снова участвует в следующем пересчёте. Предпочтение на архивном правиле сохраняется, но не отображается и не влияет на пересчёт.

#### Версии диктантов

Текст хранится в dictation_version.text. При наличии прохождений версия неизменяема. Активность определяется по периоду, серверному времени Postgres и полуоткрытому интервалу.

#### Безопасность

Все права проверяются на сервере. Нельзя доверять переданным клиентом user_id, owner_id, admin_id без проверки сессии. Студент изменяет только собственные ресурсы. Секретные ссылки дают только чтение. Заблокированный пользователь не выполняет защищённые действия. Секреты не пишутся в логи. Для секретных ссылок хранится только token_hash; исходный токен показывается один раз при создании. UC-36 — удаление другого пользователя администратором после подтверждения и арифметической проверки; UC-37 — самостоятельное удаление после повторной аутентификации. Первого администратора нельзя удалять ни самостоятельно, ни другим администратором. admin_email — серверная настройка; неявное связывание аккаунтов по совпадающему email запрещено.

#### Ограничения для посетителей и студентов

- Дневной лимит диктантов для посетителя: N = 4 (настройка), контроль по календарным суткам.
- Ограничение на повторное выполнение одной версии диктанта: не чаще 1 раза в M часов (M = 2, настройка) для посетителя и студента.
- После каждого диктанта (кроме последнего в сутки для посетителя) — предложение зарегистрироваться для отслеживания прогресса и секретных ссылок. После последнего — предложение о безлимитном выполнении.

### Уточнения реализации v7.4

- **M часов** — неблокирующая рекомендация при повторном прохождении; версию определяют до проверки. **N = 4 в день** — мягкий лимит посетителя по подписанной серверной сессии, возможен обход очисткой cookie; не заявлять как защиту от злоумышленника. Дневная граница — настроенная временная зона сервиса (`Europe/Moscow` по умолчанию).
- **Прогресс дерева:** `rule_progress.status` — собственный статус только при `use_in_placeholder = true`; при false строка не хранится и итоговый статус определяется только детьми; итоговый статус родителей вычисляется на чтении, включая родителей без строки. При изменении порогов пересчитывать собственные статусы, при перемещении/архивировании дерева — инвалидировать кэш агрегации. Сервер проверяет циклы при перемещении узлов.
- **Словарные пороги** `word_placeholder.score_*` в P0/P1 не создают статуса слова: это резерв для P2; текущая тренировка использует историю `word_done` и приоритет повторения ошибок.
- **Исторические отчёты:** сохранять неизменяемый снимок ответа на словарную подстановку; изменение слова/подстановки не должно переписывать прошлый отчёт. Для несвязанных подстановок ограничение UC-06 сохраняется.
- **Версии диктанта:** при уже запланированной будущей версии новая публикация запрещена до её отмены/переноса; администратор получает явную ошибку. Отмена/перенос — P1, с транзакцией и блокировкой. Нормативная грамматика одна — в действующей модели ER; валидатор UI и API используют одни правила.
- **Регистрация:** создание профиля и роли атомарно в RL; атомарность Better Auth+RL не заявляется без доказанной поддержки общей транзакции. При разрыве — компенсация и запрет незавершённого входа.

## 8. Не входит в первую очередь

**Важно:** UC-38 (восстановление пароля), UC-39 (смена пароля) и минимальный серверный security rate limiting для чувствительных endpoint входят в P0. Их нельзя исключать, ссылаясь на возможности Better Auth.

Не реализовывать без отдельного согласования:
- автоматические рекомендации следующего диктанта/упражнения;
- challenges и соревнования;
- реферальную систему;
- кабинеты преподавателей/тьюторов;
- мобильное приложение (API учитывать в архитектуре, но приложение — отдельная очередь);
- сложные персональные учебные траектории;
- черновики версий диктантов;
- cron для переключения версий диктантов;
- сложные scope секретных ссылок: в первой очереди только all.
Дополнительно вынести за пределы первой очереди, но учесть в архитектуре:
- полный экспорт данных пользователя — вне первой очереди; безвозвратное удаление реализуется через UC-36 в первой очереди;
- самостоятельное удаление аккаунта реализуется в первой очереди как UC-37 (P1);
- переназначение владения публичным контентом — P2; UC-36/37 не отказывают из-за публичного авторства, FK на обезличенный профиль сохраняется;
- уведомления (email о разблокировке, публикации диктанта, истечении секретной ссылки) — P2;
- поиск по правилам и диктантам — P2, учесть индексы БД на этапе А;
- подписка на публичные колоды — P2;
- история тренда прогресса — P2, потребует отдельной истории снимков;
- расширенные поведенческие anti-abuse/антифрод-алгоритмы — вне первой очереди; **базовый серверный security rate limiting P0 обязателен** на вход, регистрацию, OAuth, отправку/проверку email, восстановление пароля и повторные запросы. Конкретные числовые значения утверждаются в волне 0, не определяются AI-агентом произвольно. Мягкий дневной лимит N и предупреждение M часов сохраняются.
- массовая загрузка/импорт дерева правил и учебного контента — отдельная будущая задача; в первой очереди дерево правил наполняется ручным редактированием администратором (UC-23).
- экран системных ошибок в интерфейсе RL — вне первой очереди; системные ошибки администратор просматривает в GlitchTip (self-hosted, стек); при необходимости отдельного экрана — отдельная спецификация (P2);
- отдельный экран/каталог истории тренировок слов (word_done) — исключён из первой очереди (решение от 10.11.2026, бывший F06.3); ответы по словам видны в отчёте конкретного прохождения диктанта (UC-06, UC-18) и в ходе тренировки (UC-15).

## 9. Открытые вопросы и ограничения

- Юридическая оценка запрета самоудаления первого администратора (152-ФЗ), сроков хранения резервных копий и служебных задач требуется до промышленного запуска. Это не функциональная задача AI-агента.
- Секретные ссылки используют SHA-256 от 32 случайных байтов без соли; история блокировки ведётся в admin_audit_log.
- Принятые в v8.2 алгоритм тренировок 2:3:1, пересчёт прогресса после каждого ответа, индексы использования word_placeholder, административная статистика UC-32 и исключение отдельной истории слов сохраняются.
- Бизнес-риск PII в названиях/текстах сохранённых публичных материалов принят; автоматический поиск PII при удалении не предусмотрен, но административное редактирование и рассмотрение обращений обязательны.

## 10. Порядок реализации

Этап A — основной пользовательский цикл (P0)
- Better Auth, регистрация с тремя флагами согласий (обязательное `approval_personal_data`), роли и блокировка.
- Дерево правил и карточка правила.
- Диктанты, версии, парсер и валидация публикации.
- Выполнение диктанта посетителем (с дневным лимитом и рекомендацией M часов) и студентом (с предупреждением о M часах).
- Отчёт и предложения зарегистрироваться.
- Сохранение попыток студента.
- Расчёт прогресса и предпочтения.
- История.
- Базовая административная панель.
- Ручной/плановый пересчёт и журнал действий.
Этап B — слова и обмен доступом (P1)
- word, word_placeholder.
- Приватные и публичные колоды.
- word_done и тренировка слов.
- Интеграция слов в прогресс правил.
- Секретные ссылки (с учётом уточнения: resource_id для dictation → dictation_done).
- Статистика использования (UC-32) и диагностика контента (UC-34).
- Редактировать собственный профиль (UC-35), без управления юридическими согласиями.
- UC-36/37: удаление личных данных и необратимое обезличивание профиля; pg-boss завершает вторую фазу очистки Better Auth, с tombstone `user_deletion_jobs`.
Этап C — дальнейшее развитие (P2)
Рекомендации, challenges, рефералы, преподаватели, уведомления, поиск, подписка на колоды, тренд прогресса, полный экспорт данных, переназначение владения контентом — отдельные спецификации.

## 11. Общие критерии приёмки

- Реализованы основной поток, права, ошибки и альтернативные ветви согласованных Use Cases.
- Посетитель выполняет диктант и видит отчёт без сохранения учебных записей; отчёт не сохраняется и недоступен после обновления страницы.
- Мягкий дневной лимит посетителя (N = 4, настройка) действует в пределах одной подписанной серверной сессии и календарных суток в настроенной временной зоне; очистка cookie может обойти лимит и не считается нарушением требований первой очереди. При исчерпании показывается предложение зарегистрироваться.
- При повторном выполнении той же активной версии ранее M часов (по умолчанию 2) посетителю и студенту показывается неблокирующее предупреждение с рекомендуемым интервалом; прохождение не запрещается.
- После каждого диктанта посетителя (кроме последнего в сутки) показывается предложение зарегистрироваться для отслеживания прогресса и секретных ссылок; после последнего — предложение о безлимитном выполнении.
- Студент выполняет диктант; история и прогресс обновляются согласованно.
- Повторные прохождения создают новые исторические записи.
- Каждое прохождение ссылается на конкретную версию.
- Прогресс соответствует алгоритму модели: четыре месяца, источники попыток, исключения, архивные правила, `use_in_placeholder`, агрегация снизу вверх. Правила с false не имеют собственного прогресса и получают итоговый статус только по активным детям.
- Предпочтения не меняют рассчитанный прогресс.
- Тиражирование предпочтений соответствует правилам подтверждения для детей с прогрессом; для детей без прогресса состояние перезаписывается автоматически.
- Тренировки слов создают word_done и влияют на прогресс только в предусмотренных моделью случаях.
- Секретные ссылки проверяют token_hash, срок, отзыв и soft delete и дают только чтение; исходный токен показывается только при создании. Для resource_type = 'dictation' ссылка ведёт на конкретное прохождение dictation_done, а не на dictation_record.
- Административные действия журналируются.
- Заблокированный пользователь не может выполнять защищённые действия.
- Soft delete не разрушает историю.
- Ограничения модели проверяются на сервере и, где требуется, на уровне БД.
- Открытые вопросы раздела 9 не закрыты предположениями без согласования.
- Email пользователя уникален и синхронизируется из Better Auth.
- В первую очередь входят три флага согласий и их проверки при регистрации; полноценный юридический документооборот и управление версиями юридических документов не входят.
- Администратор с ролью student в обычных учебных сценариях создаёт историю как студент; предпросмотр историю не создаёт.
- Архивация правила не каскадная; предпочтение на архивном правиле сохраняется, но не отображается и не влияет на пересчёт.
- Последний администратор не может быть лишён роли admin.
- UC-36/37: `user_profile` сохраняется, необратимо обезличивается, приватный контент и все личные попытки удаляются; публичный контент и FK на профиль остаются. Фаза 1 атомарна в RL; фаза 2 идемпотентно удаляет Better Auth через pg-boss. Фактический статус не сообщается как полный успех до завершения фазы 2. Первый администратор не самоудаляется; всем остальным требуется повторная аутентификация перед UC-37.
- UC-38/39: password 8–128 символов, 8–11 требуют явного непредустановленного подтверждения риска без хранения; сброс одноразовым токеном, смена после текущего пароля, отзыв сессий.
- UC-40: объединение методов входа по проверке владения обоими, не по одному email.
- `dictation_record.is_public` и `deck.is_public` по умолчанию false; только admin меняет публичность; права проверяются в API, списках, по прямым ссылкам и при прохождении.
- Остальные критерии v8.2 (тренировки, отчёты, статистика, парсер, прогресс) сохраняются неизменными.

## 12. Формат задач для ИИ-агента

Перед реализацией каждого этапа агент должен подготовить:
- матрицу доступа visitor / student / admin / scheduler;
- соответствие Use Cases сущностям и полям действующей модели ER;
- список экранов и API-операций;
- транзакционные границы;
- серверные проверки и валидацию;
- список миграций, индексов, ограничений и фоновых задач;
- открытые вопросы;
- последовательность небольших проверяемых задач.
Каждая задача должна содержать: ID Use Case, цель, затрагиваемые сущности, права доступа, бизнес-логику, валидацию, транзакционные требования, ошибки, тесты и критерии приёмки.
Не начинать массовую реализацию всех сценариев одним большим изменением. Сначала согласовать план, открытые вопросы и границы этапа.
### Актуальные следующие шаги

1. Выполнить волну 0 функциональной декомпозиции: спайк Better Auth/Prisma и границ транзакций регистрации и двухфазного удаления (F01.1/F01.6/F01.7), фиксация версий стека в lockfile, миграционный каркас со схемами auth/public.
2. Подготовить матрицу прав, карту UC → API → сущности, миграции PostgreSQL, фоновые задачи и тесты инвариантов действующей модели ER.
3. Реализовывать небольшими проверяемыми задачами: этап A (регистрация, правила, диктанты, прогресс), затем этап B (слова, колоды, ссылки, профиль, UC-36–40).
4. Для UC-36/37 не удалять общие материалы и не переназначать авторство; приватные материалы удалять в порядке FK.


## 13. Права доступа к приватным материалам и настройкам

- `dictation_record.is_public` boolean NOT NULL DEFAULT false. Студент создаёт и редактирует только собственные приватные диктанты; администратор имеет обычные полномочия для всех. Только admin может устанавливать или снимать `is_public` как у диктанта, так и у колоды. В БД default `deck.is_public=false`, UI администратора может предлагать true.
- Публичное прохождение требует `is_public=true`, `is_active=true`, действующую версию и отсутствие soft-delete; прямой API/ID не должен обходить ограничения. Собственный приватный диктант доступен автору, чужой — только admin.
- `service_setting.email_registration_enabled` default true; только admin меняет настройку. Существующие пользователи входят и восстанавливают/меняют пароль независимо от её состояния.
- Удаление пользователя не меняет содержимого и владельцев публичных материалов. Право администрирования определяется ролью admin, специальная передача управления не нужна.
