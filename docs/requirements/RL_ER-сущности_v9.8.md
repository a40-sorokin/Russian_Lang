## Общие соглашения

Типы, явно указанные в таблицах (в частности, BIGINT идентификаторов `rule`/`dictation_done`/`secret_link.resource_id`, UUID, timestamptz и CHECK), **обязательны**. Выбор оставшихся технических SQL-типов делегируется агенту только при соблюдении заданной семантики, индексов и миграционных тестов; самостоятельно менять утверждённые типы и API-контракты нельзя.

Имена атрибутов — всегда в нижнем регистре (snake_case). В таблицах документ использует нижний регистр.

Поле sort_order (общее для всех сущностей, где оно есть) — целое число для управления порядком вывода в списках UI. Сортировка всегда по возрастанию. Уникальность не требуется; при равенстве порядок стабилизируется по id (или code). Смысл: администратор может вручную менять порядок отображения.

Внешние ключи на user_profile (поля created_by, updated_by, deleted_by, user_id) — по умолчанию RESTRICT на удаление (исключения — см. раздел «Каскадное поведение при удалении»).

Исключения: dictation_done и placeholder_done — append-only (только created_at), без updated_*/deleted_*; см. соответствующие разделы.

**Конвенция полей аудита и сортировки.** Во всех сущностях, имеющих audit-поля, они перечисляются в едином порядке: created_by, created_at, updated_by, updated_at, deleted_by, deleted_at. Поля, не нужные сущности, опускаются: append-only таблицы (placeholder_done, word_done) хранят только created_at (и при необходимости created_by); JOIN-таблицы (role_user_profile, dictation_version_rule, deck_word) — только created_at/created_by. deleted_at/deleted_by — soft delete: запись исключается из активного множества, но физически остаётся. Поле сортировки во всех сущностях называется sort_order (например, rule.sort_order, deck_word.sort_order).

## Пользователь, "user_profile"

Человек, зашедший на страницы веб-сервиса. Атрибуты, минимально необходимые для авторизации, + никнейм для отображения на сайте.

| Атрибут | Пояснения |
|---|---|
| id | BIGINT PK, идентификатор профиля; сохраняется после обезличивания, FK других сущностей того же типа |
| nickname | TEXT NULLABLE; для действующего профиля обязательно, для обезличенного — NULL. Ввод приводится к Unicode NFC. Разрешены 3–32 буквы/цифры/`_`/`-`; первый и последний символ — буква либо цифра, хотя бы одна буква; только кириллица (включая Ё/ё), латиница и цифры. Источник SQL-проверки и индекса уникальности — `ck_user_profile_nickname` и `uq_user_profile_nickname_ci` ниже; не использовать диапазоны `[а-яА-Я]` без фиксированной collation. |
| auth_user_id | FK на Better Auth `auth.user(id)`, UNIQUE; для действующего профиля NOT NULL, для обезличенного — NULL. При удалении Better Auth user ссылка уже должна быть обнулена в транзакции RL; `ON DELETE SET NULL` служит страховкой и не заменяет фазу 1. |
| email | Email действующего пользователя, синхронизируется из Better Auth; NOT NULL при `is_anonymized=false`, NULL при `is_anonymized=true`. UNIQUE для ненулевых значений. Прежний email допускается при повторной регистрации нового профиля. |
| is_anonymized | boolean NOT NULL DEFAULT false. Необратимый признак обезличивания; переход true → false запрещён БД/серверной логикой. |
| anonymized_at | timestamptz NULL для действующего профиля; NOT NULL после обезличивания. |
| is_founder_admin | boolean NOT NULL DEFAULT false. Неизменяемый признак первого администратора, устанавливается только при первоначальном бутстрапе. Не более одного true (частичный уникальный индекс); удаление первого администратора запрещено при любых инициаторах и через любые штатные пути, включая фоновые процессы; снятие роли admin также запрещено. |
| approval_personal_data | boolean NOT NULL DEFAULT false. Явное согласие на обработку персональных данных; при регистрации обязательно отдельное активное согласие. Отзыв регулируется отдельным правовым процессом, не подменяется молчаливым удалением. |
| approval_marketing_mail | boolean NOT NULL DEFAULT false. Необязательное согласие на маркетинговые сообщения; флажок по умолчанию снят. |
| approval_3th_part | boolean NOT NULL DEFAULT false. Необязательное согласие на передачу данных третьим лицам; флажок по умолчанию снят. Имя поля исторически согласовано, не переименовывать самовольно. |
| last_signin_at | timestamptz NULL; время последнего успешного создания новой сессии Better Auth, **не** время регистрации. Дата регистрации — `created_at`. При обезличивании NULL. |
| last_learn_at | Дата последнего прохождения диктанта (запись dictation_done) или слова (запись word_done). Обновляется при создании соответствующей записи выполнения. |
| is_locked | Флаг блокировки пользователя (бан). true — пользователь заблокирован и не может входить и выполнять действия. |
| locked_at | Дата/время, с которого пользователь заблокирован. |
| locked_by | Пользователь, наложивший блокировку. FK на user_profile. |
| restored_at | Дата/время снятия блокировки. |
| lock_reason | Текстовая причина блокировки. |
| created_at | Дата/время создания записи. |
| updated_by | Id пользователя, изменившего профиль. Обычно сам пользователь. FK на user_profile. |
| updated_at | Дата/время обновления записи. |
| deleted_by | Пользователь, отметивший запись для удаления. FK на user_profile. |
| deleted_at | `timestamptz NULL`; дата завершения **фазы 1 обезличивания** по UC-36/37. Для действующего профиля строго `NULL`, для обезличенного — `NOT NULL` и больше не изменяется. Отдельного soft delete действующего `user_profile` нет: состояние определяется `is_anonymized` и `ck_user_profile_state`. Заполнение `deleted_at` **не означает** успешного завершения фазы 2 (удаления Better Auth identity); статус фазы 2 хранится в `user_deletion_jobs`. |

**Блокировка пользователя.** Единственный нормативный признак бана — `user_profile.is_locked` (не использовать независимый Better Auth `banUser` как второй источник истины). Вход и защищённые endpoint обязаны проверять его; при блокировке все сессии Better Auth отзываются, сбой требует надёжного повторения. Блокировка (бан) описывается полями is_locked, locked_at, locked_by, lock_reason: при бане is_locked = true, заполняются locked_at, locked_by, lock_reason; restored_at остаётся NULL. При снятии бана is_locked = false, заполняется restored_at. История блокировок (кто, когда, почему, снятие) при необходимости ведётся в admin_audit_log (action_type = 'lock_user' / 'unlock_user').

**Активность пользователя.** `last_signin_at` обновляется исключительно при успешном входе (создании новой сессии), last_learn_at — при появлении записи dictation_done или word_done. Каждый успешный вход (создание новой сессии) дополнительно фиксируется append-only записью в журнале user_signin_log — источнике показателя «авторизации» статистики UC-32 (last_signin_at хранит только последний вход и для подсчёта входов за период не пригоден).

**Обезличивание:** сохранённый `id` обеспечивает ссылочную целостность. При `is_anonymized=true` поля `nickname`, `email`, `auth_user_id`, `last_signin_at`, `last_learn_at`, `locked_at`, `locked_by`, `restored_at`, `lock_reason`, `updated_by`, `deleted_by` очищаются до NULL; `is_locked=false`; все три поля `approval_*` становятся false; `anonymized_at` и `deleted_at` заполнены. Составные CHECK `ck_user_profile_state` и `ck_user_profile_founder_state` приведены ниже; использовать их дословно и проверить на реальных миграциях. Повторная регистрация с тем же email создаёт новый `id`; связь со старым профилем не восстанавливается. `is_founder_admin` не может сбрасываться автоматически. Первого администратора запрещено удалять, обезличивать или лишать роли admin при любых обстоятельствах, в том числе через UC-36. Юридический риск отказа первому администратору в самоудалении принят как бизнес-решение и требует оценки до запуска.

### Обязательные ограничения `user_profile` (PostgreSQL 16)

Нормативные выражения CHECK для новых миграций (действующий профиль создаётся только полностью, после OAuth/email onboarding):

```sql
ALTER TABLE public.user_profile
  ADD CONSTRAINT ck_user_profile_state CHECK (
    (NOT is_anonymized
      AND anonymized_at IS NULL AND deleted_at IS NULL
      AND nickname IS NOT NULL AND email IS NOT NULL AND auth_user_id IS NOT NULL)
    OR
    (is_anonymized
      AND anonymized_at IS NOT NULL AND deleted_at IS NOT NULL
      AND nickname IS NULL AND email IS NULL AND auth_user_id IS NULL
      AND last_signin_at IS NULL AND last_learn_at IS NULL
      AND locked_at IS NULL AND locked_by IS NULL
      AND restored_at IS NULL AND lock_reason IS NULL
      AND updated_by IS NULL AND deleted_by IS NULL
      AND is_locked = false
      AND approval_personal_data = false
      AND approval_marketing_mail = false
      AND approval_3th_part = false)
  );

ALTER TABLE public.user_profile
  ADD CONSTRAINT ck_user_profile_founder_state CHECK (
    NOT is_founder_admin OR (NOT is_anonymized AND NOT is_locked)

    )

-- Проверить наличие детерминированной ICU collation und-x-icu до миграции.
CREATE UNIQUE INDEX uq_user_profile_nickname_ci
  ON public.user_profile (lower(nickname COLLATE "und-x-icu"))

```

Дополнительно для **действующего профиля** обязательны ограничение nickname на длину/алфавит из таблицы атрибутов, `UNIQUE lower(nickname COLLATE "und-x-icu")`, уникальность email/`auth_user_id`; для **обезличенного** nickname NULL. Поле `approval_personal_data` не следует требовать `true` постоянно DB-CHECK: согласие обязательно на регистрации, а его поздний отзыв требует отдельной юридически корректной процедуры. Запрет изменения признака founder, блокировки founder, удаления его профиля и снятия его роли обеспечивается отдельными триггерами; один CHECK для этого недостаточен.

Перед применением проверять, что поля согласий NOT NULL, `is_anonymized`/`is_locked` NOT NULL, служебные даты nullable и миграция использует имена столбцов ровно как здесь. Любой переход в анонимное состояние выполняется **одним UPDATE** внутри RL-транзакции после очистки зависимостей: нельзя создавать промежуточные строки, нарушающие CHECK. После миграций проверить положительные и отрицательные фикстуры на настоящем PostgreSQL 16.

**Нормализация nickname и collation:** сервер приводит введённый nickname к Unicode NFC, проверяет 3–32 **Unicode-символа** и тот же набор букв/цифр. SQL-проверка алфавита использует явное перечисление русских букв (включая Ё/ё) и `COLLATE "C"` для предсказуемости без диапазонов `[а-яА-Я]`; `lower()` для уникальности использует отдельную детерминированную ICU-коллацию `und-x-icu` (если доступна) вместо изменения locale кластера. Проверки CI обязаны включать Ё/ё, кириллические пары регистра, NFC, латиницу, цифры, запрещённые знаки и дубли, различающиеся регистром. Проверить фактическое поведение на целевом Docker PostgreSQL 16 до миграции production.

Имя user_profile выбрано, чтобы не конфликтовать с таблицей user для Better Auth. На первой очереди проекта аватарки не поддерживаются.

## Роль, "role"

Кардинальность профиля к ролям — `0..N`: действующий профиль обязан иметь минимум одну назначенную роль, обезличенный профиль не имеет ролей. При UC-22 нельзя снять последнюю роль с действующего профиля; запрет проверяется сервером в транзакции изменения ролей. Простым CHECK одной таблицы нельзя выразить ограничение на наличие строк в другой таблице.

«Студент», code = 'student' — человек, желающий проработать правила русского языка. Назначается автоматически при регистрации пользователя (в транзакции создания user_profile создаётся запись в role_user_profile). Эта роль назначается на уровне приложения в flow регистрации; триггер БД опционален как страховка.

«Администратор», code = 'admin' — пользователь с максимальными полномочиями. Первый администратор назначается автоматически при регистрации по совпадению подтверждённого email с серверной настройкой admin_email (см. инвариант «Бутстрап первого администратора» и UC-02).

Неавторизованный пользователь «Посетитель» (visitor) не имеет ролей — это состояние «не аутентифицирован», а не роль в БД.

| code | Код роли. Уникальный, immutable (не меняется после создания). CHECK (code ~ '^[a-z][a-z0-9_]*$'), длина ≤ 32. Триггер BEFORE UPDATE, запрещающий менять code. |
| title | Название роли |
| description | Описание роли |
| sort_order | Порядок сортировки ролей при выводе в глобальных списках |
| created_by | BIGINT NULL, FK на user_profile.id; для seed-ролей `student`, `admin` — NULL, поскольку пользователей ещё нет. Для создаваемых позже записей — id действующего администратора. |
| created_at | Дата/время создания записи |
| updated_by | BIGINT NULL; для seed-ролей NULL, после изменения указывается администратор |

### Критерии приёмки

При регистрации пользователя в одной транзакции создаются user_profile и запись role_user_profile с role_id = student (code = "student"); только если founder ещё не существует и подтверждённый email совпадает с `admin_email`, дополнительно создаётся роль admin и `is_founder_admin=true` (OAuth — сразу, Email/Password — после подтверждения email).

UNIQUE (user_profile_id, role_id) не допускает дублей одной роли у пользователя.

visitor — не роль в БД: у неавторизованного пользователя нет записей в role_user_profile.

role.code неизменяем после создания (триггер BEFORE UPDATE запрещает изменение code).

Заблокированный пользователь (is_locked = true) не может входить и выполнять действия; при бане заполняются locked_at, locked_by, lock_reason, при снятии — restored_at (is_locked → false).

last_learn_at обновляется при создании `dictation_done` или `word_done`; `last_signin_at` — при успешном создании новой сессии (UC-03), но не при первоначальном создании профиля без входа.

## Правило, "rule"

Правило русского языка. Например, «Написание 'не' с глаголами».

Правила объединены в дерево. Например, правило «Написание 'не'» имеет дочерние правила «Написание 'не' с глаголами», «Написание 'не' с краткими прилагательными», «Написание 'не' с наречиями» и т.п.

Корневое правило — всегда «Все правила». Оно недоступно для редактирования (можно только создавать дочерние правила) и не может быть удалено в приложении даже администратором.

В дереве правил ровно один корень. Корень — это правило с parent_id IS NULL. Инвариант обеспечивается частичным уникальным индексом:

```sql
CREATE UNIQUE INDEX uq_rule_single_root ON rule ((1)) WHERE parent_id IS NULL;
```

**Циклы (P0).** При создании и изменении `rule.parent_id` сервер запрещает назначение правилу самого себя или любого его потомка. Внутри одной PostgreSQL-транзакции перед проверкой и записью брать `SELECT id FROM rule WHERE code='all_rules' FOR UPDATE`: эта корневая строка служит общим mutex для всех штатных мутаций иерархии; затем выполнить рекурсивную проверку предков нового родителя, и только при отсутствии цикла изменять `parent_id`. UI-проверка вспомогательная, серверная обязательна. Отдельный DB-триггер предотвращения циклов в первой очереди не вводится: прямые произвольные SQL-изменения дерева считаются внешним риском и запрещаются эксплуатационными правами. Чтение дерева, агрегация и UC-34 используют защиту от циклов (множество уже посещённых id/ограничение итераций) и при повреждении данных сообщают о нарушении целостности, не зависают. Дополнительное ограничение глубины дерева не вводится.

| updated_at | Дата/время обновления записи |
| deleted_by |  |
| deleted_at |  |

**Инвариант авторства `dictation_record`:** для любого диктанта `created_by IS NOT NULL` и существует `user_profile.id`; операции UC-24/25 передают текущего проверенного пользователя при INSERT. Для запрета смены владельца применять одновременно серверную проверку прав и триггер `BEFORE UPDATE` PostgreSQL. FK `ON DELETE RESTRICT` защищает ссылку на tombstone автора; обезличивание не удаляет профиль. Администратор вправе редактировать/публиковать диктант, но не изменять `created_by`.

Нормативный DDL триггера (в миграции Prisma через SQL; имя функции и триггера фиксированы):

```sql
CREATE OR REPLACE FUNCTION public.guard_dictation_record_created_by()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF NEW.created_by IS DISTINCT FROM OLD.created_by THEN
    RAISE EXCEPTION 'dictation_record.created_by is immutable'
      USING ERRCODE = '23514';
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_dictation_record_created_by_immutable
BEFORE UPDATE ON public.dictation_record
FOR EACH ROW
EXECUTE FUNCTION public.guard_dictation_record_created_by();
```

Триггер не отменяет `NOT NULL`, FK и проверки прав в API. Прямая смена `created_by` рабочей ролью БД должна завершаться ошибкой `23514`; системные привилегии на отключение триггера рабочей роли не предоставляются. В старой существующей БД миграцию `NOT NULL` применять только после проверки и устранения NULL без выдумывания автора; в первой очереди новые диктанты уже создаются с обязательным автором.

## Версия диктанта, "dictation_version"

Диктант должен иметь версии, одна из которых является текущей. Текст диктанта может со временем редактироваться. В истории пользователя пройденные диктанты должны быть видны в той версии, в которой были пройдены.

При создании «записи диктанта» одновременно создаётся первая «версия диктанта». Со временем у одной записи диктанта может быть много версий. В один момент времени только одна версия может быть активной.

| Атрибут | Пояснения |
|---|---|
| id | PK |
| dictation_record_id | FK на dictation_record |
| version_number | Номер версии. Присваивается автоматически: prev.version_number + 1, где prev — открытая версия (valid_to IS NULL), взятая FOR UPDATE. Для первой версии version_number = 1. На UI список версий сортируется по убыванию version_number. Уникальный индекс (dictation_record_id, version_number) — страховка от гонок. |
| text | Текст, который увидит пользователь. Подстановки определяют места в тексте, где пользователю нужно заполнить пробелы или сделать выбор. Размер нормализованного текста ≤ 30 720 байт (30 КиБ) в UTF-8. Нормализация: CRLF/CR → LF, затем Unicode NFC. Учитываются все символы разметки подстановок. Сервер проверяет `Buffer.byteLength(normalized, "utf8") <= 30720` после нормализации; клиентская проверка вспомогательная. Ограничения проверяются на клиенте и на сервере. |
| valid_from, valid_to | Период активности версии. Интервал полуоткрытый [valid_from, valid_to). valid_to = NULL — «открытый конец». Активная версия: valid_from <= now() AND (valid_to IS NULL OR now() < valid_to). Подробности — в разделе «Период действия версии диктанта». |
| created_by | Автор (пользователь, создавший версию) |
| created_at |  |
| updated_by |  |
| updated_at |  |

Версия диктанта после сохранения сразу становится активной: valid_from = now(), valid_to = NULL. Если valid_from в будущем — публикация откладывается до указанной даты.

### Формальная грамматика парсера версии диктанта

Текст версии диктанта (поле text сущности dictation_version) разбирается парсером в последовательность сегментов: текстовых фрагментов и подстановок. Подстановка может ссылаться на правило (атрибут id) либо на word_placeholder (атрибут wp) — последний используется для словарных слов, не подчиняющихся правилам.

Грамматика ниже расширяет грамматику подстановки (раздел «Подстановка») правилом version_body (последовательность сегментов) и ссылкой ref_part = rule_part | wp_part. Правила для alt, base, letter и проч. совпадают с грамматикой подстановки.

```text
version_body  = { segment } ;
segment       = text_segment | placeholder ;
text_segment  = char { char } ;
char          = ? любой символ, кроме "[" , "]" , "{" , "}" ? ;
placeholder   = "[" ws ref_part? ws "{" ws alt ( ws "/" ws alt )* ws "}" "+"? ws key_part? ws "]" ;
ref_part      = rule_part | wp_part ;
rule_part     = "id" ws ":" ws integer ;
wp_part       = "wp" ws ":" ws integer ;
key_part      = "key" ws ":" ws integer ;
alt           = base { base } ;
base          = letter | space | nothing | comma | hyphen | semicolon | colon ;
letter        = "а".."я" | "А".."Я" | "ё" | "Ё" ;
space         = "_" ;
nothing       = "#" ;
comma         = "," ;
hyphen        = "-" ;
semicolon     = ";" ;
colon         = ":" ;
integer       = nonzero_digit { digit } ;
nonzero_digit = "1".."9" ;
digit         = "0".."9" ;
ws            = { " " } ;
```

Атрибут `id:<integer>` допустим только для активного правила с `rule.use_in_placeholder = true` (проверяется при публикации версии диктанта; при создании/редактировании также). Запрещено менять `use_in_placeholder` с true на false, пока существует хотя бы одна версия диктанта с `id:<rule.id>`, доступная для прохождения сейчас либо запланированная к публикации, **или** версия с такими ссылками, по которой уже есть `dictation_done` (история). Наличие `dictation_done` не является обязательным для запрета: опубликованная активная версия без попыток тоже блокирует переключение. Для черновиков и снятых с публикации версий без выполнений ссылки необходимо исправить до повторной публикации. Исторические записи не переписываются; отключение правила с историческими ссылками отклоняется, пока такие ссылки сохраняются. Проверку выполняет сервер атомарно с изменением флага, учитывая содержимое текста версии и таблицу `dictation_version_rule` как производный индекс. Атрибут wp:<integer> ссылается на word_placeholder.id (словарная подстановка); id:<integer> — на rule.id. В пределах одной версии пары (id правила, key) и (wp, key) уникальны. Символы `[`, `]`, `{`, `}` вне подстановок в тексте недопустимы; `/` разрешён в обычном тексте и разделяет альтернативы только внутри подстановки. `+` задаёт регистрозависимость. Для символов, совпадающих с синтаксисом нотации, экранирование в первой очереди не поддерживается.

## Подстановка, "placeholder"

Место в тексте версии диктанта, где пользователь должен подставить пропущенную букву (или несколько), знак препинания — или оставить пустым, если по правилам русского языка туда ничего не ставится.

Пример: «А много ль к_рова даёт молока?» — пропущена «о» в слове «корова». Заполнение пропущенного места — «решение» подстановки.

На сервере подстановка описывается в текстовой нотации и хранится только в `dictation_version.text`. Самостоятельная таблица `placeholder` в БД **не создаётся**; таблица `placeholder_done` — это история результатов, а не справочник подстановок.

### Синтаксис и семантика

[id:123 {о/а}] — правило №123, альтернативы для выбора. Правильный ответ всегда первый. Пример: «к[id:123 {о/а}]рова».

[id:123 {о}] — единственная альтернатива; пользователь не видит других вариантов.

_ — пробел; # — «ничего» (слитное написание). Это разные сущности.

Быть[id:24 {,/#}]или не[id:26 {_/#}]быть» — во фразе «Быть или не быть»: нужна ли запятая перед «или», раздельно ли пишется «не быть».

+ в конце списка альтернатив ({К/к}+) — важен регистр. Признак распространяется на все альтернативы подстановки.

key ([id:123 {о} key:2]) — необязательный атрибут; используется, когда у одного правила несколько подстановок. Сочетание (id правила, key) уникально в пределах одной версии.

Пробелы внутри [] незначащие — при парсинге удаляются.

В тексте диктанта вне подстановок запрещены [, ], {, }; символ `/` автоматически удаляется с уведомлением до валидации. Внутри подстановки `/` разделяет альтернативы. Нормализация выполняется единым лексическим сканером, который не меняет содержимое распознанных подстановок; при неразобранной/незакрытой подстановке выдаётся ошибка вместо угадывания границ.

Лимиты: подстановок в версии ≤ 100; альтернатив в подстановке ≤ 5; символов в альтернативе ≤ 5.

При показе текста в UI порядок альтернатив для пользователя — случайный.

В первой очереди версионирование нотации не предусматривается.

### Формальная грамматика

**Единственный нормативный источник грамматики** — раздел «Формальная грамматика парсера версии диктанта» выше. `placeholder` в нём поддерживает `id`, `wp` либо отсутствие ссылки; отдельная, отличающаяся грамматика здесь не дублируется. Для `word_placeholder.placeholder_text` допустима только ссылка `wp:<id>`; при создании строки до получения ID допускается серверная сборка канонического текста после INSERT. Все примеры и валидаторы используют эту грамматику.

При ошибке в определении подстановки пользователь должен получить детальное сообщение с возможными причинами и подсказками.

### Критерии приёмки

Текст версии парсится в список подстановок согласно формальной грамматике; пробелы внутри [] незначащие и удаляются при парсинге.

Правильный ответ — первая альтернатива в фигурных скобках.

key по умолчанию = 1; пары (id правила, key) уникальны в пределах версии.

Символы [, ], {, } вне подстановок — ошибка валидации. Символ `/` вне подстановок автоматически удаляется до валидации; редактор и API сообщают количество удалённых символов. Внутри корректной подстановки `/` сохраняется.

Лимиты: подстановок в версии ≤ 100, альтернатив в подстановке ≤ 5, символов в альтернативе ≤ 5.

+ после } → сравнение ответа case-sensitive; без + — case-insensitive через lower().

При ошибке парсинга — детальное сообщение с индексом подстановки и причиной (см. таблицу «Проверки при публикации»).

Один студент может пройти много диктантов; одну и ту же версию — несколько раз.

| Атрибут | Пояснения |
|---|---|
| id | BIGINT PK |
| user_id | Пользователь |
| dictation_version_id | Версия диктанта |
| score_ok | Кол-во верно решённых подстановок, включая подстановки без указания правила (id в нотации) |
| score_fail | Кол-во ошибок, включая подстановки без указания правила |
| created_at | Дата/время выполнения версии диктанта |
| submission_request_id | UUID NOT NULL для сохранённого авторизованного прохождения; клиент генерирует новый UUID на новое прохождение, а при retry сохраняет прежний |
| submission_payload_hash | CHAR(64) NOT NULL, lowercase hex SHA-256 канонически сериализованного содержимого ответов; повтор с тем же UUID и другим hash → 409 |

**Ограничение:** `UNIQUE (user_id, submission_request_id)`. Сервер фиксирует результат, дочерние ответы и обновление прогресса в одной транзакции. Для канонизации: JSON-массив ответов сортируется по стабильному идентификатору подстановки (и позиции при равенстве); в каждом объекте используются строго фиксированные ключи `placeholder_id`, `answer` в указанном порядке; строки NFC, переносы LF; кодирование UTF-8; без незначащих пробелов. Версия канонизации — `v1`, включается в строку перед хешированием. Дубликат того же UUID и hash возвращает ранее сохранённый результат без побочных эффектов. Анонимные ответы не сохраняются. При миграции существующей БД запрещено подменять неизвестный исторический payload выдуманным hash.

Так как score_ok/score_fail учитывают подстановки без правила, а placeholder_done — только подстановки с правилами, эти величины не равны. dictation_done хранит итоги прохождения; placeholder_done используется для расчёта прогресса правил.

dictation_done — append-only при штатном обучении: запись создаётся при выполнении версии диктанта и далее не редактируется и не удаляется, **кроме** санкционированного уничтожения личной истории по UC-36/37 и приватных диктантов владельца согласно специальной политике удаления. Поля updated_*/deleted_* не предусмотрены (историческая неизменяемая запись для аудита).

## Выполненные подстановки, "placeholder_done"

После выполнения версии диктанта фиксируются все ответы пользователя по подстановкам, у которых указано правило (id в нотации).

Подстановки без id правила не попадают в placeholder_done — но попадают в score_ok/score_fail таблицы dictation_done.

На основании placeholder_done и word_done пересчитывается прогресс правил (см. алгоритм «Обновление рейтинга правил»): placeholder_done учитывает выполнения подстановок-правил в диктантах, word_done — выполнения подстановок слов, привязанных к правилу через word_placeholder.rule_id. Рекомендации для следующих активностей — не реализуются в 1-й очереди.

| Атрибут | Пояснения |
|---|---|
| id | PK |
| dictation_done_id | Id пройденного диктанта |
| rule_id | Id правила из подстановки. NOT NULL. |
| placeholder_key | Атрибут key из подстановки. 1, если key не указан. Целое число. |
| task_snapshot | Неизменяемый снимок подстановки правила на момент выполнения: предъявленный фрагмент задания, варианты ответов, а также отображавшиеся описание и пример правила (`rule.description`, `rule.example`), если они показывались пользователю. Нужен для стабильности исторического отчёта после редактирования правила или текста диктанта. NOT NULL для новых попыток; для мигрированных старых данных допускается NULL с явной пометкой «детали задания недоступны». |
| correct_option | Правильный ответ. Не может быть изменено. Особые случаи: _ → " " (пробел), # → "" (пустая строка), буквы/,/-/;/: — как есть. Учесть при разработке UI — варианты должны быть визуально отличимы. |
| correct_case_sensitive | true, если регистр важен для правильного ответа (опция + в нотации) |
| user_option | Решение, выбранное пользователем |
| is_correct | Вычисляется по формуле: correct_case_sensitive ? (user_option === correct_option) : (lower(user_option) === lower(correct_option)). Хранится для производительности и аудита. |

UNIQUE (dictation_done_id, rule_id, placeholder_key).

Поле created_at не требуется — время выполнения берётся из dictation_done.created_at.

Для исторического отчёта при `task_snapshot IS NULL` показываются только сохранённые `correct_option` и `user_option`, без реконструкции старого контекста из текущих `rule` или `dictation_version`, с пометкой «детали задания недоступны».

placeholder_done — append-only: записи создаются пакетом при выполнении версии диктанта и далее не редактируются и не удаляются. Поля updated_*/deleted_* не предусмотрены.

## Прогресс правила, "rule_progress"

Прогресс правила подсчитывается для каждого пользователя отдельно.

У правила есть атрибуты score_good_default и score_excellent_default (см. rule). В подстановке Id правила может отсутствовать — такая подстановка не участвует в прогрессе.

Собственный прогресс рассчитывается только для правил с `use_in_placeholder = true`. Для `word_placeholder.rule_id` также допустимы только правила с `use_in_placeholder = true` при создании или редактировании связи; существующие опубликованные и исторические ссылки проверяются перед выключением флага. Для `use_in_placeholder = false` собственный статус не рассчитывается и строка `rule_progress` не создаётся; если флаг изменён с true на false, существующая строка удаляется после проверки исторических ссылок. Итоговый статус такого правила определяется только детьми.

Прогресс правила учитывает два источника выполнений:

- placeholder_done — выполнения подстановок-правил в диктантах (placeholder_done.rule_id → правило).
- word_done — выполнения подстановок слов, привязанных к правилу через word_placeholder.rule_id; учитываются только word_placeholder с rule_id IS NOT NULL и is_exception = false (исключения из правила и словарные слова без правила в прогресс правил не входят).

Прогресс пересчитывается после выполнения диктанта, после каждого ответа в тренировке слов (решение от 10.11.2026), а также ежесуточно по расписанию (учитывает «забывание» давних попыток).

Правила с is_archived = true не пересчитываются. Существующая запись rule_progress для архивного правила замораживается (значения status, current_score, placeholder_ok, placeholder_bad, word_ok, word_bad, calculated_at не изменяются). placeholder_done и word_done для архивных правил продолжают создаваться (для истории), но на rule_progress не влияют. При снятии is_archived правило снова участвует в пересчёте. При этом архивные правила полностью исключаются из расчёта статуса любых других правил: при агрегации родительского правила архивные дочерние правила не входят в множество C — не учитываются ни своими выполнениями, ни замороженным статусом. Если все дочерние правила родителя архивны, родитель агрегируется как лист (по собственным выполнениям) только при `use_in_placeholder = true`; при `use_in_placeholder = false` итоговый статус Grey (активных детей нет).

У правила могут быть следующие статусы:

Не начато (Grey). За окно 4 месяца нет ни одного выполнения по правилу — ни placeholder_done, ни word_done.

Плохо освоено (Red). Выполнения есть, но current_score < score_good_default (допущено неприемлемо много ошибок).

Хорошо (Yellow). score_good_default <= current_score < score_excellent_default.

Отлично (Green). current_score >= score_excellent_default.

Цель пользователя-студента: добиться прогресса «Отлично» или хотя бы «Хорошо» для как можно большего количества правил.

| Атрибут | Пояснения |
|---|---|
| id | PK (суррогатный). UNIQUE (user_id, rule_id) сохраняется как ограничение уникальности (см. раздел «Прогресс правила»). |
| user_id | Пользователь |
| rule_id | Id правила |
| status | Текущий статус: Grey / Red / Yellow / Green. Рассчитывается алгоритмом «Обновление рейтинга правил» (rule_score_calculation). |
| current_score | Кол-во очков за применение правила = (placeholder_ok + word_ok) − (placeholder_bad + word_bad) − 2. Без учёта очков дочерних правил (только собственные выполнения). |
| placeholder_bad | Кол-во подстановок-правил в диктантах с ошибками (placeholder_done.is_correct = false). Дочерние правила не учитываются. |
| placeholder_ok | Кол-во подстановок-правил в диктантах, выполненных верно (placeholder_done.is_correct = true). Дочерние правила не учитываются. |
| word_bad | Кол-во выполнений подстановок слов (word_done) с ошибками (is_correct = false), привязанных к правилу через word_placeholder.rule_id (is_exception = false). Дочерние правила не учитываются. |
| word_ok | Кол-во выполнений подстановок слов (word_done), выполненных верно (is_correct = true), привязанных к правилу через word_placeholder.rule_id (is_exception = false). Дочерние правила не учитываются. |
| calculated_at | Время последнего пересчёта прогресса |
| calculated_by | id пользователя, инициировавшего расчёт (админ из панели или студент после диктанта); NULL — для cron |

UNIQUE (user_id, rule_id). Поле created_at не нужно, его заменяет calculated_at. Отсутствие строки rule_progress для пары (user_id, rule_id) трактуется как **собственный** статус Grey для правил с `use_in_placeholder = true`; для `use_in_placeholder = false` собственный статус неприменим (значение по умолчанию). **Итоговый статус родителя не хранится в `rule_progress` и вычисляется при чтении дерева** снизу вверх по активным дочерним правилам; поле `rule_progress.status` всегда означает собственный статус. Поэтому родитель без строки `rule_progress` может отображаться как Yellow, Red или Green в зависимости от детей. Запись rule_progress создаётся только для `use_in_placeholder = true` алгоритмом расчёта прогресса при появлении у пользователя хотя бы одного выполнения по этому правилу за окно 4 месяца (placeholder_done или word_done) — со статусом Red/Yellow/Green. Если при пересчёте выполнений за окно не осталось, статус становится Grey и запись rule_progress удаляется. Состояние правила с точки зрения пользователя (state) хранится отдельно — в сущности user_rule_preference (см. соответствующий раздел) — и на жизненный цикл rule_progress не влияет: предпочтение сохраняется независимо от того, есть ли рассчитанный прогресс.

## Предпочтение пользователя по правилу, "user_rule_preference"

Состояние правила (state) с точки зрения пользователя — его намерение в отношении правила: учить, не учить или учить позже. Вынесено из rule_progress в отдельную сущность, так как state не зависит от рассчитанного прогресса и не влияет на него: это пользовательская настройка, а не расчётная величина. Одна запись на пару (user_id, rule_id); отсутствие (неудалённой) записи трактуется как state = InUse (значение по умолчанию).

| Атрибут | Пояснения |
|---|---|
| id | PK |
| user_id | Пользователь. FK на user_profile. |
| rule_id | Правило. FK на rule. |
| state | Состояние правила с точки зрения пользователя: InUse (по умолчанию) / Ok / Pause. Отражает намерение пользователя (учить / не учить / учить позже), не зависит от рассчитанного прогресса rule_progress и не влияет на него. См. значения ниже. |
| created_at | Дата/время создания записи. |
| created_by | Пользователь, установивший состояние. FK на user_profile. |
| updated_by | Id пользователя, изменившего запись. FK на user_profile. |
| updated_at | Дата/время обновления записи. |
| deleted_by | Пользователь, отметивший запись для удаления. FK на user_profile. |
| deleted_at | Дата/время soft delete. Запись удаляется только при каскадном удалении пользователя из user_profile или удалении правила — самостоятельное (не каскадное) удаление предпочтения не предусмотрено. |

UNIQUE (user_id, rule_id). Значение по умолчанию — InUse: если для пары (user_id, rule_id) нет (неудалённой) записи user_rule_preference, считается, что state = InUse.

### Значения state

| state | Смысл |
|---|---|
| InUse | Пользователь хочет выполнять диктанты и тренировки с этим правилом, чтобы выучить его. Значение по умолчанию. |
| Ok | Пользователь уверен, что хорошо знает правило, и ему не требуется его изучение. |
| Pause | Пользователь нуждается в изучении правила, но позже — пока изучать не требуется. |

State не заменяет прогресс и не влияет на него: алгоритм «Обновление рейтинга правил» не меняется при смене state, пересчёт не запускается, значения status, current_score и счётчиков rule_progress (placeholder_ok/bad, word_ok/bad) остаются неизменными — даже при переводе InUse → Ok рассчитанный прогресс сохраняется как есть.

Запись user_rule_preference создаётся при первой явной установке пользователем состояния (любого из трёх), в том числе на правило без рассчитанного прогресса. В отличие от прежней схемы (когда state хранился в rule_progress), предпочтение больше не привязано к жизненному циклу rule_progress: при старении прогресса (статус → Grey, удаление строки rule_progress) запись user_rule_preference не затрагивается — намерение пользователя сохраняется независимо от того, есть ли рассчитанный прогресс.

Установка состояния тиражируется на дочерние правила: при смене state правила то же значение применяется ко всем активным (не архивным) дочерним правилам рекурсивно. Если среди затрагиваемых дочерних правил есть правила с рассчитанным прогрессом (запись rule_progress со статусом Red/Yellow/Green — пользователь их уже учит), сервис уточняет у пользователя, следует ли применить к ним такое же состояние; для дочерних правил без рассчитанного прогресса (Grey / нет записи rule_progress) состояние применяется автоматически (переопределяя любое ранее установленное состояние, с созданием записи user_rule_preference при необходимости). Архивные дочерние правила пропускаются. Смена состояния дочернего правила, как и родительского, не влияет на его рассчитанный прогресс.

### Критерии приёмки

UNIQUE (user_id, rule_id) — у пользователя не более одного предпочтения на правило.

Отсутствие (неудалённой) записи user_rule_preference = state = InUse (значение по умолчанию).

Смена state не запускает пересчёт rule_progress и не изменяет status, current_score, счётчики (placeholder_ok/bad, word_ok/bad) — даже InUse → Ok оставляет рассчитанный прогресс неизменным.

Установка state на правило без рассчитанного прогресса создаёт запись user_rule_preference (rule_progress при этом не создаётся — он создаётся только алгоритмом при первом выполнении).

Установка state тиражируется рекурсивно на активные (не архивные) дочерние правила: для детей с рассчитанным прогрессом (Red/Yellow/Green) сервис уточняет у пользователя; для детей без собственного рассчитанного прогресса (Grey / нет записи) применяется автоматически (с созданием записи user_rule_preference при необходимости). Архивные дочерние правила пропускаются.

Запись user_rule_preference удаляется только каскадно — при удалении пользователя из user_profile или удалении правила; самостоятельное удаление предпочтения не предусмотрено.

## Слово, "word"

Справочник слов для запоминания. Хранит каноническую форму (в нижнем регистре) и часть речи. Слова служат основой для подстановок word_placeholder и состава колод deck.

Слово — редактируемый справочник с audit-полями (created_by/at, updated_by/at, deleted_by/at) и soft delete (deleted_at). Исправление ошибки в слове: либо обновление записи (updated_at/updated_by) с пересозданием зависимых word_placeholder, либо soft-delete (deleted_at/deleted_by) старой записи и создание новой.

| Атрибут | Пояснения |
|---|---|
| id | PK (суррогатный, bigint). |
| data | Слово в нижнем регистре. text, NOT NULL. CHECK (data = lower(data)) — регистр приводится при записи. |
| spart | Часть речи: существительное, глагол, прилагательное, наречие и т.п. text, NOT NULL. Допустимые значения контролируются приложением (или CHECK-перечислением). |
| created_by | FK на user_profile.id, ON DELETE RESTRICT. Создавший пользователь. |
| created_at | timestamp, NOT NULL. |
| updated_by | FK на user_profile.id, ON DELETE RESTRICT. |
| updated_at | timestamp. |
| deleted_by | FK на user_profile.id, ON DELETE RESTRICT. |
| deleted_at | timestamp (soft delete). |

UNIQUE (data, spart) — одно написание может быть разными частями речи (например, «косой» — прилагательное и существительное), но пара уникальна.

Удаление слова (физическое) допускается только при отсутствии его выполнений: ни одно word_placeholder этого слова не должно иметь записей в word_done. На уровне БД удалению препятствуют FK word_placeholder.word_id → word.id (RESTRICT) и FK word_done.word_placeholder_id → word_placeholder.id (RESTRICT); бизнес-правило дублирует эту защиту на уровне приложения. Soft delete (deleted_at) доступен и при наличии выполнений — запись исключается из активного множества, но остаётся для истории.

## Подстановка слова, "word_placeholder"

Подстановки для слов — альтернативы трудных случаев написания. Аналогичны подстановкам правил (placeholder), но привязаны к слову, а не к правилу. Используются в диктантах и в тренировках колод так же, как правила.

У одного слова может быть несколько трудных случаев (несколько строк word_placeholder), хотя чаще всего он один.

Формат placeholder_text аналогичен формату подстановки placeholder, но вместо атрибута id:<id правила> используется атрибут wp:<id из word_placeholder>.

rule_id nullable: null — для словарных слов (не объясняемых правилом); не null — если случай правописания объясняется правилом.

score_good_default и score_excellent_default — пороговые значения «хорошо» и «отлично» для словарных слов (rule_id IS NULL), не подчиняющихся правилам; при наличии rule_id пороги наследуются от rule (rule.score_good_default, rule.score_excellent_default), а собственные поля должны быть NULL. is_exception — флаг того, что случай правописания является исключением из правила rule_id (не подчиняется ему, а наоборот — исключение); устанавливается только при заполненном rule_id.

| Атрибут | Пояснения |
|---|---|
| id | PK (суррогатный, bigint). |
| word_id | FK на word.id, NOT NULL, ON DELETE RESTRICT. |
| placeholder_text | Постановка в формате, аналогичном placeholder, с атрибутом wp:<id из word_placeholder> вместо id:<id правила>. text, NOT NULL. |
| rule_id | FK на rule.id, NULLABLE. null — словарное слово; не null — случай объясняется правилом. ON DELETE RESTRICT. |
| score_good_default | Порог балла «хорошо» для слова. int, NULLABLE. Смысл как у rule.score_good_default. Заполняется только при rule_id IS NULL. CHECK (score_good_default BETWEEN 1 AND 1000). |
| score_excellent_default | Порог балла «отлично» для слова. int, NULLABLE. Смысл как у rule.score_excellent_default. Заполняется только при rule_id IS NULL. CHECK (score_excellent_default BETWEEN 1 AND 1000). |
| is_exception | Флаг: случай правописания — исключение из правила rule_id (не подчиняется ему, а наоборот, является исключением). bool, NOT NULL, default false. Может быть установлен в true только при заполненном rule_id. |
| created_by | FK на user_profile.id, ON DELETE RESTRICT. |
| created_at | timestamp, NOT NULL. |
| updated_by | FK на user_profile.id, ON DELETE RESTRICT. |
| updated_at | timestamp. |
| deleted_by | FK на user_profile.id, ON DELETE RESTRICT. |
| deleted_at | timestamp (soft delete). |

UNIQUE (word_id, placeholder_text) — у слова не может быть двух одинаковых постановок.

Soft delete: deleted_at IS NOT NULL исключает запись из активного множества; архивные подстановки не используются при формировании диктантов и колод (аналогично архивным правилам).

Пороговые поля score_good_default и score_excellent_default заполняются только для словарных слов (rule_id IS NULL): CHECK ((rule_id IS NULL) OR (score_good_default IS NULL AND score_excellent_default IS NULL)). При наличии rule_id пороги наследуются от rule (rule.score_good_default, rule.score_excellent_default). CHECK (score_excellent_default > score_good_default) при заполнении обоих (good < excellent). Диапазон каждого порога — от 1 до 1000, аналогично rule (выровнено в v8.2).

is_exception требует ссылки на правило: CHECK (is_exception = false OR rule_id IS NOT NULL). Флаг означает, что правописание слова — исключение из правила rule_id (не подчиняется ему); не дублирует случай rule_id IS NULL (словарное слово без правила вообще).

Удаление подстановки слова (физическое) допускается только при отсутствии выполнений: нет записей word_done с данным word_placeholder_id. На уровне БД удалению препятствует FK word_done.word_placeholder_id → word_placeholder.id (RESTRICT); бизнес-правило дублирует защиту на уровне приложения. Soft delete (deleted_at) доступен и при наличии выполнений.

is_public: публичную колоду может создать только пользователь с ролью admin; для админа флаг устанавливается в true по умолчанию. Обычный пользователь может создавать только приватные колоды.

## Слово в колоде, "deck_word"

Связь many-to-many между колодой и словом — состав колоды. Каждая строка — одно слово в одной колоде.

Поле sort_order задаёт порядок отображения состава колоды и детерминированный tie-breaker выбора слов в тренировке; не задаёт фиксированную последовательность тренировочных карточек.

JOIN-таблица: audit только на создание (created_by, created_at), без update/delete-полей. При жёстком удалении колоды (CASCADE) её состав удаляется автоматически; при удалении слова (RESTRICT) — блокируется, пока слово входит в какие-либо колоды.

| Атрибут | Пояснения |
|---|---|
| id | PK (суррогатный, bigint). |
| deck_id | FK на deck.id, NOT NULL, ON DELETE CASCADE. |
| word_id | FK на word.id, NOT NULL, ON DELETE RESTRICT. |
| sort_order | Порядок слова в списке колоды и tie-breaker в тренировке. int, nullable (null — без явного порядка). |
| created_by | FK на user_profile.id, ON DELETE RESTRICT. |
| created_at | timestamp, NOT NULL. |

UNIQUE (deck_id, word_id) — слово входит в колоду ровно один раз.

UNIQUE (deck_id, sort_order) WHERE sort_order IS NOT NULL — порядок не дублируется в пределах колоды (опционально, частичный индекс).

## Выполнение подстановки слова, "word_done"

Фиксирует выполнение подстановки word_placeholder пользователем. Аналог placeholder_done, но для слов. Append-only: записи создаются, но не изменяются и не удаляются (immutable после создания).

Создаётся как при тренировке по колоде (самостоятельной), так и при прохождении диктанта, содержащего word_placeholder. Во втором случае заполняется dictation_done_id.

Поле created_at обязательно — время попытки. В отличие от placeholder_done (который берёт время из dictation_done), word_done может создаваться вне диктанта, поэтому хранит время сам.

| Атрибут | Пояснения |
|---|---|
| id | PK (суррогатный, bigint). |
| user_id | Id пользователя, выполнившего подстановку. NOT NULL. FK на user_profile.id. |
| word_placeholder_id | Id подстановки слова (word_placeholder). NOT NULL. FK на word_placeholder.id. |
| dictation_done_id | Id пройденного диктанта. NULLABLE. FK на dictation_done.id. Заполняется, если попытка в рамках прохождения диктанта; null — самостоятельная тренировка по колоде. |
| training_session_id | Id тренировочной сессии (deck_training_session). NULLABLE. FK на deck_training_session.id, ON DELETE SET NULL. Заполняется для ответов в рамках тренировки колоды; null — для ответов из диктанта. При очистке сессии обнуляется, история ответов сохраняется. |
| answer_request_id | UUID запроса ответа (идемпотентность). NULLABLE. Для ответов из диктантов NULL. Частичный UNIQUE (training_session_id, answer_request_id) WHERE оба поля NOT NULL: повторная доставка того же запроса не создаёт вторую word_done. Технический маркер без влияния на отчёты. |
| placeholder_key | Атрибут key из подстановки (wp). 1, если key не указан. Целое число. |
| task_snapshot | Неизменяемый снимок словарной подстановки на момент выполнения: предъявленный фрагмент задания, варианты ответов и отображавшийся контекст слова и подстановки. Нужен для стабильности исторического отчёта при последующих изменениях `word` и `word_placeholder`. NOT NULL для новых попыток; для мигрированных старых данных допускается NULL с явной пометкой «детали задания недоступны». |
| correct_option | Правильный ответ. Не может быть изменено. Особые случаи: _ → " " (пробел), # → "" (пустая строка), буквы / , / - / ; / : — как есть. |
| correct_case_sensitive | true, если регистр важен для правильного ответа (опция + в нотации). |
| user_option | Решение, выбранное пользователем. |
| is_correct | Вычисляется по формуле: correct_case_sensitive ? (user_option === correct_option) : (lower(user_option) === lower(correct_option)). Хранится для производительности и аудита. |
| created_at | Время попытки. NOT NULL. (У placeholder_done берётся из dictation_done.created_at; у word_done — собственное, для поддержки тренировок вне диктанта.) |

Append-only (immutable): UPDATE и DELETE запрещены на уровне приложения (или триггером). Аналогично placeholder_done. Документированное исключение — автоматическое обнуление training_session_id через FK ON DELETE SET NULL при удалении тренировочной сессии (аналогично admin_audit_log при UC-36): это поведение FK, а не ручное редактирование; приложение не выполняет UPDATE word_done.

UNIQUE (dictation_done_id, word_placeholder_id, placeholder_key) WHERE dictation_done_id IS NOT NULL — в рамках одного прохождения диктанта подстановка слова выполняется один раз.

Для тренировочных ответов идемпотентность обеспечивается частичным уникальным индексом UNIQUE (training_session_id, answer_request_id) WHERE training_session_id IS NOT NULL AND answer_request_id IS NOT NULL (см. «Служебная тренировочная сессия»): повторная доставка того же запроса не создаёт вторую запись.

Для самостоятельных тренировок (dictation_done_id IS NULL) множество попыток не ограничено — каждая попытка отдельной строкой (для отслеживания прогресса).

Если слово выполнено в рамках прохождения диктанта (dictation_done_id IS NOT NULL), word_done.created_at заполняется значением из dictation_done.created_at — временем прохождения диктанта (так же, как placeholder_done наследует время от dictation_done). Это сохраняет единое время попытки для всех ответов в рамках одного диктанта. Для самостоятельных тренировок (dictation_done_id IS NULL) created_at — фактическое время попытки.

## Секретная ссылка, "secret_link"

Секретная ссылка, которой зарегистрированный пользователь делится с любым посетителем (в том числе неавторизованным) для предоставления доступа к своему ресурсу — выполнению диктанта (dictation_done) или прогрессу по дереву правил. Ссылка создаётся пользователем и действует до expires_at (а также пока is_active = true и запись не удалена).

| Атрибут | Пояснения |
|---|---|
| id | PK |
| token_hash | Хэш уникального токена ссылки. Токен генерируется при создании ссылки и передаётся в URL (например, /share/<token>); в БД хранится только хэш токена (по аналогии с паролем — чтобы при утечке БД токены нельзя было использовать напрямую). Доступ открывается сравнением хэша токена из URL с token_hash. UNIQUE, NOT NULL. **Алгоритм (v6.4):** `raw_token` — 32 криптостойких случайных байта, кодируемых base64url без padding (43 символа). `token_hash = SHA-256(raw_token)` (32 байта, хранение `bytea` либо 64-символьный hex), UNIQUE NOT NULL. Соль не используется: токен имеет 256 бит энтропии, а детерминированный хэш позволяет индексированный поиск. `raw_token` не сохраняется в БД, логах, аналитике и кэше. Сервер декодирует и валидирует токен, вычисляет SHA-256 и ищет запись по UNIQUE-индексу `token_hash`; проверяет срок, владельца и ресурс. Запрещены токены на основе последовательных ID и времени. |
| user_id | Владелец ссылки. FK на user_profile. |
| resource_type | Тип ресурса, на который даёт доступ ссылка: 'dictation' (на выполнение диктанта, dictation_done) / 'rule_progress_tree' (на прогресс по дереву правил). В дальнейшем возможно добавление других типов; ограничение аналогично role.code — CHECK (resource_type ~ '^[a-z][a-z0-9_]*$'), длина ≤ 32; новые значения добавляются как enum-like справочник. |
| resource_id | BIGINT NOT NULL. Для `resource_type='dictation'` — `dictation_done.id` (BIGINT PK), для `resource_type='rule_progress_tree'` — `rule.id` (BIGINT PK). Полиморфная ссылка не имеет общего FK; сервер проверяет существование, доступность и владельца ресурса. В API BIGINT передаётся десятичной строкой, чтобы исключить потерю точности JavaScript. |
| scope | Кому доступна ссылка. На первой очереди реализовано единственное значение 'all' — доступно всем (в том числе неавторизованным посетителям). Ограничение аналогично resource_type (CHECK ~ '^[a-z][a-z0-9_]*$'); зарезервировано под будущие варианты (например, доступ по списку пользователей). |
| is_active | Флаг активности ссылки. false = ссылка отозвана владельцем и не предоставляет доступ. |
| expires_at | Дата/время, до которого ссылка активна. После expires_at (а также при is_active = false или soft delete) посетитель видит заглушку: «доступ к информации ограничен». |
| created_at | Дата/время создания записи. |
| created_by | Пользователь, создавший ссылку (обычно сам владелец — user_id). FK на user_profile. |
| updated_by | Id пользователя, изменившего запись. FK на user_profile. |
| updated_at | Дата/время обновления записи. |
| deleted_by | Пользователь, отметивший запись для удаления (soft delete). FK на user_profile. |
| deleted_at | Дата/время soft delete. |
| sort_order | Порядок вывода ссылок владельца в списках UI. |

resource_type → resource_id: значение resource_id трактуется по resource_type; целостность (существование выполнения диктанта (dictation_done) / правила) проверяется на уровне приложения, так как полиморфная ссылка не имеет одного FK.

Доступ по ссылке — только на чтение: посетитель видит ресурс владельца, но не может его изменять или выполнять действия от имени владельца. Для resource_type = 'rule_progress_tree' доступ распространяется на прогресс по правилу resource_id и всем его дочерним (не архивным) правилам.

### Критерии приёмки

Ссылку создаёт только зарегистрированный пользователь (user_id — существующий user_profile).

После expires_at, при is_active = false или после soft delete доступ по ссылке закрыт — посетитель видит заглушку «доступ к информации ограничен».

scope на первой очереди принимает только значение 'all'.

resource_type ограничен CHECK (формат snake_case, ≤ 32); на первой очереди допустимы значения 'dictation' и 'rule_progress_tree'.

## Журнал входов, "user_signin_log"

Фиксирует каждый успешный вход (авторизацию) зарегистрированного пользователя — создание новой сессии Better Auth; продление действующей сессии записью не сопровождается. Нужен для показателя «авторизации» статистики UC-32: user_profile.last_signin_at хранит только последний вход и для подсчёта входов за период не пригоден. Записи создаются при входе (UC-03); неаутентифицированные посетители в журнал не попадают.

| Атрибут | Пояснения |
|---|---|
| id | PK (суррогатный) |
| user_id | Вошедший пользователь. FK на user_profile.id, NOT NULL, ON DELETE CASCADE. |
| created_at | Дата/время входа. timestamptz. |

Append-only: записи создаются и не изменяются и не удаляются приложением. Единственное исключение — каскадное удаление при безвозвратном удалении пользователя (UC-36): журнал входов удаляется вместе с пользователем (ON DELETE CASCADE, см. таблицу каскадов). Поле created_by не требуется — им является сам user_id. Журнал не содержит персональных данных, кроме ссылки на пользователя и времени входа.

### Критерии приёмки

При каждом успешном входе зарегистрированного пользователя создаётся ровно одна запись user_signin_log; заблокированному или обезличенному пользователю вход запрещён — запись не создаётся.

Повторный вход (создание новой сессии) — новая запись; продление действующей сессии записи не создаёт.

При безвозвратном удалении пользователя (UC-36) его записи журнала удаляются каскадно в той же транзакции.

## Журнал действий администраторов, "admin_audit_log"

Лог действий администраторов: пересчёт прогресса, блокировка/разблокировка пользователя, удаление пользователя, управление правилами и т. п. Таблица append-only — только created_at, без updated_*/deleted_*; записи не изменяются и не удаляются (история неизменна). Для `delete_user` и иных действий запрещено записывать в свободные поля nickname, email, raw auth_user_id и другие идентификаторы лица, которое может быть удалено; используется случайный непривязанный к личности `operation_id`.

| Атрибут | Пояснения |

| user_id | Пользователь, над которым выполнено действие (если применимо). FK на user_profile, ON DELETE SET NULL. Необходимость заполнения зависит от action_type. |
| rule_id | Правило, над которым выполнено действие (если применимо). FK на rule. Необходимость заполнения зависит от action_type. |

| key_id_2 | Ссылка на id (полиморфная) — смысл и необходимость заполнения зависят от action_type. |
| key_id_3 | Ссылка на id (полиморфная) — смысл и необходимость заполнения зависят от action_type. |
| key_id_4 | Ссылка на id (полиморфная) — смысл и необходимость заполнения зависят от action_type. |

Для `delete_user` и `self_delete_user`: `key_id_1..5 = NULL`, `value_1 = operation_id::text`, `value_2 = NULL`, `value_3 = NULL`, `user_id = NULL`; `operation_id` не является идентификатором пользователя. Поля `key_id_1..5` остаются числовыми идентификаторами объектов и не используются для UUID.

key_id_1..5 и value_1..3 — «слотовые» поля: конкретный смысл каждого (на какую сущность ссылается key_id_N, что хранит value_N) определяется action_type и описывается в спецификации каждого действия; на уровне БД это полиморфные ссылки без жёсткого FK. user_id и rule_id выделены отдельно, так как они — самые частые объекты административных действий, и на них заведены FK.

### Критерии приёмки

Таблица append-only: только created_at, без updated_*/deleted_*; записи не изменяются и не удаляются.

`admin_id` — действующий профиль с ролью admin для административных событий; **исключение**: `action_type=self_delete_user` студента допускает `admin_id=NULL` и `user_id=NULL`, `value_1` содержит только случайный `operation_id`, не PII. Для иных типов действия nullability задаётся нормами UC.

action_type ограничен CHECK (формат snake_case, ≤ 32); новые значения добавляются в справочник action_type.

Запись создаётся при каждом административном действии; user_id, rule_id, key_id_N, value_N заполняются по смыслу action_type.

CASCADE только для dictation_version_rule — это чистая ассоциативная таблица без самостоятельной ценности. При удалении версии (что в норме не происходит — только архивация) её связи с правилами удаляются автоматически.

Исключения из общих правил FK: `user_rule_preference.user_id` и `rule_id` — CASCADE, её собственная история удаляется явно в UC-36/37; `admin_audit_log.admin_id/user_id` — SET NULL **только если профиль когда-либо физически удаляют вне штатной процедуры**. При штатном обезличивании ID профиля остаётся, поэтому FK аудита не обнуляются; свободные поля аудита не должны содержать PII. `rule_progress.calculated_by` — SET NULL, `word_done.training_session_id` — SET NULL, `deck_training_session.user_id` и `user_signin_log.user_id` — CASCADE; явная очистка в UC-36/37 выполняется до обезличивания. Все остальные отношения и режимы ON DELETE перечислены в таблице выше.

**Штатное удаление:** физическое удаление `user_profile` запрещено; UC-36/UC-37 необратимо обезличивают его, сохраняя ID и FK публичного контента. В одной транзакции удаляются `dictation_done`, `placeholder_done`, `word_done` (включая ответы на удалённые приватные и сохранённые публичные диктанты), `rule_progress`, `user_rule_preference`, `user_signin_log`, `deck_training_session`, приватные диктанты/версии/ассоциации, приватные колоды/состав, секретные ссылки, назначения ролей. Чужие прохождения удаляемых приватных диктантов тоже удаляются, с пересчётом их прогресса; чужие самостоятельные ответы на слова при удалении приватной колоды сохраняются. Публичные диктанты/колоды, правила, общий словарь и ссылки на автора в общем контенте сохраняются. Порядок удаления определяется реальными FK, проверяется интеграционным тестом. Не допускается повторное связывание старого профиля с новым Better Auth user.

**Согласованная двухфазная процедура:** фаза 1 — транзакция RL (создание `user_deletion_jobs` со статусом pending, очистка личных записей и PII, необратимое обезличивание). Фаза 2 — серверное идемпотентное удаление Better Auth `user`, `account`, `session`, записей verification и credential; при сбое повторная задача `pg-boss`, затем ручное разбирательство. До фазы 2 вход по старой identity и создание RL-профиля запрещены по tombstone. Отсутствие Better Auth записи считается успехом. Только после фазы 2 операция полностью завершена. Без подтверждённой поддержки адаптера нельзя обещать единую транзакцию между Better Auth и RL.

**Персональные данные в публичном контенте:** риск PII в свободных текстах названий и содержимого публичных диктантов, колод и правил принят. Автоматический поиск PII в UC-36/37 не выполняется; административные полномочия по редактированию/удалению действуют без изменения. Это не отменяет обязанности оператора рассматривать обращения и законно удалять PII.

## Дополнительные инварианты модели (v6.4–v8.2)

- **История ответов на слова.** Для стабильного исторического отчёта `word_done` хранит снимок отображаемого задания, правильного ответа и ответа пользователя на момент выполнения (или эквивалентный неизменяемый snapshot в `dictation_done`); правка `word`/`word_placeholder` не меняет прошлые отчёты. Снимок не заменяет FK для аналитики.
- **Пороги `word_placeholder`.** `score_good_default` и `score_excellent_default` резервируются для персонального прогресса слов в P2. В первой очереди используются `word_done` и алгоритм выбора повторений по состояниям текущей тренировки (см. UC-15), **без** отдельного вычисляемого статуса слова по этим порогам; UI не должен выдавать нерассчитанный статус. Для слов, привязанных к правилу, работает `rule_progress`.
- **Изменение порогов и дерева.** После изменения порогов `rule` пересчитывается собственный статус всех затронутых пользователей; изменение родителя, архивирование и восстановление меняют вычисляемый итоговый статус дерева при следующем чтении (инвалидация кэша). Собственные счётчики не переписываются из-за перемещения правила. Циклы и перенос корня запрещаются серверной проверкой в транзакции.
- **Запланированные версии.** Для одной `dictation_record` одновременно разрешена максимум одна версия с `valid_from > now()` и `valid_to IS NULL`; публикация ещё одной версии при существующей запланированной отклоняется с предложением отменить или перенести запланированную. Операции переноса и отмены запланированной версии входят в P1 и должны выполняться транзакционно с блокировкой записи диктанта. Публикация с `valid_from = now()` допустима при отсутствии запланированной версии. Точность времени и пересечение интервалов проверяет БД.
- **Регистрация Better Auth.** Подтверждение email обязательно для email/password, новая регистрация разрешена при `service_setting.email_registration_enabled=true` (default true). Создание RL-профиля и student-role атомарно в транзакции RL после подтверждения identity; если Better Auth сохраняет неподтверждённую учётную запись, защищённые действия запрещены. При сбое отправки письма процедура остаётся незавершённой, специальная обработка сбоя доставки не входит в первую очередь. Для двух разных транзакционных границ необходима компенсация, не обещание общей атомарности.
- **Безопасность пароля.** Better Auth `emailAndPassword` 8–128 символов, штатный scrypt-хеш; 8–11 символов требуют явного непредустановленного подтверждения риска в текущем запросе, без хранения отметки. Правило действует при регистрации, смене и сбросе. Сброс использует одноразовый токен и отзывает все сессии, смена требует текущий пароль и отзывает остальные сессии. Наличие email не раскрывается через ответ сброса.
- **Один активный email — один профиль.** `user_profile.email` уникален для ненулевых значений. OAuth и email/password связываются **только** после доказательства владения обоими способами входа, совпадения email недостаточно; Better Auth implicit linking отключён. При повторной регистрации с прежним email после полного удаления создаются новые Better Auth user и `user_profile.id`.
- **Бутстрап первого администратора.** Серверная настройка `admin_email`; после подтверждения email при первоначальной регистрации назначаются admin и `is_founder_admin=true` в одной RL-транзакции. Признак неизменяем, не вычисляется по ID/времени, второй founder не создаётся. При изменении admin_email исторические роли не меняются; полный запрет удаления и снятия роли founder действует всегда. Юридический риск по 152-ФЗ явно принят как бизнес-ограничение, требует оценки до запуска.
- **Повторная аутентификация при UC-37.** Email/password — повторный ввод текущего пароля; OAuth — новое подтверждение того же issuer/provider account ID с гарантированно свежим входом, иначе операция недоступна до появления безопасной альтернативы. Существующей cookie-сессии недостаточно.
- **Настройки регистрации.** `service_setting.email_registration_enabled` boolean NOT NULL DEFAULT true; admin может изменять, отключение блокирует только новые email/password-регистрации, не существующий вход, смену и сброс пароля. Верификация email, восстановление и смена пароля включены в первую очередь. OAuth-провайдеры требуют отдельной верифицированной конфигурации.

- **Время и лимиты.** Для дневных лимитов используется явно настроенная временная зона сервиса (`Europe/Moscow` по умолчанию), для интервалов версий — UTC/timestamptz и часы БД. Параметр M — рекомендация, а не запрет; N — мягкий лимит посетителя по серверно подписанной сессии.

# Бизнес-логика

## Алгоритм «Обновление рейтинга правил» (rule_score_calculation)

Алгоритм, выполняющий расчёт атрибута current_score для прогресса rule_progress.status.

Правила с is_archived = true пропускаются — их rule_progress не обновляется (см. раздел «Прогресс правила»). Они также не входят в агрегацию статусов родительских правил.

| Шаг | Проверка условия | Статус |
|---|---|---|
| 0 | Если `rule.use_in_placeholder = false`, удалить существующую строку `rule_progress` (если она есть), собственный прогресс не вычислять; итоговый статус получить по активным детям согласно разделу агрегации. | — |
| 1 | Для каждого пользователя собрать за окно 4 месяца (now() − 4 месяца … now()) все выполнения по правилу из двух источников: (а) placeholder_done — время из dictation_done.created_at; (б) word_done — время из word_done.created_at (для выполнений в рамках диктанта оно равно dictation_done.created_at, для самостоятельной тренировки — собственное время попытки). Выполнения старше 4 месяцев отбрасываются. Статус может меняться даже через 1 час после пересчёта — это Ok. В дальнейшем алгоритм будет совершенствоваться. |  |
| 2 | Если выполнений нет (ни placeholder_done, ни word_done) → Grey. Расчёт завершён. Иначе — к шагу 3. Примечание: статус Grey не хранится в rule_progress — запись не создаётся (или удаляется, если существовала); отсутствие строки = Grey. | Grey |
| 3 | Подсчитать раздельно по источникам: placeholder_bad (placeholder_done.is_correct = false) и placeholder_ok (is_correct = true); word_bad (word_done.is_correct = false) и word_ok (is_correct = true). Записать все четыре значения в progress. В word_done учитываются только выполнения, привязанные к правилу через word_placeholder.rule_id IS NOT NULL и word_placeholder.is_exception = false (исключения из правила и словарные слова без правила не входят). |  |
| 4 | current_score = (placeholder_ok + word_ok) − (placeholder_bad + word_bad) − 2. «Минус 2» — коэффициент надёжности: правильных должно быть хотя бы на 2 больше. |  |
| 5 | Если current_score < rule.score_good_default → Red. Расчёт завершён. | Red |
| 6 | Если current_score < rule.score_excellent_default → Yellow. Расчёт завершён. | Yellow |
| 7 | Иначе → Green. | Green |

### Учёт статуса дочерних правил

#### 1. Статусы правила

| Код | Русское название | Смысл |
|---|---|---|
| Grey | Не начато | 0 выполнений с этим правилом за окно 4 месяца (ни placeholder_done, ни word_done) |
| Red | Плохо освоено | Выполнения есть, но current_score < score_good_default |
| Yellow | Хорошо | score_good_default <= current_score < score_excellent_default |
| Green | Отлично | current_score >= score_excellent_default |

Не путать: Grey = «0 выполнений», Red = «выполнения есть, но мало».

#### 2. Собственный статус правила

Вычисляется по собственным выполнениям правила — placeholder_done и word_done (шаги 1–7 основного алгоритма, без учёта детей). Промежуточный результат для агрегации.

#### 3. Итоговый статус правила

Если `use_in_placeholder = true`: лист дерева (нет активных детей) имеет итоговый статус = собственному; родитель агрегирует собственный статус с итоговыми статусами активных детей.

Если `use_in_placeholder = false`: собственный статус не участвует в вычислении. Итоговый статус определяется **только** активными детьми; если их нет, итоговый статус Grey.

#### 4. Правило агрегации

Пусть P — собственный статус родителя, C — множество итоговых статусов активных (не архивных) дочерних правил. **Следующая агрегация применяется только при `use_in_placeholder = true` и непустом C.** Тогда:

Если P = Red или хотя бы один ребёнок Red → Red.

Иначе, если P = Green и все дети Green → Green.

Иначе, если P = Grey и все дети Grey → Grey.

Иначе → Yellow.

Проверяется по порядку, первое сработавшее определяет результат.

**Для `use_in_placeholder = false`** P игнорируется: при пустом C → Grey; если хотя бы один ребёнок Red → Red; иначе если все дети Green → Green; иначе если все дети Grey → Grey; иначе → Yellow. Так, единственный Green-ребёнок даёт Green родителю (а не Yellow); Green + Grey даёт Yellow. Эта агрегация также выполняется снизу вверх.

Пояснения:

Red доминирует: ошибки хотя бы в одном месте → всё правило «плохо освоено».

Green требует полноты: и само правило, и все дети — Green.

Grey требует полного отсутствия данных: ни по правилу, ни по детям нет выполнений.

Иначе — Yellow (промежуточное состояние).

Формулировка «найти худший статус» не используется — она даёт неверный результат в строках 4 и 13 таблицы соответствия (см. п. 7).

#### 5. Порядок вычисления

Снизу вверх, от листьев к корню:

Листья: при `use_in_placeholder = true` итоговый статус = собственному, при false — Grey.

Родители: при `use_in_placeholder = true` агрегируют собственный статус и детей, при false — только детей.

Поднимаемся до корня.

Корень «Все правила» — последним.

Архивные правила пропускаются на всех этапах: их собственный статус не пересчитывается (замораживается), и они не входят в множество C при агрегации родительского правила.

#### 6. Примеры

P = Green, C = [Grey] → Yellow (само правило отлично, ребёнок не начат).

P = Grey, C = [Green] → Yellow (само правило не начато, ребёнок отличен).

P = Green, C = [Green, Green] → Green (и правило, и все дети отлично).

P = Green, C = [Grey, Green] → Yellow (один ребёнок не начат).

P = Grey, C = [Grey, Grey] → Grey (ни правило, ни дети не начаты).

P = Yellow, C = [Red] → Red (ошибки в ребёнке портят всё правило).

P = Green, C = [Green, Green, Grey] → Yellow (один Grey не даёт родителю стать Green).

#### 7. Соответствие таблице из 16 строк (для одного ребёнка, `use_in_placeholder = true`)

| Строка | P | C | По правилу | По таблице |
|---|---|---|---|---|
| 1 | Grey | Grey | Grey (п. 3) | Grey |
| 2 | Red | Grey | Red (п. 1) | Red |
| 3 | Yellow | Grey | Yellow (п. 4) | Yellow |
| 4 | Green | Grey | Yellow (п. 4) | Yellow |
| 5 | Grey | Red | Red (п. 1) | Red |
| 6 | Red | Red | Red (п. 1) | Red |
| 7 | Yellow | Red | Red (п. 1) | Red |
| 8 | Green | Red | Red (п. 1) | Red |
| 9 | Grey | Yellow | Yellow (п. 4) | Yellow |
| 10 | Red | Yellow | Red (п. 1) | Red |
| 11 | Yellow | Yellow | Yellow (п. 4) | Yellow |
| 12 | Green | Yellow | Yellow (п. 4) | Yellow |
| 13 | Grey | Green | Yellow (п. 4) | Yellow |
| 14 | Red | Green | Red (п. 1) | Red |
| 15 | Yellow | Green | Yellow (п. 4) | Yellow |
| 16 | Green | Green | Green (п. 2) | Green |

Для нескольких детей правило обобщается естественно (см. примеры).

**Дополнительные примеры для `use_in_placeholder = false`:** C = [Green] → Green; C = [Grey] → Grey; C = [Red, Green] → Red; C = [Green, Grey] → Yellow; C = [] → Grey. Собственный P не используется.

#### 8. Замечания

Для правил с `use_in_placeholder = false` изменение порогов не влияет на итоговый статус; менять флаг допускается только с соблюдением ограничений ссылочной целостности опубликованных диктантов.

Собственный vs итоговый статус: не путать. Собственный — только по выполнениям самого правила (placeholder_done + word_done). Итоговый — с детьми.

Red vs Grey: Red — ошибки; Grey — нет данных. В агрегации ведут себя по-разному.

«Худший статус» не используется — формулировка ошибочна для строк 4 и 13.

Корневое правило с `use_in_placeholder=false` не имеет собственного P: если все активные дети Green, итоговый статус корня Green; если есть Red — Red; если все Grey — Grey; иначе Yellow. Для корня seed с `use_in_placeholder=false` применяется именно эта ветка алгоритма, а не строка 13 для правил с `use_in_placeholder=true`.

Листья: агрегация не применяется, итоговый = собственный.

#### 9. Когда запускается пересчёт

После выполнения пользователем версии диктанта — для этого пользователя (один пересчёт по завершении прохождения).

После каждого ответа в тренировке слов (создания каждой word_done с dictation_done_id IS NULL) — для этого пользователя (решение от 10.11.2026). Пересчёт выполняется после фиксации ответа; сбой пересчёта не откатывает сохранённый ответ — страховка: ежесуточный пересчёт по расписанию.

Ежесуточно по расписанию — для всех активных (необезличенных, незаблокированных) пользователей. При разблокировке пересчёт выполняется до показа актуального прогресса.

Из панели администратора — по всем пользователям или по конкретному (id или email).

Правила с is_archived = true при пересчёте пропускаются. Если правило снято с архивации, при следующем пересчёте оно снова участвует.

### Критерии приёмки

После выполнения диктанта или тренировки слов статусы правил пользователя пересчитаны; calculated_at обновлён.

Лист дерева: итоговый статус = собственный.

Родитель: итоговый = агрегация собственного статуса с итоговыми статусами активных (не архивных) детей по нормативной матрице «Соответствие таблице из 16 строк» (раздел 7 алгоритма обновления рейтинга правил).

Архивные правила: собственный статус заморожен (не пересчитывается), в агрегацию родителя не входят.

Grey **собственный** = отсутствие строки rule_progress; итоговый статус родителя вычисляется на чтении дерева и может быть не Grey при отсутствии строки. Алгоритм не создаёт записи Grey и удаляет существующую запись при переходе статуса в Grey (выполнений за окно не осталось). Состояние пользователя (state) хранится отдельно в user_rule_preference и на удаление rule_progress не влияет — предпочтение сохраняется независимо от рассчитанного прогресса.

current_score = (placeholder_ok + word_ok) − (placeholder_bad + word_bad) − 2; статус: < score_good_default → Red; < score_excellent_default → Yellow; иначе Green.

Пересчёт по расписанию — для всех активных (необезличенных, незаблокированных) пользователей; из панели администратора — по всем таким пользователям или по одному активному пользователю (id или email). При разблокировке пересчёт до показа прогресса.

state (InUse по умолчанию / Ok / Pause) — намерение пользователя в отношении правила; хранится в отдельной сущности user_rule_preference, независимо от рассчитанного прогресса rule_progress. Смена state не запускает пересчёт и не изменяет status, current_score и счётчики (placeholder_ok/bad, word_ok/bad) — даже InUse → Ok оставляет прогресс неизменным.

Установка state на правило без записи rule_progress создаёт запись user_rule_preference с указанным state (rule_progress при этом не создаётся — он создаётся только алгоритмом при первом выполнении, со статусом Red/Yellow/Green).

Установка state тиражируется рекурсивно на активные (не архивные) дочерние правила: для детей с собственным рассчитанным прогрессом (статус Red/Yellow/Green) сервис уточняет у пользователя, применять ли то же состояние; для детей без собственного рассчитанного прогресса (Grey / нет записи) состояние применяется автоматически (с созданием записи user_rule_preference при необходимости). Архивные дочерние правила пропускаются.

## Создание и редактирование версий диктантов

Текст и заголовок версии можно редактировать, пока у версии нет dictation_done. Если хотя бы одно выполнение есть — нужно создавать новую версию.

При сохранении версии проверить:

Если в подстановке указан id — правило с таким id должно существовать.

Указан хотя бы один правильный вариант.

В альтернативах — только кириллические буквы (а–я, А–Я, ё, Ё), а также , - _ # ; : — единый перечень формальной грамматики (латиница исключена в v8.2).

id и key уникальны в пределах создаваемой версии.

## Период действия версии диктанта

### Назначение

Каждая версия диктанта имеет период активности — её текст видят и проходят студенты. Период задаётся парой valid_from / valid_to. Старые версии не удаляются: на них ссылаются dictation_done.dictation_version_id.

Цель раздела:

в любой момент у записи диктанта ровно одна активная версия;

версии — непрерывная цепочка без разрывов и пересечений;

отложенная публикация работает без ручного вмешательства и без фоновых задач.

### Семантика интервала

Интервал полуоткрытый: [valid_from, valid_to). valid_from включается, valid_to — нет.

valid_to = NULL — «открытый конец» (активна до появления следующей версии). В коде трактуется как «бесконечность».

Активная версия: valid_from <= now() AND (valid_to IS NULL OR now() < valid_to).

now() — только серверное время Postgres. Поля — timestamptz (UTC); отображение — в часовом поясе пользователя.

valid_from в будущем → версия запланирована.

### Состояния версии (вычисляются, не хранятся)

| Состояние | Условие | Редактирование текста | Смена периода |
|---|---|---|---|
| Запланирована | now() < valid_from | Да, если нет прохождений | Да (обязательно P1, операции 5–6) |
| Активна | valid_from <= now() < valid_to (или valid_to IS NULL) | Да, если нет прохождений | Нет |
| В архиве | valid_to <= now() | Нет (история) | Нет |

Состояние в БД не хранится — вычисляется из valid_from, valid_to, now().

### Инварианты

Ровно одна открытая версия. У записи — не более одной версии с valid_to IS NULL.

Нет пересечений. Интервалы версий одной записи не пересекаются.

Нет разрывов. Для соседних k и k+1: version_k.valid_to = version_{k+1}.valid_from.

Монотонность номеров. version_number растёт вместе с valid_from.

Корректный интервал. valid_from < valid_to (если valid_to не NULL). Пустой интервал недопустим.

Инварианты 1–2 обеспечиваются средствами Postgres (см. «Технические требования к БД»). Инварианты 3–5 — транзакционной логикой публикации.

### Операции

#### 1. Создание записи диктанта (первая версия)

Одна транзакция:

INSERT dictation_record.

INSERT dictation_version: version_number = 1, valid_from = now(), valid_to = NULL.

Заполнить dictation_version_rule и dictation_version_word_placeholder по подстановкам.

Первая версия активна немедленно.

#### 2. Публикация новой версии — немедленно

Вход: запись, текст, автор, опционально valid_from (по умолчанию now()).

Найти открытую версию (valid_to IS NULL) и заблокировать FOR UPDATE.

Проверить входные данные (см. «Проверки при публикации»).

UPDATE prev SET valid_to = valid_from_new.

INSERT новой версии: valid_to = NULL, version_number = prev.version_number + 1.

Пересобрать dictation_version_rule и dictation_version_word_placeholder для новой версии.

Результат: prev.valid_to = new.valid_from, новая версия активна с valid_from.

#### 3. Публикация новой версии — отложенно

То же, но valid_from в будущем. Если уже существует запланированная версия, новая публикация отклоняется до отмены/переноса существующей.

Результат: до valid_from активна prev; с valid_from — новая версия. Без cron.

#### 4. Редактирование версии без прохождений

Проверить отсутствие dictation_done для этой версии.

Проверить, что версия не в архиве.

Обновить текст, пересобрать dictation_version_rule и dictation_version_word_placeholder.

Период не меняется. Пересборка производных таблиц при смене периода не требуется.

#### 5. Смена valid_from у запланированной версии (обязательно в P1 первой очереди)

Только для версии в состоянии «Запланирована», без прохождений. Новый valid_from > prev.valid_from и > now().

#### 6. Отмена запланированной версии (обязательно в P1 первой очереди)

Только для последней версии (valid_to IS NULL) в состоянии «Запланирована», без прохождений. prev.valid_to = NULL, запланированная версия удаляется.

### Проверки при публикации

Проверки содержания (текст, подстановки, ссылки, уникальность) обязательны при создании, редактировании и публикации версии; проверки периода — при публикации и переносе даты. «Активное правило для новой подстановки» означает `rule.deleted_at IS NULL AND rule.is_archived=false AND rule.use_in_placeholder=true`. Изменение правила после публикации не переписывает исторические версии и ответы.

| Проверка | Условие | Сообщение (RU) |
|---|---|---|
| Дата не в прошлом | valid_from >= now() | «Нельзя опубликовать версию в прошлом» |
| Дата позже предыдущей | valid_from > prev.valid_from (строго) | «Дата публикации должна быть позже даты предыдущей версии» |
| Текст не пуст | после btrim длина > 0 | «Текст диктанта не может быть пустым» |
| Размер текста | ≤ 30 720 байт нормализованного UTF-8 (CRLF/CR→LF, NFC) | «Текст превышает лимит 30 КиБ (30 720 байт UTF-8)» |
| Подстановки валидны | по правилам нотации | «Ошибка в подстановке №{index}: {причина}» |
| Запись не удалена | dictation_record.deleted_at IS NULL | «Запись диктанта не найдена» |
| Количество подстановок | count(подстановок) ≤ 100 | «Превышен лимит подстановок в версии (максимум 100)» |
| Количество альтернатив | в каждой подстановке count(альтернатив) ≤ 5 | «В подстановке №{index} превышен лимит альтернатив (максимум 5)» |
| Длина альтернативы | длина каждой альтернативы ≤ 5 символов | «В подстановке №{index} альтернатива длиннее 5 символов» |
| Уникальность (id, key) | пары (id правила, key) уникальны в пределах версии | «В подстановке №{index} повторяется пара (id правила, key)» |
| Существование правила | для каждого `id:<rule.id>` правило существует, `deleted_at IS NULL`, `is_archived=false` | «В подстановке №{index} указано несуществующее или архивное правило» |
| Разрешение правила | для каждого `id:<rule.id>` `rule.use_in_placeholder=true` | «Правило не разрешено использовать в подстановках» |
| Существование словарной подстановки | для каждого `wp:<word_placeholder.id>` запись существует, не удалена, связанное слово существует и не удалено | «Словарная подстановка недоступна» |
| Допустимость правила словарной подстановки | если у `wp` заполнен `rule_id`, правило существует, не удалено, не архивировано и `use_in_placeholder=true` | «Правило словарной подстановки недоступно» |
| Уникальность пары (wp, key) | `(word_placeholder_id, key)` уникальна внутри версии, `key` по умолчанию 1 | «Повторяется пара (словарная подстановка, key)» |

### Конкурентность

Все операции с периодом — в транзакции с блокировкой открытой версии (FOR UPDATE).

READ COMMITTED + явные блокировки достаточно; SERIALIZABLE избыточен.

EXCLUDE — последняя линия обороны: при гонке одна транзакция упадёт с ошибкой 23P01, клиент получит понятное сообщение и повторит.

### Технические требования к БД

btree_gist — включить в миграциях (нужно для следующего пункта).

Запрет пересечений — EXCLUDE на dictation_version:

dictation_record_id (равенство);

tstzrange(valid_from, valid_to, '[)') (пересечение).

Запрет двух открытых версий — частичный уникальный индекс:

dictation_record_id;

WHERE valid_to IS NULL.

Корректность интервала — CHECK (valid_to IS NULL OR valid_from < valid_to).

Уникальность номера версии — UNIQUE (dictation_record_id, version_number).

Генерация version_number — в транзакции: prev.version_number + 1, где prev — открытая версия, взятая FOR UPDATE. Уникальный индекс — страховка.

### Как получить активную версию

```sql
SELECT *
FROM dictation_version
WHERE dictation_record_id = :record_id
  AND valid_from <= now()
  AND (valid_to IS NULL OR now() < valid_to);
```

Ожидается ровно одна строка.

**Операции 5 и 6 (перенос и отмена запланированной версии) обязательны в P1.**

### Что НЕ входит в 1-ю очередь

Черновики (версия без периода) — не поддерживаются.

Автоматическое изменение dictation_record.is_active при смене активной версии — is_active управляется вручную.

Cron для переключения версий — не нужен: активность определяется через now().


### Критерии приёмки

Создание записи → первая версия активна немедленно, valid_to IS NULL.

Публикация «сейчас» → prev.valid_to = new.valid_from, новая активна, предыдущая в архиве.

Публикация «на будущую дату» → до этой даты активна предыдущая, после — новая, без ручных действий.

valid_from в прошлом → ошибка.

valid_from <= prev.valid_from → ошибка.

Редактирование активной/запланированной версии без прохождений → текст меняется, период не меняется.

Редактирование версии с прохождениями → ошибка.

Редактирование архивной версии → ошибка.

Два одновременных запроса на публикацию → один succeeds, второй получает понятную ошибку.

Запрос «активная версия» возвращает ровно одну строку.

Цепочка version_k.valid_to == version_{k+1}.valid_from сохраняется.

Прямая вставка пересекающегося интервала через SQL → БД отклоняет.

Прямая вставка второй открытой версии через SQL → БД отклоняет.
