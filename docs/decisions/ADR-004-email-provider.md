# ADR-004 — Исходящая транзакционная почта RL

**Файл:** `ADR-004-email-provider.md`  
**Дата архитектурного выбора:** 12.11.2026  
**Статус архитектурного выбора:** **ACCEPTED / `DEC-05=FIXED`** — принят заказчиком 12.11.2026 в ходе согласования рекомендаций  
**Статус эксплуатационной проверки:** **`MAIL_DELIVERY_VERIFICATION=VERIFY`** — не завершена, никакие результаты реальной доставки не заявляются  
**Основание:** RL v9.8 (корректировка почты), архитектура v1.3, W0-08.

## 1. Контекст

Ранее архитектура v1.1 и стек v9.8 предлагали выбор между Unisender и Яндекс 360 (`BLOCKED: MAIL_PROVIDER_DECISION`). После обсуждения заказчик утвердил иной вариант: **свой Postfix для исходящей почты в Docker на VPS РФ и локальный Mailpit**. Этот ADR фиксирует выбор технологии и **не подменяет** отдельные технические испытания.

## 2. Принятое решение (не переопределять агентом)

1. **Production:** только собственный исходящий SMTP Postfix в Docker на размещённом в РФ VPS RL; веб-приложение обращается к нему по закрытой внутренней сети контейнеров.
2. **Local/test:** Mailpit без отправки настоящих писем в интернет.
3. **Не требуется:** Dovecot, IMAP, POP3, обработка входящих писем, пользовательские почтовые ящики, отдельная внешняя почтовая платформа.
4. Не предусматривать скрытый внешний fallback (Unisender, Яндекс 360, коммерческий relay). Если исходящий TCP 25 блокируется VPS или доставка неприемлема, фиксировать `BLOCKED` и вернуться к заказчику за новым архитектурным решением.
5. Выбор библиотеки SMTP-клиента/адаптера для установленного Better Auth разрешено сделать W0-08 после проверки реального API и тестов — это локальная техническая деталь, не изменение почтовой архитектуры.

## 3. Обоснование и компромиссы

Преимущества: контроль эксплуатации и хранения журналов в РФ, независимость от конкретного SaaS, упрощение стека по части входящей почты. Издержки: самостоятельная настройка DNS/IP-репутации, риск блокировки порта 25, эксплуатация очереди, поддержка доставки и мониторинг отказов. **Наличие VPS РФ не гарантирует, что email всегда доставляется или что отсутствуют трансграничные потоки к почтовым доменам получателей.**

## 4. Эксплуатационные ограничения и риски

- SMTP Postfix не является публичным relay; ограничить доступ Docker сетью, не публиковать SMTP submission для всего интернета, проверить `mynetworks`/relay policy.
- Секреты подключения и DKIM-ключи — вне Git и логов; ссылки подтверждения email и reset-токены не логировать.
- W0-08 обязан проверить исходящие TCP 25 к внешним MX, наличие/настройку статического IP, PTR, SPF, DKIM, DMARC, HELO/EHLO и репутационные ограничения.
- Доставка проверяется фактическими письмами подтверждения регистрации и сброса пароля. Должны проверяться срок/одноразовость ссылки, таймауты, повторы, очередь, 4xx/5xx, restart/recovery без ложного успешного статуса.
- **Поздние bounce:** без входящего SMTP письма-отчёты о недоставке по Return-Path автоматически в систему не поступят. Требуется отдельная оценка наблюдаемости и принятие этого риска заказчиком до production. Не внедрять входящий MTA/Dovecot без нового решения.
- Эксплуатационные метрики — без персональных данных в логах. Логи, persistent volumes и бэкапы в РФ. Внешние DNS/CA/MX и передача получателям требуют карты потоков и отдельной юридической оценки; эта ADR не подтверждает автоматически соблюдение всех требований 152-ФЗ.

## 5. Требование к W0-08 (acceptance gate)

| ID | Проверка | Доказательство |
|---|---|---|
| MAIL-01 | Postfix на реальном VPS РФ, изоляция SMTP | Конфигурация без секретов, сетевой тест |
| MAIL-02 | Из VPS разрешён исходящий SMTP к MX | Результат теста TCP 25 и ограничения хостера |
| MAIL-03 | DNS/SPF/DKIM/DMARC/PTR настроены | Выписка DNS, заголовки полученных писем |
| MAIL-04 | Подтверждение email доставлено | Фактический end-to-end тест, одноразовый токен |
| MAIL-05 | Сброс пароля доставлен | Фактический end-to-end тест, срок действия/отказ повторного входа |
| MAIL-06 | Ошибки и очереди | 4xx/5xx, временные отказы, повторы, restart |
| MAIL-07 | Локальный Mailpit | Тесты не отправляют email вовне |
| MAIL-08 | Ограничение bounce и эксплуатация | Протокол/решение о риске без входящей почты |
| MAIL-09 | Безопасность/152-ФЗ | Проверка логов/секретов, карта потоков данных |

Для каждого пункта указать `PASS/FAIL/BLOCKED/NOT RUN`, время, окружение, команду/метод и свидетельство без PII. Пока хотя бы один обязательный пункт не завершён — `MAIL_DELIVERY_VERIFICATION=VERIFY` или `BLOCKED`, а не `PASS`.

## 6. Статусы и ответственность

- `DEC-05`: **FIXED** — технология утверждена заказчиком. Изменение требует нового решения.
- `MAIL_DELIVERY_VERIFICATION`: **VERIFY**, W0-08, ответственный за реализацию — AI-агент в пределах ТЗ; за принятие ограничений — заказчик.
- `DEC-06`: **BLOCKED**, независимо от DEC-05; числовые пороги rate limiting в этом ADR не определяются.
- `WAVE0_ACCEPTED` и production-ready не допускаются до результатов MAIL-01…MAIL-09 и выполнения остальных общих критериев архитектуры v1.3.

## 7. Реестр фактических испытаний W0-08

**Не заполнен.** Дата, домен, VPS, точные версии, конфигурация, результаты и решение заказчика добавляются только по факту W0-08. Отсутствие протокола — не доказательство успешной доставки.
