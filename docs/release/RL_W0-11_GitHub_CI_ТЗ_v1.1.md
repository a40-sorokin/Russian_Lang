# RL — W0-11. GitHub, CI и приёмка автоматизированных проверок

**Редакция:** 1.1 · **Дата:** 13.11.2026  
**Статус:** конкретизация существующего задания W0-11 архитектуры v1.3, **не** замена общего W0-11 и не изменение W0-01.  
**Основание:** `RL_Git_CI-CD_и_окружения_v1.1.md`, `RL_Стек_v9.8.md`, «Архитектура» v1.3 §11 и §13, `AGENTS.md`, W0-01 v1.2.

**Изменения v1.1:** привязка к полному выпуску `v9.8-DEC05-r2`, архитектуре v1.3 и регламенту Git/CI/CD v1.1. Содержательные границы W0-11 не изменены; release/deploy workflows по-прежнему не входят в обязательную приёмку W0-11.

## 1. Предварительные условия

1. Использовать **фактический** Git-проект и результаты W0-01…W0-10. Если они не готовы, оформить `W0-11_PARTIAL` со списком блокеров, не создавать фиктивные реализации и не обходить неудавшиеся тесты.
2. Уточнить у владельца: реальный GitHub repository URL, тип доступа (private/public), административные полномочия, допустимую модель review и разрешение создать `develop` и настроить workflows. **Агент не создаёт remote, токены, secrets и оплачиваемые ресурсы без полномочий.**
3. Сверить `package.json` и scripts с W0-01. В git не коммитить `.env`, OAuth credentials, dump production, PII/логи.
4. Прочитать `RL_Стек_v9.8.md`, версию lockfile, `AGENTS.md`, `RL_Git_CI-CD_и_окружения_v1.1.md`, существующие ADR и таблицу соответствия DEC → ADR в §12.1 архитектуры v1.3; проверить статусы DEC. Не закрывать `DEC-06`/`DEC-11` только настройкой CI.

## 2. Границы W0-11

**Входит:** GitHub remote (при разрешении владельца); сохранение истории `main`; создание `develop`; доступные правила защиты двух веток; PR template; CI на PR/push; PostgreSQL integration на временных синтетических данных; Playwright smoke; отчёт доказательной приёмки; инструкция владельцу для review и release approval. При наличии уже действующего CI редактировать аккуратно, без уничтожения настроек.

**Не входит:** создание PROD VPS/домена, настройка Postfix, реальный live OAuth, запуск DEMO/PROD, выкладка image или объявление готовности production; это отдельные согласования/работы. `release.yml` и `deploy-*.yml` из целевого регламента **не обязательны** для приёмки самого W0-11; их добавляют только в момент подготовленного и разрешённого этапа. Если шаблоны созданы заранее, они должны быть явно отключены от автоматического запуска/без deployment credentials.

**Примечание о доступности GitHub:** правила защиты и reviewers зависят от плана/типа репозитория. Если конкретная функция недоступна, не имитировать её workflow; перечислить фактические доступные ограничения и безопасный ручной контроль владельца. Отсутствие независимого второго человека не компенсировать фиктивным «AI approval».

## 4. Структура примерного `ci.yml` (технические правила, не готовый файл)

- `name: CI`; триггеры `pull_request` на `develop/main` и `push` на `develop`.
- `permissions: contents: read` по умолчанию. Никаких secrets для тестов PR из внешних веток.
- `concurrency` по ref/PR для экономии ресурсов (не отменять release/deploy jobs).
- `actions/checkout`, `actions/setup-node` — версии и pin подтверждаются при настройке, Node 24 и npm cache по lockfile.
- `npm ci`, далее `npm run check` **только если** скрипт действительно покрывает согласованные проверки; иначе запускать шаги отдельно, чтобы отчёт был прозрачным.
- PostgreSQL 16 контейнер только для integration job; auth/public схемы создаются настоящими миграциями через зафиксированную Prisma 7.8 и проверенный driver adapter, не `db push`.
- Playwright Chromium устанавливается через команду актуальной версии 1.64.x; при недоступности браузера CI job красный/`BLOCKED`, не помечать `PASS`.
- Отчёт фиксирует точные версии Node/npm/Next/Prisma/Vitest/Playwright, SHA, длительность и результаты.
- Когда W0-03…07 ещё не выполнены, **нет** предмета для некоторых проверок; поставить `NOT_APPLICABLE_YET` с привязкой к задаче, не вставлять тест, всегда возвращающий true.

## 5. Инструкции по настройке для владельца (без повторного ручного доступа агента)

1. В GitHub создать **приватный репозиторий**, если это согласовано; убедиться, что репозиторий не содержит паролей или закрытой документации, которую нельзя размещать на GitHub. Проверить условия размещения исходников/метаданных и доступность GitHub из рабочего окружения.
2. Добавить агента в GitHub только с нужным объёмом доступа, без production ключей. Настроить `origin` на локальном проекте по явному адресу.
3. После первого синхронизированного `main` создать `develop`; защитить оба branch rule/ruleset по доступным функциям.
4. Назначить обязательный `CI` status check лишь **после первого успешного запуска**, иначе можно заблокировать все PR несуществующим именем check.
5. Создать тестовый PR в `develop`; увидеть команды и проверку падения; затем выполнить review и merge по принятому порядку.
6. Сохранить фактический отчёт с SHA, ссылками на runs (если репозиторий закрыт, ссылки доступны только имеющим права), снимком статусов DEC.

## 6. Негативные/аварийные проверки

- Падение typecheck/lint/test действительно блокирует merge.
- PR из неизвестного источника не читает deployment secrets и не имеет write access к package/infra ресурсам.
- Обнаруженный секрет в PR удаляется с ротацией ключа; одного удаления файла из последнего коммита недостаточно, история и логи оцениваются на компрометацию.
- Миграция со сломанным FK/SQL приводит к отказу integration job.
- Повторный запуск CI на том же SHA должен быть воспроизводимым (в пределах внешних нестабильностей); при flaky test — отдельный дефект.
- Никакая ветка `develop` не активирует развёртывание на PROD.
