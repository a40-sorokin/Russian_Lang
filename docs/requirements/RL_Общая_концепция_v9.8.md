# RL — общая концепция v9.8

**Дата:** 12.11.2026. Основа — полная версия v8.2, с сохранением ранее согласованных требований к тренировкам, прогрессу и статистике.

Я хочу организовать онлайн активности для подготовки к ЕГЭ по русскому языку.
Планирую организовать веб-сервис со следующими основными возможностями.
Первая очередь реализации:
1. Дерево правил русского языка. Пользователь имеет возможность наглядно отслеживать прогресс по каждому узлу.
2. Пользователь выполняет онлайн-диктанты. Диктант - текст с пропущенными буквами и знаками препинания, пользователь должен заполнить пропущенные места. Каждое пропущенное место связано с одним из правил из дерева правил. Таким образом, отслеживается прогресс в освоении правил (задания в пройденных диктантах выполнены хорошо или с ошибками, или правила еще не отрабатывались пользователем).
Вторая очередь реализации:
3. Пользователям предлагается выполнить челенджи - регулярные задания. Задания в челенджах так же связаны с правилами в дереве правил, что помогает отследить прогресс пользователя в дереве правил.
4. Пользователь может делиться своим прогрессом с помощью "тайных ссылок".
Третья очередь реализации:
5. Референсная модель: предлагаем пользователям привлекать других пользователей за процент от их подписок.
6. Интеграция с профессиональными репетиторами. Предлагаем репетитору использовать онлайн диктанты для своих учеников. Можно создавать свои уникальные онлайн-диктанты, можно проводить на платформе свои уникальные челенджи. Прогресс учеников также отслеживается в дереве правил.

Работать должно в современных наиболее используемых браузерах.
Фронтенд должен быть оптимизирован как для настольных мониторов, так и для экранов смартфонов и планшетов.
Разработка будет выполняться ИИ-агентами.
Стек технологий согласован и зафиксирован (см. ниже). Канонические требования определены в отдельных документах: UX/сценарии — Use Cases, сущности/алгоритм прогресса — ER, удаление — специальная спецификация, фазы и состав работ — декомпозиция. В концепции фиксируются только продуктовые принципы.
Это должны быть технологии с хорошо зарекомендовавшими себя опытом использования, с обширным комьюнити, отлично документированными.  Важна доступность технологий в России.
Все данные сервиса должны храниться на территории России.
Все software-продукты должны иметь лицензию для свободного коммерческого использования. Однако, при острой необходимости можно предложить варианты платных продуктов.
Количество пользователей и нагрузка на сервер не будут высокими, не нужно закладываться на highload-решения.

# Стек

Стек технологий зафиксирован в отдельном документе `RL_Стек_v9.8.md` и здесь не дублируется: он — единственный источник по выбору версий и компонентов. Краткая сводка: Node.js 24 LTS, TypeScript 5.9 (strict), Next.js ≥ 16.4.1, React 19.3, Tailwind CSS v4, shadcn/ui + Radix, PostgreSQL 16 (одна база, схемы `auth`/`public`), Prisma 7.8, **Better Auth** (Yandex ID / VK ID / Sber ID после проверки / Email-Password), **pg-boss**, pino + OpenTelemetry + GlitchTip (self-hosted), Docker Compose + Caddy, Vitest + Playwright. Хостинг — российский VPS, все данные только в России.

Язык интерфейса — только русский (i18n не нужен).

# История принятых продуктовых решений — 09.11.2026

• Тренировка слов по колоде: повторение в блоках из шести показов с целевым распределением NEW:ERROR:CORRECT = 2:3:1; при нехватке категорий применяются детерминированные правила замещения.
• Тренировка автоматически завершается, когда в текущем запуске пользователь хотя бы раз правильно ответил на каждое слово колоды. Затем предлагается выбрать другую колоду или выполнить диктанты. Ранее пройденную колоду можно начать заново в новой сессии.
• Вне подстановок символ / удаляется автоматически с уведомлением; внутри подстановок он разделяет варианты.
• Better Auth и RL используют одну PostgreSQL с двумя схемами auth/public. Транзакция RL создаёт профиль и роль после подтверждения email; удаление состоит из транзакционного обезличивания профиля и последующей идемпотентной очистки Better Auth через pg-boss. Не обещать общую транзакцию адаптера без проверки.
• Полноценный юридический документооборот исключён из первой очереди, однако три флага согласия пользователя и технические меры защиты данных обязательны. Подробная нормативная спецификация — RL_Use_Cases_v9.8.md и RL_ER-сущности_v9.8.md.

# История принятых продуктовых решений — 10.11.2026

• Первый администратор назначается автоматически при регистрации: если подтверждённый email совпадает с серверной настройкой admin_email, в RL-транзакции создаётся и роль admin, а профилю однократно устанавливается неизменяемый признак `is_founder_admin`. Один активный email — один профиль; разные способы входа связываются только после доказательства владения обоими, автоматическая привязка по совпадающему email запрещена.
• Пересчёт прогресса правил при тренировке слов выполняется после каждого ответа.
• Слова без активных подстановок в колодах — допустимое состояние: в составе колоды (администраторский интерфейс) они выделяются и доступны для фильтрации, из тренировки исключаются.
• Наполнение дерева правил в первой очереди — ручное редактирование администратором; задача массовой загрузки дерева будет сформулирована отдельно.
• Расширенный поведенческий anti-abuse вне первой очереди; серверный security rate limiting регистрации, входа, OAuth и email/password обязателен в P0. Мягкий дневной лимит посетителя и предупреждение о рекомендуемом интервале сохраняются.
• Административная статистика (UC-32): регистрации, авторизации, выполненные диктанты (с повторными прохождениями и счётчиками ответов), выполненные слова, созданные колоды и слова в колодах — за день/неделю/10 дней/месяц/произвольный период, с фильтрами аудитории. Системные ошибки администратор смотрит в GlitchTip, экран ошибок в RL вне первой очереди.
• История тренировок слов отдельным экраном исключена из первой очереди.

# История принятых продуктовых решений — 11.11.2026

• Better Auth поддерживает регистрационный вход через VK ID, Яндекс ID и email/password; Sber ID подключается только после подтверждения интеграции. Регистрация по email управляется серверной настройкой (по умолчанию разрешена), подтверждение email обязательно. Если письмо подтверждения не доставлено, регистрация не завершается; отдельный механизм обработки сбоя доставки вне первой очереди.
• Пароль хранится только как стойкий scrypt-хеш; допустимы 8–128 символов. Для 8–11 символов пользователь получает предупреждение и явно принимает риск через непредустановленный флажок. Отметка не хранится. В первую очередь включены восстановление и смена пароля.
• Диктант и колода по умолчанию приватны; только администратор может изменить публичность. Обычный пользователь вправе создавать и редактировать свои приватные материалы; чужие приватные объекты недоступны.
• Пользователь вправе удалить свою учётную запись только после повторной аутентификации, кроме первого администратора, удаление которого запрещено всем, включая других администраторов и фоновые процессы. Данное ограничение принято с осознанием юридического риска по 152-ФЗ; требуется правовая оценка до промышленного запуска.
• При удалении `user_profile.id` сохраняется как необратимо обезличенная запись, личная учебная история и приватные материалы удаляются, публичные диктанты/колоды/правила остаются с обычными административными правами. После полного удаления Better Auth допускается регистрация тем же email с новым профилем. Риск PII внутри публичных текстовых полей принят, автоматический поиск PII при удалении не проводится; стандартное администрирование сохраняется.
• Секретные ссылки, тренировочные сессии с квотами 2:3:1, пересчёт прогресса после каждого ответа, административная статистика UC-32 и прочие уточнения v8.2 остаются в первой очереди без изменения.

# Обязательные продуктовые принципы

Первый администратор не может быть удалён ни самостоятельно, ни другим администратором, ни через API, ни фоновым процессом; его роль admin не снимается. Самоудаление остальных пользователей входит в первую очередь.

При удалении автора сохраняется публичный учебный контент и чужая история по нему. Приватные на момент удаления диктанты уничтожаются вместе со всеми прохождениями, включая чужие; потеря соответствующего прогресса допустима и должна быть пересчитана. Приватные колоды уничтожаются, но чужие самостоятельные ответы на слова сохраняются.

В первой очереди обязательно хранить три согласия пользователя: на обработку персональных данных, маркетинговые сообщения и передачу третьим лицам. Только первое обязательно для регистрации. Сроки хранения резервных копий и заданий удаления не фиксируются без отдельного решения.

Нормативные подробности: `RL_Удаление_данных_и_проверка_FK_v9.8.md`. Юридические риски запрета удаления founder и персональных данных в сохраняемом публичном контенте требуют оценки до запуска.


## Продуктовые границы первой очереди

Первый администратор не удаляется, не обезличивается, не блокируется и не лишается роли штатными средствами (правила UC-21, UC-36, UC-37). Авторизованная регистрация требует nickname, подтверждённого email и явного согласия на обработку персональных данных. При удалении чужие прохождения приватного диктанта удаляются; публичная история остаётся согласно спецификации удаления.

Тренировка слов использует **одну подстановку на показ**; даже для слов с несколькими активными `word_placeholder` завершается после хотя бы одного правильного ответа на каждое слово (UC-15). Ограничение доступных примеров в одной тренировке принято для первой очереди реализации. Браузерный адаптивный интерфейс обязателен; установка PWA и offline-сервис отложены в P2.

В P0 входят сброс/смена пароля, подтверждение email и базовый security rate limiting; сложный anti-abuse — за пределами первой очереди. Почтовый провайдер и числовые пороги rate limiting должны быть утверждены в волне 0 до разработки зависящих от них экранов. Подробности без дублирования: `RL_Use_Cases_v9.8.md`, `RL_ER-сущности_v9.8.md`, `RL_Стек_v9.8.md`, `RL_Функциональная_декомпозиция_v9.8.md`.
