# RL — Git, CI/CD и управление окружениями

**Редакция:** 1.1  
**Дата:** 13.11.2026  
**Статус:** согласованная целевая политика Git/релизов для RL; конкретный production-хостинг и не закрытые DEC остаются в своих действующих статусах  
**База совместимости:** полный комплект RL v9.8-DEC05-r6 (исходный проверенный r1); «RL — Архитектурные решения и технический фундамент» v1.3; W0-01 v1.2  
**Ответственные:** заказчик — утверждение релиза и продуктивное развёртывание; AI-агент — реализация, проверки и отчёт в пределах поручения.

**Изменения v1.1:** ссылки согласованы с фактически приложенным базовым архивом `v9.8-DEC05-r1 / архитектура v1.2 / W0-01 v1.1` и новыми редакциями r2; уточнена безопасная процедура hotfix при расхождении `main` и реально запущенного PROD; уточнён возврат DEMO к старому digest при несовместимой схеме; закрыта редакционная ошибка в таблице рисков. Стек и права не менялись.

## 1. Назначение, область действия и приоритет

Регламент описывает, **как хранить код, тестировать изменения, выпускать неизменяемые сборки, показывать демо и развёртывать продуктивную версию**. Он не изменяет продуктовые UC, модель ER, версии стека, правила удаления, инфраструктурные решения со статусом `PROPOSED`, `VERIFY` или `BLOCKED`. При конфликте с нормативным пакетом v9.8 агент не выбирает победителя: документирует расхождение и останавливает затронутую операцию.

**Преемственность:** W0-01 создаёт локальный Git-проект с `main`, **не** GitHub remote/CI. Настоящий регламент реализуется поэтапно: CI — **W0-11**, подготовка DEMO/PROD — только в соответствующих разрешённых эксплуатационных работах после необходимых проверок. Нельзя задним числом предъявлять W0-01 требования из W0-11.

**Технологические границы:** один репозиторий, **один npm-проект** с `package-lock.json`, **один модульный монолит Next.js** и, когда он реализован, worker из того же codebase/образа. **Не monorepo/workspaces, не Turborepo, не микросервисы.** Node.js 24, Next.js 16.4.x, TypeScript 5.9, PostgreSQL 16, Prisma 7.8, Better Auth 1.7.x, pg-boss, Caddy, Mailpit (local), Postfix outbound (production), Vitest 5.0, Playwright 1.64 — только по действующему `RL_Стек_v9.8.md`. Redis/BullMQ, Traefik и PWA не вводить.

## 2. Терминология: ветка ≠ среда ≠ релиз

- **Ветка** — изменяемая ссылка Git на последовательность коммитов. Она не развёрнутая копия приложения.
- **Коммит SHA** — точная версия исходников; использовать полный SHA для трассировки.
- **Релиз** — одобренный коммит `main` (для штатного релиза) или явно утверждённый hotfix-коммит от PROD tag, аннотированный Git tag формата `vMAJOR.MINOR.PATCH`, а также созданный из него Docker image с зафиксированным `sha256` digest и протоколом проверки.
- **Артефакт** — конкретный image по digest, а не тег `latest`; web и worker работают из одной сборки, но с разными командами запуска.
- **Среда** — отдельные конфигурации, секреты, БД/файловое хранилище и (если нужно) адрес. Не требует отдельной ветки Git.
- **Promotion** — развёртывание *уже созданного* digest в следующую среду, без повторной сборки.

**Единственные постоянные ветки:** `main` (релизная линия) и `develop` (интеграция). В W0-01 допустима только `main`; при W0-11 создаётся `develop` от актуального `main`, без переписывания истории. Временные: `feature/<issue>-<slug>`, `fix/<issue>-<slug>`, `hotfix/<issue>-<slug>`. Имена slug — латиница, строчные буквы, дефисы, без секретов/ПД.

## 3. Модель сред

| Среда | Источник версии | Назначение | База/секреты | Правило допуска |
|---|---|---|---|---|
| **LOCAL/DEV** | Рабочая ветка разработчика | Разработка AI-агентом, ручная проверка | Только локальные фикстуры; Mailpit | Без production credentials/ПД |
| **TEST/CI** | Точный SHA PR и `develop`; затем release candidate | Автотесты lint/typecheck/unit/integration/E2E; временный PostgreSQL 16 | Эфемерные сервисы; синтетические данные | Удалять после job, без постоянной пользовательской истории |
| **STAGING** | Опциональный точный release candidate | Отдельная интеграционная проверка HTTPS/OAuth/Postfix/worker, если это нужно | Своё изолированное хранилище в РФ; тестовые учётные записи | **`PROPOSED` в архитектуре v1.3; не объявлять уже развёрнутым** |
| **DEMO** | По умолчанию тот же digest, что сейчас разрешён на PROD; допускается иной одобренный tag для показа будущей версии с явной меткой | Демонстрация работающего RL, без реальных данных пользователей | Отдельная БД, ключи, OAuth-приложения и файлы; только синтетические данные | Развёртывание только после одобрения владельца; отдельно от TEST |
| **PROD** | Одобренный tag + неизменяемый digest | Реальные пользователи | Реальные ключи и БД только на согласованной инфраструктуре в РФ | **Заблокировано, пока не закрыты production-зависимые решения, включая DEC-11** |

**Топология:** количество VPS, домены, способ выдачи TLS, размещение GlitchTip, registry, отдельный STAGING и выбор managed DB относятся к эксплуатационным решениям и `ADR-006/DEC-10`; регламент **не утверждает** их. На одном VPS несколько Compose-проектов допустимы только после ресурсных измерений и оценки изоляции. TEST/CI и DEMO **никогда** не подключаются к PROD-БД/volume/backup. Даже «обезличенная копия» PROD-БД по умолчанию **не допускается**: пользовательские тексты и логические связи могут позволять реидентификацию.

**DEMO из production-кода:** по команде владельца выбрать digest реально запущенного PROD, записать его в журнал, пройти проверку совместимости схемы DEMO, применить отдельные DEMO-миграции и развёрнуть этот digest. Если DEMO ранее получила более новые **несовместимые** миграции, старый PROD digest поверх неё запускать нельзя: использовать подтверждённый отдельный план восстановления/переинициализации DEMO с **синтетическими** данными, а не самовольный down-migration; при отсутствии плана операция `BLOCKED`. Нельзя переносить ни пользовательские данные, ни PROD `.env`, ни реальные SMTP-ключи. DEMO использует Mailpit или отключённую реальную доставку; иной канал допускается только после явной проверки. Демонстрационное окружение не должно инициировать реальные письма/фоновые операции над PROD.

## 4. Git-процесс

### 4.1. Обычное изменение

1. Владелец назначает задачу с UC/Fxx/ER, допусками и критериями приёмки. Агент обновляет локальный `develop` и создаёт `feature/*` либо `fix/*` от последнего согласованного `develop`.
2. Изменения строго в границах задачи. Миграции — отдельный обзор с перечислением FK, CHECK, индексов, триггеров, последовательности и тестов. Никаких секретов, real user fixtures или неоговорённых обновлений версий.
3. Агент запускает локальные доступные проверки; оформляет PR **в `develop`** с результатами, рисками, ссылкой на UC/ER, списком непройденных проверок и миграций.
4. CI запускается на PR в контексте **без секретов развёртывания**. PR принимается только при зелёном обязательном CI и решении владельца; AI-агент не одобряет собственный PR от имени владельца.
5. Мерж в `develop` после принятия. Тестируется фиксированный SHA, а не неопределённое «последнее состояние» ветки. При обнаружении дефекта — новый `fix/*`, новые CI и повторная проверка.

### 4.2. Релиз

1. Владелец определяет конкретный зелёный SHA `develop`, подтверждает объём выпуска, миграции и открытые ограничения.
2. PR `develop` → `main` проходит обязательные CI и ручное одобрение. **`main` содержит исходники кандидатного релиза, но сам по себе не означает, что они уже работают на PROD.**
3. После merge и повторного CI для точного `main` SHA владелец разрешает создание аннотированного тега `vX.Y.Z`. Исключение — утверждённый hotfix по §4.2.1. Нельзя передвигать существующие теги; новый выпуск — новый тег.
4. CI делает **одну** production-сборку Docker image для tag SHA, публикует в согласованный registry, сохраняет `repository@sha256:<digest>`, git SHA, tag, дату, тесты, список миграций и отчет. Любая неудачная сборка/проверка не становится релизом.
5. При наличии разрешённого DEMO — ручное promotion digest в DEMO и smoke. Разрешение PROD — отдельное **явное действие владельца**, плюс все production gates. Не использовать `latest`/автоматическую пересборку на PROD.
6. Порядок развёртывания определяется совместимостью миграций, работоспособностью web/worker и готовностью к восстановлению. Журнал развёртывания хранит старый и новый digest, схему и результаты smoke/rollback readiness.
7. После PROD обновить информационные данные о релизе; DEMO по отдельной команде можно привести к **ровно тому digest, который выполняется в PROD**.

### 4.2.1. Hotfix при расхождении `main` и PROD

1. Зафиксировать актуальный **запущенный** `tag + SHA + image digest` PROD. Создать `hotfix/<issue>-<slug>` **от этого SHA**, а не от `develop` и не от текущей верхушки `main`.
2. Внести только исправление, прогнать обязательный PR/CI на **самом hotfix SHA** с тестами негативного сценария. Владелец лично утверждает SHA, scope и исключение из обычного источника релизного тега.
3. Если `main` **уже содержит неопубликованные на PROD изменения**, **нельзя** выпускать hotfix сборкой с верхушки `main` и нельзя предварительно merge-ить туда изменения, перенося недоделанный код в выпуск. Создать **новый patch tag на проверенном hotfix SHA**, собрать единственный Docker image из тега, затем выполнить явное разрешение PROD deployment. Это узкое исключение из правила «tag от main».
4. **После** релиза внести исправление обратно в `main` и `develop` через отдельные PR с повторным CI; выбрать merge/cherry-pick после анализа графа и конфликтов (без force push/переписывания истории). Если в `main` не было неопубликованных изменений и он совпадал с PROD-линией, обычный PR hotfix → `main` перед тегированием допустим.
5. Обновить release ledger: связь old PROD digest → hotfix SHA/tag/digest → обратные PR. Если новая миграция несовместима со старым production-кодом, hotfix выполняется лишь после отдельного утверждённого плана; нельзя импровизировать с откатом БД.

Ни одно из этих действий не разрешает агенту самостоятельно создавать теги или развёртывать PROD. «Патч непосредственно на сервере» запрещён.

### 4.3. История и права

- Запрещены force-push и удаление общих веток/тегов без отдельного аварийного решения. PR обсуждается и сохраняет трассировку.
- `main` и `develop` защищены правилами с обязательными успешными проверками и review. Правила уточняются под фактическую подписку GitHub и число доступных ревьюеров. Для соло-владельца запретить изменение `main` агентом и использовать ручной контроль владельца; не создавать невозможное условие «обязателен второй человек», если его нет.
- Агент не получает постоянные PROD-секреты и не имеет права самостоятельно обновлять PROD. GitHub Actions permissions по минимуму; `GITHUB_TOKEN` для PR jobs — только read.
- AI-агент может выбрать имя внутренних функций и тестовых фикстур, но не версии стека, политику хранения, правовой статус, способ авторизации, бизнес-логику или архитектурное разрешение открытого DEC.

## 5. Автоматические проверки и CI

| Уровень | Запуск | Обязательные проверки | Граница |
|---|---|---|---|
| **PR-fast** | каждый PR в `develop`/`main` | `npm ci`; проверка Node 24; ESLint; Prettier check; `tsc --noEmit`/`typecheck`; Vitest; `npm run build`; проверка отсутствия секретов в diff | Команда/скрипты должны соответствовать `package.json` W0-01 |
| **Integration** | PR, merge `develop`, кандидат релиза | PostgreSQL 16, **применение `prisma migrate deploy` на чистой БД** из версионированных миграций, соответствующие FK/CHECK/триггеры/инварианты, тесты сервисов, проверка доступности API | PG-01…PG-44 добавляются по мере реализации соответствующих таблиц/UC, не имитировать полное покрытие заранее |
| **E2E/smoke** | `develop`, кандидат релиза, после DEMO/PROD deploy | Playwright Chromium, главная, health; после реализации F01 — отрицательные тесты доступа, реальные маршруты | Внешние OAuth/SMTP отдельно по утверждённому плану в российском окружении |
| **Security/build** | релизный tag | lockfile, запрет незакреплённых критических dependencies, минимальные права образа, scan уязвимостей с протоколом, отсутствие production secrets и ПД, build image, digest, provenance при доступности | Уязвимости оцениваются по фактическому риску; автоматически менять major запрещено |
| **Post-deploy** | DEMO/PROD | HTTP health, basic authenticated test разрешёнными test users, доступ к своим зависимостям, статус worker, DB migrations version, отсутствие критических ошибок, реальная версия/digest | Не делать destructive E2E и массовые тесты на PROD |

**Тесты провалены или не запускались:** статус `FAIL`/`NOT_RUN`, не `PASS`. Ошибка тестовой среды (например, недоступен браузер, registry, SMTP) — отдельный `BLOCKED`, не «зелёный» выпуск. Флейки исправлять, не отключать молча. Все pg migrations в PR проверяются и рецензируются; **`prisma db push` на staging/DEMO/PROD запрещён**.

## 6. GitHub Actions, доверие и защита

**Обязательный workflow к завершению W0-11 — только `.github/workflows/ci.yml`.** Остальные workflow в таблице ниже — целевые компоненты последующих этапов релизов и развёртывания. Они **не входят в обязательную приёмку W0-11**, не создаются и не включаются до отдельного разрешения владельца и выполнения соответствующих предпосылок (включая блокирующие DEC).

| Файл | Триггер | Результат |
|---|---|---|
| `.github/workflows/ci.yml` | PR в `develop`/`main`; push в `develop` | PR-fast, unit, чистые интеграционные тесты и smoke (по текущей готовности W0) |
| `.github/workflows/release.yml` | Защищённый tag `v*` + ручной релизный допуск | один образ, digest, manifest, отчёт и ссылка на SHA |
| `.github/workflows/deploy-demo.yml` | `workflow_dispatch` с **digest** и явным подтверждением | DEMO, smoke, журнал; включается только после утверждения DEMO топологии |
| `.github/workflows/deploy-prod.yml` | `workflow_dispatch` c digest из выпуска и отдельным разрешением | PROD, gated migration/deploy/smoke/rollback readiness; **не включать пока DEC-11 BLOCKED** |

**Обязательные практики безопасности:** использовать проверенные версии `actions/*`, предпочтительно pin по полному commit SHA; `permissions` минимальны отдельно на job, `pull_request_target` с исполнением непроверенного PR-кода запрещён. PR из форков не получают production secrets; не печатать секреты даже в debug. Не выполнять пользовательский shell из названия PR/ветки и не подставлять непроверенные inputs в командную строку. При необходимости registry push у конкретного job разрешить `packages: write`, не всему workflow. Для deployment secrets — отдельные environment/host permissions, отдельные ключи для DEMO и PROD, минимальный scope, ротация/ревокация.

**Особое ограничение GitHub:** для приватных репозиториев доступность `Environments`, `required reviewers` и связанных protections зависит от тарифа. На GitHub Free/Pro/Team требование `required reviewers` для environment доступно только для публичных репозиториев (по документации на 13.11.2026); поэтому нельзя описывать его как гарантированное для частного репозитория. При отсутствии нативного reviewer gate обязательны разделённые учетные данные/права на хосте и явная ручная команда владельца с журналом. Сама `workflow_dispatch` не является полноценным подтверждением вторым лицом.

**География:** общедоступный GitHub-hosted runner может исполняться вне РФ. В CI — **только синтетические тестовые данные и токены с минимальными правами**. Не отправлять реальные персональные данные, production дампы, логи, секреты и вложения в GitHub Actions/artifacts. Если для интеграции требуются настоящие данные/инфраструктура в РФ — отдельное согласование потока данных и изолированный российский runner/хост; self-hosted runner не должен исполнять недоверенный PR-код. Сетевую доступность GitHub/GHCR из РФ проверять фактически; при невозможности использовать согласованный российский registry/зеркало, **не пересобирать** релизный образ при копировании — сохранять содержимое и проверять digest/контрольную сумму.

## 7. Секреты, конфигурация и build-once

**Отдельные пространства:** `DATABASE_URL`, Better Auth secret/base URL, OAuth secrets/callbacks, Postfix/SMTP, ключи cookies, S3 credentials, мониторинг/GlitchTip и signing keys — различаются между DEMO и PROD. `.env.example` содержит лишь названия/назначения. Секреты не попадают в Git, image layer, build args, логи, screenshot, тестовые артефакты; контроль на CI и при публикации.

**Критический нюанс Next.js:** `NEXT_PUBLIC_*`, если прямо использованы в client bundle, встраиваются при сборке; если DEMO/PROD должны запускать **один digest**, их публичная конфигурация должна быть одинаковой или получаться **в runtime** разрешённым механизмом (например, относительные URL, серверный endpoint с допустимыми публичными значениями). Не передавать секреты в `NEXT_PUBLIC_*`; нельзя обещать одинаковый digest при заведомо разных build-time публичных URL. `BETTER_AUTH_URL`/trusted origins/callback относятся к runtime и отдельно тестируются после deploy. Отказ от build-once требует отдельного утверждённого исключения с указанием причины и контроля эквивалентности кода.

## 8. Миграции, резервные копии, rollback

1. До выпуска каждой миграции определить обратную совместимость с предыдущими web/worker, длительность, риск блокировки, поведение незавершённых pg-boss задач и orphan FK. Любая SQL-миграция — часть PR, без ручной правки на PROD.
2. В DEMO/STAGING миграции исполняет отдельный одноразовый `migrate`-процесс с DDL-ролью после backup (где обоснован) и до переключения web/worker. Runtime роли DDL не предоставлять. На PROD — только после gate и обязательного backup/restore протокола.
3. Предпочитать миграции *expand → migrate → contract*: новая схема временно совместима с прежним образом до подтверждённого перехода. Не удалять колонки/данные во время релиза без плана.
4. Rollback приложения — возврат на **записанный старый digest**, только если новая схема допускает запуск старого кода. Сам по себе `docker compose up` старого образа **не откатывает БД**.
5. Необратимая миграция → отдельный план roll-forward/восстановления, оценка потери данных, контрольное окно и явное разрешение владельца. Запрет молча делать down SQL или восстанавливать PROD из backup.
6. До разрешения PROD должны быть закрыты DEC-11 (включая юридические сроки хранения/удаления), подтверждено тестовое восстановление, права доступа, мониторинг, инцидентный порядок и защита РФ-хранения.

**Протокол релиза и деплоя** хранит: tag; SHA исходников; digest; предыдущий digest; версию схемы/список миграций; источники тестовых evidence; имена целевых сред (без секретов); решение/время/ответственного; результат backup/restore gate; health/smoke; произошедшие ошибки и действие rollback/roll-forward.

```text

│   │   ├── ci.yml
│   │   ├── release.yml
│   │   ├── deploy-demo.yml   # после решения инфраструктуры DEMO
│   │   └── deploy-prod.yml   # не активировать до production-gates
│   └── dependabot.yml        # при согласованном автоматическом обновлении зависимостей

│   ├── architecture/          # v1.3 + настоящее дополнение
│   ├── decisions/             # только реально существующие ADR; будущие решения об окружениях оформляются после утверждения
│   ├── release/               # протоколы утверждённых выпусков
│   └── handover/              # отчёты AI-агентов по W0/спринтам
├── src/                       # Next.js и доменные модули из архитектуры v1.3
```

Не создавать пустые каталоги, фальшивые Dockerfiles/сервисы и файлы `deploy-prod.yml`, которые можно случайно запустить до утверждения инфраструктуры. Документ описывает **целевое состояние**, а не перечень файлов, которые надо создать немедленно.

## 10. Приёмка Git/CI-CD

**Этап W0-11 (обязателен для `WAVE0_ACCEPTED`):**

- [ ] Есть доступный GitHub remote или документированный внешний блокер; `main` и `develop` созданы без потери истории; настроены доступные правила защиты.
- [ ] PR из feature в `develop` запускает реальный CI без production секретов; ошибки тестов дают красный статус.
- [ ] CI проверяет npm lockfile, TS, lint, unit, сборку, PostgreSQL migrations и реализованные integration/smoke.
- [ ] Показан чистый тестовый прогон, лог с SHA, результатами и перечнем **не реализованных/не запускавшихся** проверок.
- [ ] AGENTS.md содержит границы AI-агента по Git; ни агент, ни PR job не могут выполнять PROD deploy.
- [ ] Существующие критерии архитектуры v1.3 остаются в силе; W0-11 не объявляет PROD готовым.

**Этап DEMO (после отдельного допуска):** тестовая БД/файлы/SMTP независимы, нет ПД; вручную указан digest; migrations и smoke успешны; демонстрируется фактический digest и дата обновления; задокументированы ограничения.

**Этап PROD (после всех gate):** владелец утвердил tag/digest и план миграций; DEC-11 и прочие применимые блокеры закрыты; backup **проверен восстановлением**; секреты/данные в РФ; задокументированы rollback/roll-forward; post-deploy smoke успешен. При любом провале — `NOT_RELEASED` или `PARTIAL`, но не `PROD_READY`.
