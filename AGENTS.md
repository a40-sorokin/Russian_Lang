# AGENTS.md — правила работы AI-агентов над проектом RL

**Базовая редакция требований:** RL v9.8 с согласованной поправкой почтового канала DEC-05 · **Уточнение для волны 0:** 13.11.2026; архитектура v1.3, DEC-05/ADR-004 и регламент Git/CI/CD v1.1. **Назначение:** инструкция для разработки и проверки кода. Этот файл **не является источником новых продуктовых требований**. При расхождении с нормативными документами остановить соответствующую работу и запросить решение заказчика.

## 1. Нормативные источники и порядок работы

- `RL_Общая_концепция_v9.8.md` — цели, границы первой очереди и продуктовые принципы.
- `RL_Use_Cases_v9.8.md` — поведение, права, пользовательские сценарии и критерии приёмки.
- `RL_ER-сущности_v9.8.md` — таблицы, поля, типы, FK, CHECK, алгоритмы расчётов и инварианты.
- `RL_Стек_v9.8.md` — технологии, версии, интеграционные и эксплуатационные ограничения.
- `RL_Функциональная_декомпозиция_v9.8.md` — модули, зависимости, приоритеты и волны реализации.
- `RL_Удаление_данных_и_проверка_FK_v9.8.md` — обязательная детализация UC-36/37, порядок удаления и контроль FK.
- `RL_FK_audit_PostgreSQL_v9.8.sql` — **инструмент аудита**, а не миграция и не доказательство прохождения интеграционных тестов.
- `RL_История_изменений_v9.8.md` и `RL_Контроль_изменений_ER_v9.8.md` — справочные документы, **не нормативные**.
- `RL_Git_CI-CD_и_окружения_v1.1.md` — рабочая политика Git, CI, релизов, TEST/DEMO/PROD; не меняет UC/ER/стек.
- `RL_W0-01_Создание_репозитория_и_каркаса_приложения_v1.2.md` и `RL_W0-11_GitHub_CI_ТЗ_v1.1.md` — точные границы соответствующих задач; не смешивать W0-01 с W0-11.

**Дополнительный технический источник для волны 0 (согласован заказчиком):** `RL-Архитектурные решения и технический фундамент v1.3.md`. Он определяет структуру реализации, технические гипотезы, план спайков и критерии завершения волны 0. **Не переопределяет** `RL_Use_Cases_v9.8.md`, `RL_ER-сущности_v9.8.md`, `RL_Стек_v9.8.md` и другие нормативные документы v9.8. `FIXED` цитирует утверждённое требование; `PROPOSED`, `VERIFY`, `BLOCKED` — **не утверждённые отдельные решения**, даже если сам документ принят как рабочая основа. Для DEC/ADR использовать единый маппинг из §12.1 архитектурного документа: `DEC` — статус конкретного вопроса, `ADR` — артефакт его фиксации. Один ADR может содержать несколько DEC; согласование ADR без доказательств/решений по DEC не означает закрытия DEC.

Не использовать исторические формулировки как замену действующим требованиям. При конфликте между нормативными источниками **не выбирать самостоятельно**: зафиксировать оба фрагмента, последствия, предложить минимальное решение и получить подтверждение. Нельзя скрывать проблему за предположением «стандартное поведение библиотеки».

**Правило применения архитектуры v1.3:** она согласована с текущей RL v9.8 и принятым почтовым DEC-05. В версии исходного пакета, где раздел стека ещё содержит выбор Unisender/Яндекс 360, единственным допустимым переходным основанием является утверждённая поправка DEC-05 и актуальный `ADR-004`; при подготовке обновлённого пакета это противоречие должно быть устранено в самом `RL_Стек_v9.8.md`. Другие положения нормативной v9.8 нельзя изменять архитектурным документом без одобрения заказчика.

## 2. Перед началом задачи

1. Определить UC, модуль Fxx, затронутые сущности, права и тесты. Составить короткую матрицу «требование → реализация → проверка».
2. Проверить зависимости волны и решения со статусом `BLOCKED`. **Почтовая технология уже утверждена**: `DEC-05=FIXED` — Postfix outbound на VPS РФ, Mailpit локально; без Dovecot/IMAP/POP3 и входящей почты. **Доставка ещё не подтверждена**: `MAIL_DELIVERY_VERIFICATION=VERIFY` до испытаний W0-08. Числовые пороги security rate limiting (`DEC-06`) остаются `BLOCKED` и требуют утверждения заказчика.
3. Проверить реальные API, версии и совместимость установленных пакетов; если контракт библиотеки не подтверждён, сначала сделать минимальный интеграционный прототип. Не придумывать методы Better Auth, Prisma или pg-boss.
4. Допускается самостоятельно выбирать имена внутренних функций, разбиение на файлы, локальные тестовые фикстуры и простые детали реализации, **если** это не меняет права, схему, алгоритм, безопасность, интерфейс API и поведение UC. Такие решения кратко документировать.

## 3. Технологические ограничения

Использовать версии и выбор компонентов **только из `RL_Стек_v9.8.md`**. Не добавлять Redis, BullMQ, новый ORM, отдельный сервис или альтернативный auth-фреймворк без обоснования и согласования. Писать понятный TypeScript в strict-режиме; не усложнять код ради несущественной оптимизации. Сервер является источником истины по авторизации, проверке прав, состоянию тренировки и изменениям БД.

## 4. PostgreSQL, Prisma и миграции

- Схема в ER нормативна. Изменение типов, NULL/NOT NULL, FK, `ON DELETE`, индексов, CHECK, триггеров и состояний данных требует явного основания и проверки во всех затронутых документах.
- Prisma-схема не заменяет SQL-ограничения PostgreSQL. Если ограничение не поддерживается Prisma декларативно, реализовать его в SQL-миграции и проверить после применения.
- Не заменять массово `RESTRICT` на `CASCADE` ради упрощения удаления. Удаление выполнять по утверждённому порядку, с тестами Dxx/PG-xx.
- Не заявлять атомарность между Better Auth и RL без подтверждённой общей транзакционной границы. Для двухфазного удаления использовать утверждённые состояния, повторные попытки и восстановление.
- Для `dictation_record.created_by` обеспечить `NOT NULL`, `ON DELETE RESTRICT` и неизменяемость, в том числе на уровне БД. Founder защищён от удаления, обезличивания, блокировки и снятия роли штатными операциями.
- При изменении ER готовить дифф по полям/типам/nullability/FK и отмечать каждое намеренное изменение; случайные текстовые замены запрещены.

## 5. pg-boss: фоновые задачи без скрытых допущений

- Источник истины по удалению — `user_deletion_jobs`, а не наличие записи в очереди. После рестарта выполнять recovery polling незавершённых заданий, не теряя повторы и ручной разбор исчерпанных попыток.
- **Не считать вызов `send()` доказательством постановки задания.** Проверить по фактическому контракту установленной версии, что возвращено (в том числе возможный `null` при политике уникальности/дедупликации), и обеспечить безопасное восстановление, если задача не поставлена.
- **Не комбинировать `singletonKey` и `singletonSeconds` по догадке.** Их взаимодействие и последствия для повторов/дедупликации проверить в документации и интеграционном тесте установленной версии `pg-boss` до использования. Защита от повторной бизнес-операции должна обеспечиваться состоянием БД и идемпотентностью обработчика, а не только параметрами очереди.
- **Не предполагать возможность произвольно менять policy существующей очереди.** Политику очереди закреплять при её создании; изменение выполнять отдельной проверенной процедурой/миграцией с оценкой действующих заданий. Если API/семантика не подтверждены — остановить работу и запросить решение.
- В обработчике предусмотреть безопасный повтор после сбоя в любой точке; успех фиксировать только после проверки целевого состояния.

## 6. Безопасность и персональные данные

Все операции с правами проверять на сервере. Не допускать обхода founder-ограничений через другой UC, фоновые задачи или прямое изменение API. При блокировке немедленно закрывать доступ проверкой `is_locked` и обязательно отзывать сессии Better Auth с повтором при сбое. Согласия и порядок обезличивания брать только из UC/ER/спецификации удаления. Не логировать пароли, токены, персональные данные и секретные ссылки. Требование размещения данных в РФ распространяется также на почту, телеметрию, резервные копии и интеграции — до включения внешнего сервиса проверять фактические потоки данных. **Почта:** production — собственный Postfix Docker на VPS РФ, исходящие письма, без входящей почты; local — Mailpit. Не устанавливать Dovecot/IMAP/POP3 или Unisender/Яндекс 360 без нового согласованного DEC. Не считать `DEC-05=FIXED` доказательством доставки: реальные письма, ограничения VPS/порта 25, SPF/DKIM/DMARC/PTR и наблюдаемость недоставок проходят W0-08.

## 7. Тесты и приёмка

- Для каждого UC: позитивные, негативные, проверки прав, конкурентные операции и повторы запросов там, где они существенны.
- Для БД: применить миграции на тестовой PostgreSQL 16, выполнить SQL-аудит FK и интеграционные тесты PG-01…PG-44. **Наличие текстового описания PG-теста не означает, что он выполнен.**
- Для UC-15 проверить несколько `word_placeholder`, снимок, идемпотентность ответов, порядок выбора и завершение по `ever_correct`.
- Для UC-36/37 проверить сохранение публичного контента, удаление приватного, невозможность удаления founder, повторные фоновые задачи и аварийное восстановление.
- Для дерева правил проверить запрет циклов при изменении и диагностику повреждённых данных.
- Перед сдачей запустить применимые unit/integration/E2E тесты, линтер и проверку типов; сообщить, какие проверки реально запускались и какие остались непроверенными.

## 8. Формат результата агента

Указать: выполненные UC/Fxx, изменённые файлы и миграции, реализованные инварианты, проведённые тесты с результатами, открытые риски и блокирующие решения. Не выдавать частичную реализацию или непроверенную миграцию за завершённую. При конфликте спецификаций не продолжать опасную операцию до решения заказчика.

## 9. Git, GitHub, CI/CD, среды и управление релизами

**Источник:** `RL_Git_CI-CD_и_окружения_v1.1.md`. Его правила действуют в рамках принятых этапов; он не закрывает технические `DEC-10/12`, юридический `DEC-11` или `DEC-06`. Утверждённый процесс Git не является разрешением на развёртывание приложения.

- **W0-01:** создать только локальный Git-проект с `main`, сохранить исходные документы из **полного текущего архива** по `MANIFEST_v9.8-DEC05-r6.json`. Не создавать remote, `develop`, workflows или deployment credentials в рамках W0-01.
- **W0-11:** при санкционированном доступе настроить `develop` от `main`, PR и CI; защищать `main` и `develop` реальными доступными правилами GitHub. Защита, недоступная на фактическом тарифе, не считается настроенной; отразить ограничение и ручной контроль.
- **Обычная задача:** отдельная `feature/*` или `fix/*` от `develop`, PR в `develop`, фактические проверки, ревью владельца. Ни агент, ни CI не должны самоодобрять PR от лица владельца или обходить правила защиты.
- **Релиз:** Git tag, commit SHA и единственный Docker image по digest; DEMO/PROD получают согласованный digest без пересборки. Теги не передвигать; `main` **не является автоматически запущенным PROD**. Для hotfix, когда `main` уже опережает PROD, применять исключение из регламента с отдельным разрешением владельца, чтобы не выпустить незавершённый код.
- **DEMO:** отдельные синтетические данные, секреты, БД и файловое хранилище; PROD backup/PII/SMTP credentials не копировать. Синхронизация с PROD означает перенос **версии кода**, а не данных.
- **PROD:** AI-агент не вправе запускать deployment, изменять секреты или рабочую БД без прямого отдельного решения заказчика. Пока `DEC-11=BLOCKED`, продуктивное развёртывание с реальными данными запрещено. Развёртывание и миграции требуют проверенного backup/restore, возможности rollback/roll-forward и фактических smoke-тестов.
- **Безопасность CI:** недоверенные PR не получают production secrets и write permissions; никакие реальные ПД/бэкапы/секреты не передаются в зарубежные runners/artifacts. Тесты запускаются на синтетических данных; результаты `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED` отражают факты, а не планы.
- **Самостоятельные решения агента:** только названия технических вспомогательных файлов, локальная организация шагов CI и тестовые фикстуры без изменения безопасности/доступов/релизной модели. Registry, адреса, топология DEMO, PROD и production-gates согласуются владельцем отдельно.

**Примечание о версии комплекта (r6):** при выполнении W0-01 использовать файл `MANIFEST*.json` **из того же текущего полного ZIP**, что и копируемые документы; `r6` — актуальная на момент выпуска конкретизация. Нельзя проверять файлы нового архива по историческому манифесту r1–r5.
