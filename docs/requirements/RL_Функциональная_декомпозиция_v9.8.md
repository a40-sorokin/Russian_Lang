# RL — функциональная декомпозиция первой очереди

**Версия:** 9.8 · **Дата:** 12.11.2026 · **Статус:** утверждённая функциональная декомпозиция RL v9.8; изменения редакции носят только редакционный характер.

## 1. Назначение и правила использования

Документ разбивает первую очередь RL на функциональные подсистемы, модули и реализуемые функции. Он предназначен для планирования задач AI-агентов, распределения ответственности, определения зависимостей и проверки полноты покрытия Use Cases. **Это не замена** нормативным сценариям `RL_Use_Cases_v9.8.md` и модели `RL_ER-сущности_v9.8.md`: алгоритмы, поля, права, ограничения, транзакции и критерии приёмки берутся из них. При противоречии агент останавливается и запрашивает решение, а не выбирает самостоятельно.

**Источники:** `RL_Use_Cases_v9.8.md`; `RL_ER-сущности_v9.8.md`; `RL_Стек_v9.8.md`; `RL_Общая_концепция_v9.8.md`. Все действующие материалы сверяются с комплектом v9.8; при расхождении агент сообщает о нём заказчику и не придумывает бизнес-правило.

**Ключевые ограничения первой очереди:** Better Auth вместо Auth.js; регистрация по email с паролем и OAuth, управление восстановлением/сменой пароля и связями аккаунтов; двухфазное удаление Better Auth и необратимое обезличивание профиля; самостоятельное удаление с повторной аутентификацией кроме первого администратора; приватность диктантов по умолчанию, перевод диктантов и колод в публичный режим только администратором; автор-студент может публиковать версии собственных приватных диктантов.

**Приоритеты:** P0 — обязательный базовый пользовательский цикл; P1 — функции той же первой очереди, выполняемые следующим этапом. P2 — вне объёма. **Не путать** функциональную декомпозицию с физическим делением на микросервисы: для первой очереди достаточно модульного приложения Next.js с PostgreSQL.

Сбой отправки подтверждения регистрации не завершает регистрацию, специальное восстановление доставки вне первой очереди | Better Auth `account/verification/session`, почтовый шлюз РФ | 38 |
| F01.9 Смена пароля | Проверка текущего пароля, новый пароль 8–128 символов; подтверждение рисков 8–11 символов; отзыв остальных сессий; хеш `scrypt`, никогда не сохранять исходный пароль | Better Auth `account/session` | 39 |
| F01.10 Связь способов входа | Привязка VK ID/Яндекс ID и email/password к существующему аккаунту только при подтверждении владения обоими методами. Запрет неявного объединения по email, чужой внешней identity и отвязки последнего доступного метода входа | Better Auth `account`, `user_profile` | 40 |
| F01.11 Настройки регистрации | Только admin управляет `email_registration_enabled`, по умолчанию true. Отключает новые email-регистрации, но не вход, смену/сброс пароля. Подключение OAuth-провайдеров требует корректной конфигурации и тестирования | `service_setting`, конфигурация Better Auth | 02, 20–22 |

**Граница:** PostgreSQL 16 и Prisma 7.8, логические схемы `auth` (Better Auth) и `public` (RL). Нельзя считать callbacks Better Auth доказательством общей транзакции. F01.1 создаёт профиль и роль одной RL-транзакцией после подтверждения email; при отдельных транзакциях авторизации и RL действует компенсация/блокировка незавершённого профиля. F01.6/F01.7 выполняют **двухфазную** операцию: атомарное удаление личных данных RL, обезличивание профиля и создание `user_deletion_jobs`; после коммита — идемпотентное удаление Better Auth с повторными попытками. Не показывать полный успех до фазы 2. Строго проверить способ удаления identity через серверный API адаптера Better Auth до реализации. Публичное авторство не переназначать.

**Отрицательные тесты F01.6/F01.7:** founder нельзя удалить через UC-36/37, прямой HTTP API, штатный worker и UPDATE/DELETE рабочей ролью PostgreSQL; все попытки не создают `user_deletion_jobs`.

**Готовность:** регистрация не даёт доступа незавершённому профилю; заблокированный и обезличенный пользователь не выполняет защищённых операций; права не зависят от переданного клиентом `user_id`. Удаление данных RL атомарно, очистка Better Auth асинхронно доводится до завершения. Первый администратор не может быть удалён или заблокирован никаким штатным способом, риск несоответствия 152-ФЗ зафиксирован и требует юридического решения до промышленного запуска.

| F03.4 Нормализация | Удаление `/` **только вне подстановок**; подсчёт удалений; уведомление редактора; повторная серверная проверка | Текст версии | 26 |
| F03.5 Валидация | Ограничения числа подстановок/альтернатив и длины вариантов; проверка ссылок и допустимости публикации | `rule`, `word_placeholder`, версии | 25, 26, 34 |

| F03.7 Предпросмотр | Отображение диктанта после той же нормализации и тем же парсером, что используются при публикации/прохождении | Версия и задания | 26 |
| F03.8 Политика публикации | Серверная проверка изменения `is_public` только администратором; БД default false; приватные версии не выдавать через публичные списки, API или произвольный URL. **Особое правило `/`:** внутри `{о/а}` — нормативный разделитель альтернатив, вне подстановки — удаляемый запрещённый символ. Удаление может склеить соседние фрагменты текста; это сознательно принятое поведение. Уведомление показывает количество удалённых символов. Нельзя применять глобальную замену `/` ко всему тексту.

**Готовность:** редактор, предпросмотр, публикация и прохождение одинаково интерпретируют текст; невозможна публикация с невалидной ссылкой или пересекающимся периодом; история старых версий не меняется.

## 17. Сквозные критерии приёмки первой очереди

1. Каждый UC-01…UC-40 имеет владельца в матрице, проверяемые сценарии, тесты и права доступа. Отсутствующие номера UC не добавляются произвольно. История добавления сценариев фиксируется только в `RL_История_изменений_v9.8.md`.
2. Текст диктанта содержит `/` только как разделитель альтернатив внутри корректных подстановок; вне них символ удаляется с уведомлением.
3. Для колоды соблюдаются квоты выбора 2:3:1 **при наличии категорий**; недостаток категорий не блокирует тренировку.
4. Состояние последнего ответа и факт хотя бы одного правильного ответа — независимые признаки; после достижения `ever_correct=true` для всех слов тренировка автоматически завершается.
5. Завершённая тренировка предлагает другую колоду или диктанты; новая тренировка той же колоды начинается с чистых состояний; история ответов сохраняется.
6. Дублированные/конкурентные запросы не создают двойных `word_done` и не нарушают последовательность карточек.
7. RL-профиль и роль создаются атомарно только в рамках транзакции RL; для Better Auth не обещается общая транзакция без подтверждённой поддержки адаптера. Удаление — две фазы: транзакционная очистка RL с обезличиванием профиля и задачей, затем идемпотентная очистка Better Auth с повторными попытками.
8. Расчёт прогресса учитывает четырёхмесячное окно, иерархию правил и независимость предпочтений.
9. Исторические результаты и ссылки на них не изменяются задним числом при публикации новой версии диктанта.
10. Все защищённые операции проверяют права на сервере; данные хранятся в РФ; выполняются резервное копирование и проверка восстановления.
11. При регистрации подтверждённый email уникален для активного профиля; разные способы входа могут быть привязаны к одной identity только после доказательства владения обоими. Совпадение email само по себе не инициирует связывание. После удаления прежний email может использоваться новым профилем с новым `user_profile.id`.
12. Первый администратор получает роль по `admin_email` из серверной настройки при регистрации после подтверждения email. Неизменяемый `is_founder_admin=true` назначается ровно одному профилю при бутстрапе, не вычисляется по времени/ID; абсолютный запрет удаления, блокировки и снятия роли действует независимо от числа других администраторов. Юридический риск по 152-ФЗ подлежит оценке до запуска.
13. Каждый ответ тренировки запускает пересчёт прогресса; сбой пересчёта не отменяет ответ.
14. Слова без активных подстановок выделяются и фильтруются в администраторском составе колоды и исключаются из снимка тренировки.
15. Регистрация по email разрешена по умолчанию и может отключаться администратором без запрета существующего входа, смены и восстановления пароля. Email обязательно подтверждается; недоставленное письмо не завершает регистрацию. Пароль 8–128 символов, 8–11 — предупреждение и отдельное явное согласие без хранения; хранить только штатный защищённый scrypt-хеш.
16. До самоудаления пользователь повторно аутентифицируется. Первому администратору самоудаление запрещено. Все личные попытки, прогресс, приватные материалы и секретные ссылки удаляются; публичные материалы и ссылки на обезличенный профиль остаются, без отдельной передачи прав. Идентифицирующие строки внутри публикаций автоматически не анализируются — принятый риск, но администратор может исправлять их обычными средствами.
17. `dictation_record.is_public=false` и `deck.is_public=false` по умолчанию на уровне БД; только admin меняет публичность. Все защищённые API, списки и версии проверяют доступ сервером.

## 18. За рамками первой очереди

### 18.1. Исключения из первой очереди с учётом утверждённых Use Cases

Без отдельного согласования **не реализовывать**:

- автоматические рекомендации следующего диктанта или упражнения;
- challenges и соревнования, реферальную систему, кабинеты преподавателей/тьюторов;
- мобильное приложение (его будущее API учитывается в архитектуре);
- сложные персональные учебные траектории;
- черновики версий диктантов и отдельный cron для переключения их версий;
- дополнительные scope секретных ссылок (в первой очереди только `all`);
- полный экспорт данных пользователя и переназначение владения публичным контентом при удалении автора (самоудаление, сброс и смена пароля включены в UC-37–39);
- email-уведомления о разблокировке, публикации и истечении ссылок;
- поиск по правилам и диктантам (индексы БД учесть), подписки на публичные колоды и историю тренда прогресса.

**Anti-abuse / rate limiting:** продвинутые поведенческие антиабьюз-механизмы вне первой очереди. Однако минимальное серверное ограничение частоты входа, восстановления пароля и других чувствительных Better Auth endpoint обязательно как мера безопасности. Также остаются мягкий дневной лимит посетителя N (UC-04) и неблокирующее предупреждение M часов.

### 18.2. Дополнительные ограничения объёма декомпозиции

- Платежи и коммерческие подписки, сложные рекомендательные алгоритмы — не описаны нормативными UC первой очереди; не добавлять без отдельного решения. Самостоятельный экран полной истории ответов по словам исключён решением от 10.11.2026 (бывший F06.3 удалён из декомпозиции).
- Полноценный юридический документооборот и сопровождение не входят в первую очередь; три флага согласий, их сбор и техническая защита данных обязательны. Историческое решение v8.1 об исключении согласий отменено.

## 19. Вопросы, которые необходимо проверить до постановки задач AI-агентам

Это не новые функциональные требования, а контроль реализуемости уже согласованных решений.

1. **Better Auth/Prisma:** подтвердить точные совместимые версии Better Auth, Next.js 16 и Prisma 7.8, схему таблиц и миграции, практическую транзакционную границу и доступный серверный способ идемпотентного удаления Better Auth identity. Для F01.7 подтвердить повторную OAuth-аутентификацию того же провайдерского пользователя. Для фоновых повторов использовать pg-boss. Выполняется в волне 0 до массовой разработки.
2. **Идемпотентность тренировки:** ER задаёт `word_done.training_session_id`, `word_done.answer_request_id` и частичный UNIQUE `(training_session_id, answer_request_id)` для строк, где оба поля не NULL. При реализации проверить наличие этих полей и соответствующего частичного уникального индекса в миграциях PostgreSQL. При расхождении остановить реализацию и согласовать исправление; самостоятельно изменять требование нельзя.
3. **Точность алгоритма 2:3:1:** реализовать тесты на пустые категории, невозможность немедленного повтора, завершение на 1–5-м показе блока, повторную ошибку после правильного ответа, исключение слов без активных подстановок из снимка и запуск пересчёта после каждого ответа.
4. **Нормализация текста:** убедиться, что редактор и сервер используют один парсер и что `/` внутри синтаксически некорректной подстановки не скрывается от диагностики.
5. **UC-32 — закрыт 10.11.2026:** специфицирована административная статистика (6 показателей, периоды, фильтры аудитории; журнал входов `user_signin_log`); системные ошибки просматриваются в GlitchTip — экран ошибок в RL вне первой очереди. Реализация F09.7 разблокирована; при реализации сверить производительность агрегирующих запросов (индексы по `created_at`).
6. **История слов — закрыто 10.11.2026:** F06.3 исключён из первой очереди; `word_done` сохраняется, ответы слов видны в отчётах конкретных прохождений (F06.1) и в ходе тренировки (F07).
7. **«Просмотр использования» word_placeholder — закрыт 10.11.2026:** производная таблица `dictation_version_word_placeholder` по образцу `dictation_version_rule`, заполняется и пересобирается вместе с ней; `word_done` — справочный счётчик выполнений, не источник «использования».

Решениями от 10.11.2026 закрыты: бутстрап администратора (`admin_email`), гранулярность пересчёта прогресса (после каждого ответа), слова без активных подстановок, ручное наполнение дерева правил, источник «просмотра использования» word_placeholder, UC-32 (административная статистика), история слов (исключена из первой очереди). Решение v8.2 об автоматическом связывании аккаунтов по подтверждённому email **заменено** правилом v9.5 о проверке владения обоими способами входа.

**История редакций 8.x–9.x перенесена в** `RL_История_изменений_v9.8.md`. Исторические решения не переопределяют требования действующей редакции.
