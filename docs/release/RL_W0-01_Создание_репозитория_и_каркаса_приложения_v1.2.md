## 1. Назначение задания

Создать **один Git-репозиторий с минимальным, реально работающим каркасом веб-приложения RL**, который можно запустить на локальном компьютере и на котором следующие AI-агенты смогут последовательно выполнять W0-02…W0-11.

В результате **W0-01** должны существовать:

1. Git-репозиторий с корректными исключениями, исходниками, инструкциями и исходным коммитом.
2. Одно приложение Next.js App Router на Node.js 24 и TypeScript 5.9 (`strict: true`).
3. Адаптивная стартовая страница на русском языке и минимальный HTTP liveness endpoint.
4. Воспроизводимые версии пакетов и **один** `package-lock.json`.
5. Рабочие команды `dev`, `build`, `start`, `lint`, `typecheck`, `format:check`, `test:unit`, `test:e2e` и совокупная `check`.
6. Минимальные тесты и фактический протокол их выполнения.
7. Корневой `AGENTS.md` и комплект утверждённых проектных документов **без редактирования их содержания**.
8. Понятный `README.md`, позволяющий новому разработчику повторить запуск без неописанных ручных шагов.

**Ключевая граница:** работающий каркас **не означает** работающую авторизацию, подключённую БД, бизнес-функции, production-развёртывание или завершённую волну W0.

**При конфликте:** не выбирать одну из несовместимых норм самостоятельно. Описать оба требования с названием файла и разделом, последствия и минимальный вариант разрешения. Остановить **только затронутую часть** работ. Для несвязанных операций продолжать выполнение. Не объявлять `PROPOSED`, `VERIFY` или `BLOCKED` решения автоматически утверждёнными.

### 2.1. Доступность исходного пакета

- Использовать **полный актуальный утверждённый комплект** RL v9.8 с архитектурой v1.3 и утверждённым изменением DEC-05. Предыдущий полный пакет `RL v9.8-DEC05-r1 / W0-01 v1.1` — лишь исторический источник; при исполнении W0-01 использовать **текущий полный архив `RL_Docs_v9.8-r6.zip`** и находящийся **в этом же архиве** `MANIFEST_v9.8-DEC05-r6.json`. Проверять SHA-256 до копирования. В последующих выпусках применять манифест из фактически предоставленного актуального архива, а не фиксированное имя из исторического ТЗ. Не комбинировать документы из несовпадающих архивов.
- Не переписывать документы «по памяти», не реконструировать их из более старых версий и не создавать имитации актуальных файлов.
- При отсутствии полного пакета можно создать код каркаса, **но нельзя закрывать пункт о передаче нормативных документов**. Отметить `BLOCKED: SOURCE_DOCUMENTS_MISSING` в отчёте; не создавать фиктивные файлы.
- **Комплектность обязательна:** скопировать **каждый** файл, перечисленный в актуальном `MANIFEST*.json` (основные нормативные, дополнительные нормативные, проверочный SQL, история/контроль ER и документация по архитектуре); наличие и SHA-256 сверить с `files[].sha256` и `files[].bytes` манифеста. Сам манифест также включить в репозиторий и сохранить без изменений. Не полагаться только на число файлов: приёмка проверяет список манифеста. При ошибке контрольной суммы/отсутствии любого файла — `BLOCKED: SOURCE_DOCUMENTS_INCOMPLETE`; **W0-01 не принимается**. Не генерировать недостающие тексты по памяти. Копии должны совпадать с исходниками побайтово, кроме явно одобренной корректировки состава при новой редакции комплекта.

## 3. Границы полномочий AI-агента

### 3.1. Агент может решить самостоятельно

- Названия небольших внутренних функций, test fixtures и локальных констант.
- Технически нейтральное размещение **небольших** вспомогательных файлов внутри согласованной структуры.
- Конкретный patch **в пределах нормативно разрешённой линии**, если он доступен в npm, совместим и полностью зафиксирован в lockfile. Исключение: смена линии версии не разрешена.
- Небольшие косметические детали **временной** стартовой страницы, не устанавливающие продуктовый дизайн.
- Команды вспомогательных скриптов в рамках принятого `npm`, если они дают те же проверяемые результаты.

Все такие решения должны быть простыми, понятными разработчику уровня middle и не требовать новых инструментов без реальной необходимости.

### 3.2. Агент не вправе самостоятельно

- Менять версии/компоненты стека за пределами `RL_Стек_v9.8.md`.
- Заменять npm на pnpm/Yarn/Bun, модульный монолит на monorepo, вводить микросервисы/Turborepo.
- Заменять Next.js App Router на Pages Router, TypeScript на JavaScript, ESLint на Biome.
- Подключать Auth.js вместо Better Auth либо начинать писать собственную авторизацию.
- Добавлять Redis, BullMQ, PWA/Serwist/Service Worker, офлайн-кэш, инструменты аналитики и внешние SaaS.
- Создавать ER-таблицы, менять FK/CHECK/типы/индексы, миграции или seed — это **W0-03 и последующие задания**.
- Подключать реальные OAuth, SMTP, Postfix, GlitchTip, Sber ID либо отправлять тестовые персональные данные во внешние сервисы.
- Считать demo-страницу завершением UC-01 или временный health endpoint доказательством готовности БД.
- Выбирать и закрывать `DEC-01`…`DEC-12` вместо заказчика, выдавать предложенную архитектуру за утверждённую без отдельного статуса.
- Затирать существующий код/историю Git, удалять ветки, форсировать push, менять чужие файлы без анализа.

**Важные пояснения:**

1. `src/server/modules/`, `src/server/auth/`, `src/server/db/`, `worker/`, `prisma/`, `infra/` и `src/generated/prisma/` **не обязаны существовать** после W0-01; соответствующие агенты создадут их по реальной необходимости.
2. Не создавать `src/app/api/auth/[...all]/route.ts` с фиктивным ответом: это реальная точка Better Auth из W0-04.
3. Не создавать `src/app/(admin)` и `(app)` с иллюзорной защитой: до W0-06 нет серверного guard. Страницы вне главной не нужны.
4. `src/app/api/health/route.ts` отвечает только за живость веб-процесса; признак готовности PostgreSQL добавляется позже отдельным решением.
5. Примерные файлы, созданные `create-next-app` (`next.svg`, `vercel.svg`, шаблонные картинки, приветственный экран Next.js), удалить, если они не нужны RL. **Не удалять** обязательную конфигурацию сборки.
6. Точные имена автоматически сгенерированных конфигов могут отличаться по patch-версии; сохранить поддерживаемую генератором форму, перечислить реальное дерево в отчёте.

## 6. Технологические версии и зависимости

### 6.1. Обязательные на данном шаге

| Компонент | Ограничение | Политика W0-01 |
|---|---|---|
| Node.js | `24.x LTS` | Запускать и проверять на Node 24; зафиксировать `.nvmrc` и `engines` |
| npm | Версия, поставляемая с установленным Node 24 | Один пакетный менеджер; `package-lock.json` обязателен; версию записать |
| TypeScript | `5.9.x` | `strict: true`; итоговый patch зафиксировать |
| Next.js | `16.4.x`, **не ниже 16.4.1** | Вариант на дату ТЗ: `16.4.6`, если доступен и проходит тесты |
| React и React DOM | `19.3.x` | Одинаковый точный patch у обоих; вариант `19.3.1` |
| Tailwind CSS | `4.x` | Стандартная актуальная интеграция Next.js, без Tailwind v3-конфигов |
| ESLint | Совместим с Next 16.4 | Использовать поддерживаемую конфигурацию генератора |
| Prettier | Стабильная версия, совместимая с Node 24 | Точный patch в `package.json`/lockfile |
| Vitest | `5.0.x` | Не переходить на 5.1.x/6.x без изменения нормативного стека |
| Playwright Test | `1.64.x` | Точный patch, только Chromium для smoke W0-01 |

**Версии, зафиксированные в ТЗ как варианты** (`16.4.6`, `19.3.1`), — локальная конкретизация допустимых линий, **не** право автоматически брать `latest`. Перед установкой агент проверяет доступность каждого пакета, peer dependencies и отсутствие известных критических уязвимостей на дату исполнения. Если безопасная версия **в разрешённой линии** недоступна, фиксирует блокер и не перескакивает на новую major/minor молча.

### 6.2. Не устанавливать заранее

`prisma`, `@prisma/client`, `@prisma/adapter-pg`, `better-auth`, `@better-auth/prisma-adapter`, `pg-boss`, `react-hook-form`, `zod`, `@tanstack/react-query`, `zustand`, `@xyflow/react`, `recharts`, `serwist`, `@serwist/next`, Redis/BullMQ, Nodemailer, Sentry SDK, GlitchTip-интеграции.

Эти компоненты либо требуют отдельного интеграционного задания, либо пока не используются. Их преждевременная установка увеличивает поверхность конфликта версий и стоимость сопровождения.

**shadcn/ui + Radix:** технология утверждена для будущего UI, **но W0-01 не требует компонентов шадцн/файла `components.json`**. Не запускать конфигуратор с дефолтным Base UI; настройка именно Radix станет предметом первой UI-задачи. Это не изменение стека, а отказ от неиспользуемого пакета на этапе каркаса.

## 7. Порядок реализации — точная последовательность

### Шаг 0. Инвентаризация и защита существующей работы

1. Проверить рабочий каталог, `git status`, наличие `.git`, `package.json` и документов.
2. Если каталог уже содержит репозиторий/проект, **не перегенерировать поверх и не удалять файлы**. Сначала описать совместимые изменения и работать аккуратно с существующим кодом.
3. Если рабочего проекта ещё нет, выбрать свободный каталог с именем `rl`. Для **полностью нового** проекта сначала запустить генератор из шага 1, который сам создаёт каталог; не создавать там заранее файлы или `.git`, иначе генератор может отказаться работать с непустым каталогом.
4. После генерации проверить, инициализировал ли CLI Git автоматически. Если нет — выполнить `git init -b main` **внутри** каталога `rl`. В существующем репозитории `git init` пропустить.
5. Записать текущие версии Node, npm, Git и ОС в `docs/handover/W0-01-report.md`.
6. Не создавать удалённый GitHub-репозиторий и не делать push без заранее предоставленных прав и явно заданного адреса remote.

Предварительная проверка окружения (PowerShell/терминал):

```bash
node --version
npm --version
git --version
```

Для нового проекта Git инициализируется **после шага 1**, если генератор этого не сделал. Для существующего проекта сохранить его `.git` и историю.

### Шаг 1. Создать Next.js-проект

Для **нового** проекта использовать официальный генератор с закреплённой версией. Ниже пример для сценария, когда команда запускается **из родительского каталога** и создаёт папку `rl`:

```bash
npx --yes create-next-app@16.4.6 rl \
  --ts --eslint --tailwind --app --src-dir \
  --import-alias "@/*" --use-npm --no-react-compiler --yes
cd rl
```

В PowerShell обратный слэш `\` не продолжает строку. Поэтому эквивалент для Windows PowerShell **одной строкой**:

Отказ генератора — повод проверить поддерживаемые CLI-флаги с `--help`, а не удалять репозиторий.

Перед дальнейшими шагами проверить, что проект действительно использует `src/app`, `tsconfig.json`, Tailwind v4 и что `npm run dev` показывает страницу. React Compiler не включать автоматически; его необходимость в этой задаче отсутствует.

### Шаг 6. Добавить liveness API

Реальный файл: `src/app/api/health/route.ts`.

```http

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

```

Требования:

- Route Handler Next.js App Router; метод `GET`.
- Статус 200 только если веб-процесс смог обработать запрос.
- Отсутствие вызовов БД, OAuth, SMTP, worker или любого внешнего сервиса.

## 8. Нефункциональные требования

### 8.1. Качество и понятность кода

- TypeScript strict; ошибки не «лечить» `any`, `@ts-ignore`, `eslint-disable` без объяснения.
- Понятные компоненты и функции, минимум абстракций. Не создавать generic base repositories, plugin architecture, DI-контейнер, CQRS, event bus.
- Не использовать `useEffect`/глобальный store там, где достаточно Server Component.
- Имена исходных функций/переменных — понятный английский; UI-тексты — русский.
- Нет незавершённых `TODO` по обязательной части W0-01. Задокументированные TODO будущих волн допустимы **только в документации**, не как код заглушек.

### 8.2. Безопасность

- Не сохранять пользовательские ПД в статическом HTML, тестах и логах.
- Не использовать стороннюю аналитику, удалённые шрифты, шрифтовые CDN или runtime-запросы к внешним сервисам. Для W0-01 применять системные шрифты либо локальные ресурсы; если стартовый шаблон использует `next/font/google` с сетевой загрузкой при сборке, заменить его на системный стек для воспроизводимости и снижения внешних зависимостей.
- Не добавлять внешние telemetry endpoints. При необходимости отключить Next.js CLI telemetry поддерживаемой настройкой среды/командой и записать это в README; не ломать функциональность ради запрета.
- При сборке проект может скачивать публичные npm-пакеты/браузер Chromium, но это **не** означает право отправлять туда будущие данные пользователей RL.

### 8.3. Производительность и UX

- Каркас должен открываться без базы и без API внешних провайдеров.
- На мобильном экране 320 px не должно быть горизонтальной прокрутки.
- Не добавлять тяжёлые графические зависимости, диаграммы, анимации и маркетинговые панели без задачи.
- Действия, для которых нет backend, не показывать как работоспособные.

### 8.4. Консистентность с архитектурой

- Не превращать `DEC-01` (`PROPOSED` web/worker модульный монолит) в утверждение только потому, что создан Next.js репозиторий. W0-01 создаёт совместимый каркас, а техническое утверждение фиксируется отдельным ADR/решением.
- Не обещать атомарность Better Auth + RL; библиотека ещё не подключена.
- Не создавать третью схему БД и инфраструктуру pg-boss; это отдельный `VERIFY` в W0-07.
- `DEC-05=FIXED`: заказчик утвердил Postfix outbound в Docker на VPS РФ, локально Mailpit, без Dovecot/IMAP/POP3 и приёма входящей почты. W0-01 **не** устанавливает Postfix/Mailpit и не объявляет email-верификацию работоспособной. `DEC-06` (числовые пороги rate limiting) по-прежнему `BLOCKED`.

## 14. Передача следующему AI-агенту (W0-02)

Следующий исполнитель получает **работающий** Next.js-каркас и добавляет к нему локальную PostgreSQL 16 через Docker Compose. Он должен иметь возможность:

- открыть репозиторий и прочитать `AGENTS.md`, актуальные требования v9.8 и архитектуру v1.3;
- выполнить `npm ci`, `npm run dev` и базовые проверки;
- создать `infra/compose.yaml`, переменные локальной БД и volumes, не изменяя контракт `/api/health` без отдельного решения;
- после W0-02 передать чистую PostgreSQL следующему исполнителю W0-03, который создаст Prisma-схему и миграции;
- не искать и не устранять недокументированные конфликты пакетов, необходимость второго пакетного менеджера или скрытые зависимости от настоящих OAuth/SMTP credentials.

**Итоговый критерий качества W0-01:** другой AI-агент или разработчик, не участвовавший в создании репозитория, способен воспроизвести сборку и увидеть страницу RL, не задавая исполнителю вопросов о командах, версиях и расположении файлов.
