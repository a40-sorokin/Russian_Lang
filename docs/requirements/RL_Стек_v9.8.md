# Уточнение архитектуры первой очереди — 09.11.2026

PostgreSQL 16: одна физическая база данных, две схемы: `auth` (Better Auth) и `public` (RL). Prisma 7.8 с явной настройкой нескольких схем и межсхемных связей, сгенерированных Better Auth; реальные имена таблиц сверяются с адаптером.
Регистрация: после подтверждения email создание `user_profile` и student-role атомарно в RL. Не заявлять атомарность между Better Auth и RL без подтверждённого совместного TransactionClient; при раздельной границе — компенсация и запрет доступа незавершённой identity. Удаление: транзакция RL по очистке истории и обезличиванию `user_profile` с `user_deletion_jobs`, затем идемпотентное удаление Better Auth через pg-boss и повторы; никаких BullMQ/Redis для этой функции.
Тренировка колоды: серверное состояние в PostgreSQL (deck_training_session), транзакционные ответы, идемпотентность answer_request_id; pg-boss очищает просроченные сессии.
Раздел «Юридические требования» исходной таблицы относится к вопросам за пределами функционального объёма первой очереди. Сохраняются технические меры безопасности и размещение данных в России.

### Настройки сервиса — 10.11.2026

Серверная конфигурация (env/конфигурация приложения, недоступна клиенту): `admin_email` — email бутстрапа администратора (роль admin назначается при регистрации с подтверждённым совпадающим email: OAuth — сразу, Email/Password — после подтверждения email; смена настройки не действует ретроактивно); N — дневной лимит посетителя (по умолчанию 4); M — рекомендуемый интервал повторного прохождения версии (по умолчанию 2 часа); временная зона календарных суток (по умолчанию Europe/Moscow); лимит размера текста версии (по умолчанию 30 720 байт UTF-8 после нормализации).

Расширенный anti-abuse вне первой очереди, но минимальный серверный rate limiting чувствительных Better Auth endpoints (вход, сброс пароля и подтверждения) обязателен по безопасности. Один активный email — один профиль; **неявное связывание по совпадению email запрещено**, пользователь доказывает владение обоими способами входа через UC-40.

### Изменения жизненного цикла пользователя — 11.11.2026

- Настройка `service_setting.email_registration_enabled` boolean NOT NULL DEFAULT true управляет только новой регистрацией; вход, смена и восстановление пароля существующего аккаунта работают при false.
- Better Auth использует scrypt по умолчанию; исходные пароли не сохраняются. Пароль 8–128 символов, для длины 8–11 — предупреждение, непредустановленный чекбокс и явное согласие в текущем запросе без хранения.
- Требуется отправка писем подтверждения и восстановления через российского провайдера; при сбое письма подтверждения регистрация остаётся незавершённой, специальная обработка доставки вне первой очереди.
- `user_profile` сохраняет ID при удалении, все идентифицирующие поля очищаются; данные авторизации, сессии и личная история удаляются, публичные материалы сохраняются. Первый администратор не может самоудаляться; для остальных обязательна повторная аутентификация. Риск 152-ФЗ зафиксирован и требует юридической проверки до запуска.
- Телеметрия Better Auth отключена; токены, raw email и пароли не включать в логи; чувствительные данные, резервные копии и почтовый шлюз должны соответствовать требованиям размещения в РФ.

## Требования к реализации удаления

- Использовать PostgreSQL 16 и Prisma 7.8; сравнить реальные миграции с матрицей ожидаемых FK посредством `RL_FK_audit_PostgreSQL_v9.8.sql`.
- Better Auth identity удаляется после транзакционной очистки RL; нельзя считать атомарными две фазы без доказанной общей транзакционной границы.
- `pg-boss` — механизм фонового исполнения, но источник истины о незавершённом удалении — `user_deletion_jobs` в PostgreSQL; нужен recovery polling.
- Обязательны DB-триггеры защиты founder и интеграционные тесты на настоящем PostgreSQL; middleware/API-проверок недостаточно.
- Для первого этапа не вводить Redis/BullMQ и не задавать произвольные сроки хранения резервных копий и задач удаления.
- Любое отклонение реальной схемы Better Auth от предполагаемой требует обновления плана очистки, а не обхода FK.


## Интеграционные требования

**Better Auth/OAuth:** регистрация новых пользователей начинается на RL-странице согласий, затем OAuth `state`, callback и обязательный экран завершения nickname. Без подтверждённого email требуется собственная email verification RL; при невозможности обработки callback без email сначала выполнить интеграционный спайк. Не создавать фиктивный email. Активный `user_profile` создаётся после всех проверок.

**PostgreSQL:** уникальность `(user_id, submission_request_id)` для `dictation_done`, атомарный повтор результата по UUID, триггер запрета блокировки founder, блокировки для soft delete колоды и ответа. `user_deletion_jobs`: максимум 10 неуспешных попыток, затем `failed_manual_review`.

**Frontend:** для первой очереди не подключать Serwist и не регистрировать Service Worker. Проверять 30 720 байт нормализованного UTF-8 на сервере, а не число символов.

**GlitchTip:** MIT для используемого проекта по состоянию на проектирование; перед фиксацией версии подтвердить SPDX/LICENSE конкретного релиза и его компонентов. Лицензия разрешает коммерческое использование, но не заменяет соблюдение 152-ФЗ.


**Однократный bootstrap `admin_email` (нормативное правило).** Настройка применяется только пока в БД не существует ни одного `user_profile.is_founder_admin=true`. После появления founder любое новое совпадение подтверждённого email с текущим либо изменённым `admin_email` **игнорируется для выдачи ролей**: новый пользователь получает только student; admin назначается только отдельной авторизованной административной операцией. Сам `admin_email` не является постоянным механизмом назначения ролей. Проверка и назначение первого founder должны быть сериализованы транзакцией и защищены частичным уникальным индексом; гонка обрабатывается повторной проверкой, без выдачи второй admin-роли. Изменение настройки не меняет исторические роли и founder.


**Безопасность P0:** минимальный серверный rate limiting обязателен для регистрации, входа, OAuth callback/state, запроса и проверки email-кода/ссылки, сброса пароля и повторной отправки писем. Расширенный поведенческий anti-abuse вне первой очереди. До реализации агент фиксирует проверяемые лимиты для каждого endpoint в отдельном конфигурационном перечне; запрещено оставлять неограниченные чувствительные endpoint.


**Транзакционная почта P0 — выбран способ, доставка ещё не проверена.** `DEC-05=FIXED`: собственный Postfix для исходящего SMTP в Docker на VPS РФ, Mailpit локально, без Dovecot/IMAP/POP3 и входящей почты. `MAIL_DELIVERY_VERIFICATION=VERIFY` до W0-08: подтвердить доступ к исходящему TCP 25, SPF/DKIM/DMARC/PTR, фактическую доставку подтверждения email и восстановления пароля, повторы/очередь/ошибки и ограничение поздних bounce без входящей почты. Запретить открытый relay и хранение секретов в Git; сторонние почтовые сервисы не подключать без отдельного утверждения заказчика. Не подменять реальную доставку локальным Mailpit в production. Подробности — архитектура v1.3, §9.1, ADR-004.

**Открытый параметр перед кодированием:** числовые пороги security rate limiting остаются `DEC-06=BLOCKED`; почтовая технология фиксирована (`DEC-05=FIXED`), но продуктивную отправку и интеграцию email-зависимых сценариев нельзя принимать без реальных проверок W0-08.

## Требования к проверкам перед реализацией

**Сессии при блокировке UC-21.** Канонический статус — `user_profile.is_locked`; не активировать самостоятельный Better Auth `banUser` как параллельный источник статуса без отдельного согласованного решения. Для отзыва всех активных сессий использовать проверенный server-side `revokeUserSessions` (Better Auth Admin plugin или эквивалент установленной версии); проверить callback/login-запрет и доступ с ранее созданными cookies. Отказ отзыва — обязательный повтор через существующую инфраструктуру фоновых задач, при этом каждый запрос уже блокируется RL. Восстановление после падения между коммитом блокировки и постановкой фонового задания: раз в минуту worker находит `is_locked=true` и существующие `auth.session` для их `auth_user_id` в общей PostgreSQL, сверяет актуальность блокировки и повторно вызывает отзыв до исчезновения сессий. Новую таблицу создавать не требуется; опрос и вызов идемпотентны. Документация API: https://www.better-auth.com/docs/plugins/admin.

**PostgreSQL Unicode.** Для валидации nickname использовать явные классы кириллических символов без диапазонов `[а-яА-Я]` и явный `COLLATE "C"` только в regex; уникальность по `lower(nickname COLLATE "und-x-icu")` — при наличии установленной детерминированной ICU-коллации. Полную локаль PostgreSQL-кластера ради этого не менять. Отсутствие ICU — блокер миграции до выбора эквивалентного решения; интеграционные тесты — PostgreSQL 16 из production-образа.

**Почта P0.** Утверждён Postfix (только исходящая почта, Docker/VPS РФ), для локальных испытаний — Mailpit; не разворачивать Dovecot/IMAP/POP3 и входящий SMTP. `DEC-05=FIXED`; необходима реальная проверка `MAIL_DELIVERY_VERIFICATION` на W0-08. Внешние провайдеры не выбираются AI-агентом.
